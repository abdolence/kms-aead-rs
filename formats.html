KMS envelope encryption for Rust

Formats

Every byte layout the library reads or writes is on this page.

The library writes one envelope format for every provider, Tink’s KMS envelope. A value encrypted by KmsAeadEnvelope::encrypt decrypts with Tink’s KmsEnvelopeAead on the same KMS key and algorithm, and a value Tink encrypts decrypts with KmsAeadEnvelope::decrypt.

Tink’s KMS envelope

KmsAeadEnvelope::encrypt writes Tink’s KMS envelope, and Encrypted::join writes it from a bare value and an encrypted DEK. separate reads it back:

use kms_aead::backends::Ring;
use kms_aead::formats::Envelope;
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{Encrypted, KmsAeadEnvelope};
use secret_vault_value::SecretValue;

#[tokio::main(flavor = "current_thread")]
async fn main() -> kms_aead::KmsAeadResult<()> {
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::new(provider)?;
let encrypted: Encrypted<SecretValue, Envelope> =
    envelope.encrypt(b"aad", &SecretValue::from("secret")).await?;

let (bare, encrypted_dek) = encrypted.separate()?;
let joined = Encrypted::<SecretValue, Envelope>::join(&bare, &encrypted_dek)?;
assert_eq!(joined.value(), encrypted.value());
Ok(())
}
  • w is 1 to 4,096 bytes, the limit of every Tink implementation, on write and on read;
  • the encrypted DEK is the provider’s EncryptedDataEncryptionKey, the KMS ciphertext of the serialised DEK, or of the raw DEK for Azure;
  • the AAD goes to the DEK’s AEAD only. The KMS encryption of the DEK has no AAD, as in Tink, so Tink’s AWS client sends no encryption context and its GCP client no additional authenticated data;
  • the rest is a Bare value.

The envelope records neither the algorithm nor the KEK version, so the writer and the reader, kms-aead or Tink, are configured with the same algorithm. Tink calls it the DEK template:

AlgorithmTink key typeTink for Java and GoTink for C++ and Python
ChaCha20-Poly1305ChaCha20Poly1305Keyreads and writesno
AES-128-GCM, AES-256-GCMAesGcmKeyreads and writesreads and writes
AES-256-GCM-SIVAesGcmSivKeyreads and writesreads and writes

AES-256-GCM is the default of KmsAeadEnvelope::new, so every Tink implementation reads the values of an envelope that names no algorithm. The default of 0.29 and earlier was ChaCha20-Poly1305, see Migrating from 0.29.

Tink for Python reads a kms-aead value with the key URI of the provider’s key:

from tink import aead
from tink.integration import gcpkms

aead.register()
key_uri = 'gcp-kms://projects/p/locations/l/keyRings/r/cryptoKeys/k'
remote = gcpkms.GcpKmsClient(key_uri).get_aead(key_uri)
envelope = aead.KmsEnvelopeAead(aead.aead_key_templates.AES256_GCM, remote)
plain_text = envelope.decrypt(value, aad)

Checked on a Cloud KMS key and an AWS KMS key, both ways: AES-128-GCM, AES-256-GCM and AES-256-GCM-SIV with Tink 1.16.1 for Python, and ChaCha20-Poly1305 with Tink 1.24.0 for Java on the Cloud KMS key. tests/tink_interop.py and examples/tink_interop.rs repeat the Python check.

Encrypted DEKs

EncryptedDataEncryptionKey is the bytes the provider returned from an encryption, which are also the bytes to store and the bytes it decrypts. Each provider’s bytes name the KEK version that encrypted the DEK where the KMS needs one to decrypt:

ProviderBytesKey version
GCPthe Cloud KMS ciphertext, starting with 0x0ainside the ciphertext
AWSthe AWS KMS ciphertext blob, starting with 0x01not exposed
Azure[0x01][k: u8][key version: k][Key Vault encrypted DEK]in the layout
Vault Transitthe Transit ciphertext, vault:vN:…the N
local[0x01][i: u8][KEK id: i][KEK version: u32 BE][nonce: 12][encrypted DEK][tag: 16]in the layout
any, encrypted with a public key[0x02][a: u8][i: u8][KEK id: i][k: u8][KEK version: k][RSA block], see DEKs encrypted with a public keyin the layout
an application’s ownwhatever it returns

The Azure layout is the library’s own: Key Vault decrypts only with the key version that encrypted, and no Tink client exists for Azure. For the same reason, the Key Vault encrypted DEK is the KMS ciphertext of the raw DEK of 16, 32 or 64 bytes, as in 0.29, not of the serialised DEK: AES key wrap, A128KW to A256KW, takes only multiples of 8 bytes, which no serialised DEK is. The local KMS encrypts the DEK with AES-256-GCM under the KEK version, with its header up to the version as the AAD, so neither the id nor the version can be changed without the decryption failing.

The 0x02 layout is the same for every KMS: a producer holding the public half of an RSA key encrypts the DEK in its own process, and the provider of the KMS that holds the private half decrypts it. The providers of 0.31 read it beside their own bytes, and no earlier release reads it, see DEKs encrypted with a public key and Asymmetric KEKs.

Store value() or to_hex_string(), and read them back with EncryptedDataEncryptionKey::from or try_from_hex_string. Neither holds the KEK version of kek_version(), see Storing encrypted DEKs.

Serialised DEKs

The plaintext a provider encrypts is the DEK serialised as Tink serialises a key, the message of its Tink key type with version 0, which protobuf leaves out. The Azure provider encrypts the raw DEK instead, see Encrypted DEKs:

AlgorithmMessageBytes
ChaCha20-Poly1305ChaCha20Poly1305Key[0x12][0x20][key: 32]
AES-128-GCMAesGcmKey[0x1a][0x10][key: 16]
AES-256-GCMAesGcmKey[0x1a][0x20][key: 32]
AES-256-GCM-SIVAesGcmSivKey[0x1a][0x20][key: 32]
AES-256-SIV, deterministicAesSivKey[0x12][0x40][key: 64]
HMAC-SHA256, MAC keyHmacKey[0x1a][0x20][key: 32]
HMAC-SHA512, MAC keyHmacKey[0x1a][0x40][key: 64]

A beacon key of HMAC-SHA256 is serialised as [0x1a][0x20][key: 32], its 32 bytes in key_value, field 3, as in Tink’s HmacPrfKey without its parameters: the bytes of a 32-byte AesGcmKey. It is encrypted as a DEK is, raw under an Azure key. A MAC key of a keyring is serialised the same way, in field 3 and never in field 2, since [0x12][0x40][key: 64] is byte for byte an AES-SIV key, see MACs in a keyring.

KmsAeadEnvelope::generate_encrypted_dek, generate_encrypted_deterministic_dek and the generate_encrypted_dek of both ciphers and of BeaconMac encrypt their keys the same way. The message does not name its type, and AES-256-GCM and AES-256-GCM-SIV keys are written alike, so the algorithm of the reader decides how the key is used, as in Tink.

A decrypted DEK that is no serialised Tink key, or under an Azure key no raw DEK, fails with INVALID_KEY_FORMAT. An encrypted Tink keyset decrypts under the same KEK too, and this is what keeps it out of the DEK cache.

Tink keysets and the TINK prefix

Two items describe the TINK-prefixed values:

  • kms_aead::KeyId: the key id of Tink’s output prefix of type TINK, [0x01][key id: u32 BE], the start of every Randomized and Deterministic value and of every beacon. It picks the key that decrypts the value, and Tink and BigQuery pick the key of a keyset by it. It is not authenticated;
  • kms_aead::formats::TinkKeyset: a serialised google.crypto.tink.Keyset of enabled, symmetric, TINK-prefixed keys, the bytes tinkey writes for the same keys. Encrypted by a Cloud KMS key, it is the keyset of BigQuery’s KEYS.KEYSET_CHAIN: an application writes it for its one key, see One fixed key, and a keyring exports it for its versions.

TinkKeyset::into_encrypted_bytes writes the keyset encrypted by a KMS key, as Tink writes an encrypted keyset: a google.crypto.tink.EncryptedKeyset whose encrypted_keyset, field 2, is the KMS ciphertext of the serialised keyset, encrypted with no associated data. Tink’s binary keyset writers leave out keyset_info, field 3, and so does the library. Tink’s KeysetHandle.read reads it with the KMS client of KekRef::tink_key_uri, which Tink has for GCP and AWS keys, and Tink for Go for Vault Transit keys too. A keyring exports it for its versions, see Exporting a keyset to Tink.

Formats of Encrypted

Every value the library encrypts is an Encrypted<T, F>: the bytes of one layout, named by its format F from kms_aead::formats. Encrypted::try_from and Encrypted::try_from_hex_string check stored bytes against it:

FormatLayoutShortest valuekey_id()Written by

Bare[nonce: 12][ciphertext][tag: 16]28 bytesnoneAeadCipher::encrypt_bare, KmsAeadEnvelope::encrypt_with_dek and encrypt_with_encrypted_dek, Encrypted::separate
Randomized[0x01][key id: u32 BE][nonce: 12][ciphertext][tag: 16]33 bytesKeyIdAeadCipher::encrypt, and kms-aead-keyring through it

A Bare value is Tink’s AEAD output under a key with the output prefix RAW, and the part of every Envelope value after the encrypted DEK. It names no key: the application keeps track of the key that decrypts it.

The check reads the framing only, and whether the bytes are authentic is known when they are decrypted. With legacy-formats, an Envelope value also holds the envelope layout v1 of 0.29 and the length-prefixed envelope, checked by their lengths, so a column decodes its old rows into the same type until they are upgraded, see Upgrading stored values. Without the feature, Encrypted::try_from refuses them with LEGACY_FORMAT. separate refuses them in every build. The layout of 32-bit targets before 0.24.0 has Tink’s framing, so it reads as an Envelope value in every build, and KmsAeadEnvelope::decrypt decrypts it with legacy-formats.

The plaintext inside is the encoding of the value’s Plaintext type: UTF-8 for String, the bytes themselves for Vec<u8> and SecretValue, true or false for bool, decimal ASCII for the integers, and compact JSON for JsonEncoded<T>. See Stored values.

Beacons

A Beacon<T> is a prefix and a truncated HMAC-SHA256:

[0x01][key id: u32 BE][HMAC-SHA256: the first ceil(bits / 8) bytes]
  • 0x01 is the version of the beacon layout. A later layout takes another first byte, so that beacons of both layouts can share a column during a re-index;
  • the key id names the beacon key that calculated the beacon;
  • the HMAC keeps its first bits bits, and the unused low bits of the last byte are zero. A beacon is 6 to 37 bytes.

The HMAC covers the bits, the context and the plaintext, as the Plaintext type encodes it:

HMAC-SHA256(key, [bits: u16 BE][context length: u32 BE][context][plaintext])

so that beacons of two fields, or of two bit counts, never match. Beacon::try_from checks the prefix and that 1 to 32 bytes of HMAC follow, and fails with INVALID_BEACON_FORMAT otherwise.

Keyring key ids

kms-aead-keyring writes the key id of a version into the TINK prefix of every value and beacon under it. The two high bits of the id are the purpose, and the rest is the ordinal:

BitsMeaning
31set for deterministic versions, alone
30set for beacon versions, alone
31 and 30set for MAC versions
0 to 29the ordinal, from 1, counted per purpose

So the ids of each purpose are:

  • randomised: 1, 2, 3, …;
  • deterministic: 2147483649, 2147483650, …;
  • beacon: 1073741825, 1073741826, …;
  • MAC: 3221225473, 3221225474, ….

An id whose ordinal is 0 is reserved: 0, 2^30, 2^31 and 2^31 + 2^30. A value that carries one fails with ReservedKeyId. A value whose id is of another purpose than the call fails with KeyPurposeMismatch. Both fail before any store or KMS call. Ids are never reused: a destroyed version keeps its id in the record. A key id goes up to 2^32 - 1, so a SQL column holding one is a BIGINT.

A reader fails with RecordInvalid on a document that breaks any of:

  • at most one active and one pending version per purpose, neither of them compromised;
  • an encrypted DEK on every version but the destroyed ones, and a kek_version, when there is one, of 1 to 255 ASCII alphanumerics beside it;
  • unique key ids of the purpose of their algorithm, increasing within a purpose in creation order;
  • no two versions with the same encrypted_dek bytes (DuplicateEncryptedDek), so that a key filed under a second id is refused where the record is read;
  • a seal_epoch of 1 or more;
  • seal_epochs on every active, decrypt-only and retired version and on no pending one, open on the active version, starting at 1 or more and below its end, and within the seal_epoch.

Encryption markers

An encryption marker is the re-encryption epoch of the keyring record a write encrypted a record’s fields under, which the application stores beside them:

[0x01][re-encryption epoch: u32 BE]

5 bytes in all, so that markers compare as their epochs do, and so do their bytes as Firestore, PostgreSQL and BigQuery compare them. EncryptionMarker::ENVELOPE, 01 00 00 00 00, is epoch 0, the marker of a record of envelope values. EncryptionMarker::try_from fails with InvalidEncryptionMarker on bytes of any other length or first byte. Serde stores a marker as bytes, an array of numbers in serde_json, and the postgres and sqlx features as BYTEA. See Sweeps for the query it serves.

The record’s JSON members for the epoch and the ranges keep the names seal_epoch and seal_epochs. KeyVersion::reencrypt_range() returns the markers of a version’s seal_epochs as a ReencryptRange: start(), and end(), None while the range is open. A record whose fields were encrypted through one Encryptor, and which stores the marker of the encryptor’s record, lies in the range of every version its fields are under. See Records under a version for the query it serves.

DEKs encrypted with a public key

An encrypted DEK that a public key encrypted has one layout for every KMS:

[0x02][a: u8][i: u8][KEK id: i bytes][k: u8][KEK version: k ASCII alphanumerics][RSA block]
  • 0x02 is the layout. No encrypted DEK of a built-in provider starts with it before 0.31, see Telling layouts apart;
  • a is the algorithm: 0x01 for RSA-OAEP with SHA-256 as the OAEP hash and the MGF1 hash, and an empty label. A later algorithm is another value;
  • i and the KEK id are the local KEK’s LocalKekId. i is 0 for a cloud KEK;
  • k and the KEK version are the version the public key carried, as the reader names it to its KMS: 1 to 255 ASCII alphanumerics. k is 0 under AWS KMS, which has no versions, and the version is the decimal LocalKekVersion under the local KMS;
  • the RSA block is as long as the modulus: 256, 384 or 512 bytes for a key of 2048, 3072 or 4096 bits. The encrypted DEK is the header and the block, 260 bytes under AWS KMS with a 2048-bit key.

The block is the OAEP encryption of the DEK in the form its KEK’s provider encrypts it: the serialised DEK, or the raw DEK under Key Vault. The seed of OAEP is random, so two encryptions of one DEK differ.

A reader checks the header against its own shape before any KMS call, and refuses the encrypted DEK with ASYMMETRIC_ENCRYPTED_DEK_FORMAT otherwise: a known algorithm byte; a header within the bytes; i of 0 for a cloud KEK; k of 0 under AWS KMS and 1 or more elsewhere; a block of 256, 384 or 512 bytes. Nothing in the header is authenticated: a changed version or KEK id names a key that fails to decrypt the block, and no change decrypts a value.

How each KMS decrypts the block:

KMSRequest
Google Cloud KMSAsymmetricDecrypt on <key>/cryptoKeyVersions/<version>, ciphertext the block
AWS KMSDecrypt with KeyId the key, EncryptionAlgorithm RSAES_OAEP_SHA_256 and CiphertextBlob the block
Azure Key VaultunwrapKey on the key and the version with alg RSA-OAEP-256
Vault Transitdecrypt on the key with ciphertext vault:v<version>: and the standard base64 of the block, padding_scheme oaep and hash_algorithm sha2-256
Local KMSRSA-OAEP decryption with the version’s private key

None of the four KMS decryptions takes a label or an AAD. What binds a value to its place is its own AAD.

Streamed values

A streamed value is a header and chunks. Every length is in bytes and integers are big-endian. The prefixed form, the one of AeadCipher::stream_encryptor and of the keyring:

offset          len     field
     0            1     0x01, Tink's output prefix of type TINK
     1            4     key id, u32: the keyring version that encrypted the value, or the caller's KeyId
     5           24     salt, random per value
    29           32     key commitment
    61       16,400     chunk 0: 16,384 bytes of ciphertext and a 16-byte tag
    61 + k × 16,400     chunk k

The bare form is a Cobblestone-256 message as C2SP chunked encryption writes it, with the caller’s AAD as its context and the DEK as its input key:

offset          len     field
     0           24     salt
    24           32     key commitment
    56       16,400     chunk 0
    56 + k × 16,400     chunk k

The envelope form, the one KmsAeadEnvelope::stream_encryptor writes, puts the encrypted DEK in front of the bare form, as Tink’s KMS envelope puts it in front of a bare value:

offset          len     field
     0            4     w, u32: the length of the encrypted DEK, 1 to 4,096
     4            w     encrypted DEK, the provider's EncryptedDataEncryptionKey
 4 + w           24     salt
28 + w           32     key commitment
60 + w       16,400     chunk 0
60 + w + k × 16,400     chunk k
  • the header H is 61 bytes in the prefixed form, 56 in the bare form and 60 + w in the envelope form. From the Cobblestone header on, the forms are the same;
  • every chunk but the last is 16,400 bytes as stored. The last chunk is 16 to 16,399 bytes, the tag and 0 to 16,383 bytes of ciphertext, so a plaintext of a multiple of 16,384 bytes ends with a tag alone. An empty plaintext is the header and one tag, 77 bytes prefixed, 72 bare and 76 + w in the envelope form. There is one chunking for each length;
  • only the first byte of a prefixed header is checked when it is read. The key id is not authenticated: it names the key that decrypts the value;
  • a reader of the envelope form reads w from the first 4 bytes, refuses a w outside 1 to 4,096 before it fetches or allocates anything, then reads the 60 + w bytes of the header. The encrypted DEK is not authenticated either: another value’s encrypted DEK decrypts to another DEK, which fails the key commitment;
  • no byte tells the bare form from the others, since a bare value starts with its random salt. The call names the form.

The keys come from the DEK K of 32 bytes, the salt and the AAD A:

key || base nonce || commitment = HKDF-Expand(SHA-512, PRK = K,
    info = "c2sp.org/chunked-encryption@v1+" || "AEAD_AES_256_GCM" || 0x00 || salt || A,
    length = 32 + 12 + 32)

With a 32-byte PRK, HKDF-Expand is two HMAC-SHA-512 calls: T1 = HMAC(K, info || 0x01) gives the key (T1[0..32]), the base nonce (T1[32..44]) and commitment[0..20] (T1[44..64]), and T2 = HMAC(K, T1 || info || 0x02) gives commitment[20..32] (T2[0..12]). A reader derives all three and compares the commitment in constant time before it decrypts a chunk. The AAD is bound here and nowhere else: each chunk’s GCM associated data is empty.

Chunk k holds plaintext bytes [k × 16,384, (k + 1) × 16,384) and is AES-256-GCM(key, N_k, aad = "", M_k), with the nonce N_k = base nonce XOR k, k as a 96-bit big-endian integer. There is no final flag: the final chunk is the one that is shorter than a full one.

For a plaintext of L bytes the stored length is Z = H + L + 16 × n with n = L div 16,384 + 1 chunks. From a stored length Z, with body = Z - H:

Z < H + 16          refused: shorter than the header and one tag
n = body div 16,400 + 1
r = body - (n - 1) × 16,400     the final chunk as stored
r < 16              refused: r = 0 is a value cut at a chunk boundary, 1 to 15 no encryptor writes
n > 2^38            refused
L = body - 16 × n

A value holds at most 2^38 chunks, 4 PiB less one byte of plaintext. The refusals are STREAM_LENGTH. Z is what the store reports: until the final chunk has been decrypted, L is the store’s word. A reader that reads the value to its end needs no Z: the bytes after the last full chunk are the final chunk, and the rules above hold for the length it read.

For a plaintext range [a, b) with a <= b <= L, the chunks to decrypt and the bytes to fetch are below. A range open at the start has a = 0 and one open at the end has b = L, so .. is [0, L):

first = a div 16,384
end   = n                      if b == L: the final chunk, even when it holds no plaintext
        first                  if a == b < L
        (b - 1) div 16,384 + 1 otherwise
ciphertext = [H + first × 16,400, min(Z, H + end × 16,400))

The reader cuts the decrypted plaintext to [a - first × 16,384, b - first × 16,384). For a = 1,000,000 and b = 1,064,512 the chunks are 61..65 and the bytes [1,000,461, 1,066,061) prefixed or [1,000,456, 1,066,056) bare, and 4 + w bytes further in the envelope form.

Signatures and MACs

Detached and attached signatures and MACs are Tink-prefixed values:

LayoutTypeBytesLength
Detached signatureSignature<T>see Signatures and MACskms-aead
Attached signatureSigned<T>see Signatures and MACskms-aead
Detached MACMac<T>see Signatures and MACskms-aead, and kms-aead-keyring for its MAC versions
Attached MACWithMac<T>see Signatures and MACskms-aead, and kms-aead-keyring for its MAC versions
  • 0x01 is the version of the layout. A later layout takes another first byte;
  • the key id names the key that signed or computed the tag. It is not authenticated and is a hint only: a value whose id is changed verifies under no key;
  • the signature is the raw signature of the key’s algorithm: 64 bytes for Ed25519 (RFC 8032) and r || s with each scalar left-padded to 32 bytes for P-256. The algorithm is not in the value: the verifying key fixes it;
  • the tag is the full HMAC output, never truncated: 32 bytes under HMAC-SHA256, 64 under HMAC-SHA512. The key version’s algorithm fixes the length;
  • w is the signature or tag length, 1 to 65,535, so a reader finds the payload at offset 7 + w without knowing the key.

TryFrom<Vec<u8>> checks a value against its layout and fails with INVALID_SIGNATURE_FORMAT or INVALID_MAC_FORMAT.

Every signature and every MAC is computed over the pre-image, never over the payload itself. It is the Pre-Authentication Encoding (PAE) of DSSE, the Dead Simple Signing Envelope, with the SHA-256 of the payload as its body:

pre-image = "DSSEv1" SP DEC(len(type)) SP type SP "32" SP SHA-256(payload)
  • SP is one byte 0x20;
  • DEC(n) is n in ASCII decimal with no leading zeros;
  • type is the payload type: 1 to 255 bytes of visible ASCII, 0x21 to 0x7E, such as application/vnd.example.invoice+json;
  • SHA-256(payload) is the 32-byte digest of the payload bytes.

The pre-image is 46 to 302 bytes long. Ed25519 signs it as it is, and ECDSA P-256 signs its SHA-256. A MAC is the HMAC of the pre-image. The payload is the bytes Signable::to_payload returns, which the library neither parses nor re-serialises.

The key id of a signing key is derived from its public key:

thumbprint input = {"crv":"Ed25519","kty":"OKP","x":"<base64url of the 32 bytes>"}
                 | {"crv":"P-256","kty":"EC","x":"<base64url of x>","y":"<base64url of y>"}
digest           = SHA-256(thumbprint input)
kid              = base64url(digest), without padding, 43 characters
key id           = the first four bytes of digest, as a big-endian u32

The thumbprint input is the JWK thumbprint of RFC 7638: the required members of the key in lexicographic order, with no whitespace. A publisher with a numbering of its own sets the id instead, and the published key carries it as the integer member kms_aead_key_id. The key id of a MAC key is the keyring’s id of the version, see Keyring key ids.

A set of public keys is a JWK Set (RFC 7517). Each key has kty, crv, x (and y), kid the full thumbprint, use sig and alg EdDSA or ES256, and kms_aead_key_id where the publisher set the id:

The signed keyring record

A keyring record carries its signature as the top-level member signature, the standard base64 of a detached Signature over the record’s canonical document:

canonical = JCS(record document without its "signature" member)
pre-image = PAE("application/vnd.kms-aead.keyring-record+json", SHA-256(canonical))

JCS is the JSON Canonicalization Scheme of RFC 8785: members sorted by name, no whitespace, standard string escaping with non-ASCII kept as UTF-8 and control characters as \u00XX. It is computed over the parsed JSON document with every member kept, including members this release does not know, so a later release may add members and sign records that carry them. A record holds strings, integers, booleans, null, arrays and objects; a fraction, an exponent or an integer beyond 2^53 anywhere in it is RECORD_INVALID. Telling layouts apart

The first bytes of a stored value:

First bytesLayout
00 00 00 00the length-prefixed envelope of 0.28.1 and earlier
00, then a length of 1 to 4,096Tink’s KMS envelope, an envelope streamed value, or the 4-byte length prefix of 32-bit targets before 0.24.0
01envelope layout v1 of 0.29, or a TINK-prefixed value
02a DEK encrypted with the public half of an asymmetric KEK
FF 01encrypted DEK layout v1 of 0.29

Only the decrypted DEK tells a Tink envelope from the 32-bit layout before 0.24.0: a raw key of 16 or 32 bytes against a serialised Tink key, whose lengths differ. An encrypted DEK of AWS, Azure or the local KMS also starts with 0x01, and Tink’s LEGACY and CRUNCHY output prefixes with 0x00.

A column that holds two layouts:

  • Tink envelopes and TINK-prefixed values: the first byte, 0x00 or 0x01;
  • Tink envelopes and 0.29 envelopes: the first byte, 0x00 or 0x01;
  • Tink envelopes and 0.28.1 envelopes: the first four bytes;
  • 0.29 envelopes and TINK-prefixed values: no byte tells them apart, so the layout is recorded outside the value, such as in another column;
  • bare values and any other layout: a bare value has no framing, and its random nonce can start with any byte, so a column of bare values holds no other layout;
  • streamed values and bare streamed values: no byte tells them apart, since a bare one starts with its random salt, so the call names the form, as decrypt_bare does for a bare value, see Streamed values;
  • envelope streamed values and Tink envelopes: both start with [w][encrypted DEK], so the layout is recorded outside the value, as for bare values;
  • encrypted DEKs of 0.29 and of 0.30: 0xFF 0x01 starts no encrypted DEK of a built-in provider, so the library tells them apart for those. It never inspects the bytes of an application’s own provider: strip the header [0xFF][0x01][k][key version] of its 0.29 keys before reading them.

Values written by 0.29 and earlier

The layouts of 0.29 and earlier are read only with the deprecated legacy-formats feature:

  • KmsAeadEnvelope::decrypt reads the three envelope layouts, which Encrypted<T, Envelope> holds with the feature;
  • the *_with_encrypted_dek calls and the DEK cache read the encrypted DEK layout v1 of 0.29 and raw encrypted DEKs.

Encrypted::separate never reads the older envelope layouts: for Azure, the encrypted DEK they hold needs the provider to become its bytes.

Without the feature, reading them fails with KmsAeadError::LegacyFormat, the code LEGACY_FORMAT, and one of:

  • KmsAeadLegacyFormat::EnvelopeV1;
  • KmsAeadLegacyFormat::LengthPrefixedEnvelope;
  • KmsAeadLegacyFormat::EncryptedDekV1;
  • KmsAeadLegacyFormat::RawEncryptedDek, for an encrypted DEK that decrypts to the raw key. The values of 32-bit targets before 0.24.0 fail with it, since their framing is Tink’s.

The error never echoes the bytes read. With the feature, the first read of each layout in a process logs one WARN event that names the upgrade methods. Without it, the KMS AEAD decrypt spans of such values record error_code=LEGACY_FORMAT, see Observability.

Upgrading stored values

With legacy-formats, two methods of KmsAeadEnvelope rewrite a stored value in Tink’s format, and return None when it already is in it, so a sweep writes only the rows that change:

  • upgrade_legacy_value, for envelope values;
  • upgrade_legacy_encrypted_dek, for encrypted DEKs stored apart, such as the bytes of 0.29’s to_bytes.

Each decrypts the DEK with the provider, without the DEK cache, and encrypts it again as a serialised Tink key when it was in an older layout: one KMS call for a current value, two for an old one. A value in Tink’s framing needs the decryption to be told from the 32-bit layout before 0.24.0. The AEAD bytes stay as they are.

An upgraded DEK is encrypted under the KEK’s current version, so the upgrade also does what reencrypt_dek and reencrypt_encrypted_dek do for a value or a DEK already in Tink’s format, see Re-encrypting DEKs after a KEK rotation. Those two refuse a layout of 0.29 or earlier with LEGACY_FORMAT, so a sweep after a KEK rotation upgrades a value in an old layout and re-encrypts the DEK of a value in Tink’s format.

The envelope’s algorithm is the one the values were encrypted with: ChaCha20-Poly1305 for values that 0.29 and earlier encrypted under their default. A raw DEK does not record its algorithm, and the encrypted DEK of the upgrade records it as a Tink key type, so upgrade_legacy_value takes the value’s AAD and decrypts the value before it writes anything. Under another algorithm or another AAD it fails with DECRYPT. upgrade_legacy_encrypted_dek has no value to decrypt, so it records the envelope’s algorithm for any key of its length. Be aware not to upgrade a DEK stored apart under another algorithm than its values were encrypted with: use upgrade_legacy_value wherever the values are at hand.

A sweep over stored rows:

use kms_aead::backends::AeadBackend;
use kms_aead::formats::Envelope;
use kms_aead::{Encrypted, KmsAeadDecryptionProvider, KmsAeadEnvelope, KmsAeadResult};
use secret_vault_value::SecretValue;

/// A stored envelope value and the AAD it was encrypted under.
struct Row {
    aad: Vec<u8>,
    value: Vec<u8>,
}

/// Rewrites the envelope values of `rows` in Tink's format, and returns how many changed.
#[allow(deprecated)]
async fn upgrade_values<P, B>(
    envelope: &KmsAeadEnvelope<P, B>,
    rows: &mut [Row],
) -> KmsAeadResult<usize>
where
    P: KmsAeadDecryptionProvider,
    B: AeadBackend,
{
    let mut upgraded = 0;
    for row in rows.iter_mut() {
        let stored = Encrypted::<SecretValue, Envelope>::try_from(row.value.clone())?;
        if let Some(value) = envelope.upgrade_legacy_value(&row.aad, &stored).await? {
            row.value = value.into_value();
            upgraded += 1;
        }
    }
    Ok(upgraded)
}
use kms_aead::backends::Ring;
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{AeadAlgorithm, AeadCipher, KmsAeadEncryptionProvider, KmsAeadEnvelopeOptions};
#[tokio::main(flavor = "current_thread")]
async fn main() -> KmsAeadResult<()> {
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
// A value as 0.28.1 wrote it: [w: u64 BE][encrypted raw key][cipher text]
let cipher = AeadCipher::<Ring>::new(AeadAlgorithm::ChaCha20Poly1305)?;
let dek = cipher.generate_dek()?;
let bare = cipher.encrypt_bare(b"aad", &SecretValue::from("secret"), &dek)?;
let encrypted_dek = provider.encrypt_data_encryption_key(&dek).await?;
let mut legacy = u64::try_from(encrypted_dek.value().len()).unwrap().to_be_bytes().to_vec();
legacy.extend_from_slice(encrypted_dek.value());
legacy.extend_from_slice(bare.value());
let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::with_options(
    provider,
    KmsAeadEnvelopeOptions::new().with_algorithm(AeadAlgorithm::ChaCha20Poly1305),
)?;
let mut rows = vec![Row { aad: b"aad".to_vec(), value: legacy }];
assert_eq!(upgrade_values(&envelope, &mut rows).await?, 1);
assert_eq!(upgrade_values(&envelope, &mut rows).await?, 0);
let upgraded = Encrypted::<SecretValue, Envelope>::try_from(rows[0].value.clone())?;
let decrypted: SecretValue = envelope.decrypt(b"aad", &upgraded).await?;
assert_eq!(decrypted, SecretValue::from("secret"));
Ok(())
}

Upgrade every reader to 0.30 before the sweep writes: 0.29 and earlier cannot read Tink’s format.

Deprecation

Reading the layouts of 0.29 and earlier is deprecated since 0.30.0 and will be removed in a later breaking release, together with the legacy-formats feature and the upgrade methods, which carry #[deprecated] from their first release, so every call site warns. Without the feature, the older layouts keep failing with LEGACY_FORMAT.

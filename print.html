KMS envelope encryption for Rust

KMS envelope encryption for Rust

Library provides envelope encryption with a key encryption key held by a KMS, and AEAD encryption without a KMS:

  • KMS providers for:
    • Google Cloud KMS;
    • AWS KMS;
    • Azure Key Vault and Managed HSM;
    • HashiCorp Vault Transit;
    • A local KMS with a key the application holds, for development, tests and single-host installs;
  • AEAD algorithms ChaCha20-Poly1305, AES-128-GCM, AES-256-GCM and AES-256-GCM-SIV;
  • Tink’s KMS envelope format for every provider, so Tink reads the values of GCP and AWS keys and the library reads Tink’s, see Formats;
  • Crypto backends ring, aws-lc-rs (including its FIPS module) and the pure Rust RustCrypto crates. A value sealed by one backend opens with any other;
  • Per-call envelopes, store-less DEK reuse, and an in-process cache of decrypted data encryption keys;
  • Deterministic encryption with AES-SIV, for values that are looked up by equality;
  • Typed fields, Encrypted<T, F>, stored with serde, tokio-postgres or sqlx;
  • Optional KMS-side random generators for GCP and AWS;
  • Field encryption with a keyring, in the kms-aead-keyring crate: key versions kept in Firestore, PostgreSQL, Cloud Storage or S3, central staged rotation, beacons, and values in Tink’s wire format;
  • Tracing spans for every operation and every KMS call, with no plaintext, key material or AAD in them;
  • No unsafe code.

To start using the library, see Getting started.

Envelope encryption

A value is sealed with an AEAD algorithm under a data encryption key (DEK). The DEK is then encrypted by a key encryption key (KEK) that never leaves the KMS, and the encrypted DEK is stored next to the cipher text. KMS documentation, and Azure Key Vault’s wrapKey and unwrapKey operations, call this wrapping the DEK. To read the value, the KMS decrypts the DEK, and the DEK opens the value locally.

So the KMS sees only DEKs, never the data, and a KMS call is needed only to encrypt or decrypt a DEK. Access to the data is controlled by access to the KEK: revoke the KMS permission, or destroy the key, and the stored values cannot be opened.

The additional authenticated data (AAD) is authenticated but not encrypted: a value opens only with the AAD it was sealed with. Use it to tie a value to where it is stored, such as a table and a row id, so that a value copied to another row fails to open.

Choosing a mode

The ways to use a KMS differ in how many DEKs exist, how often the KMS is called and what a stored value holds:

  • Per-call envelope, the default of KmsAeadEnvelope: a new DEK for every value, encrypted with one KMS call, and stored in the value itself. Every decryption decrypts its DEK with one more KMS call, unless the envelope has a DEK cache. Use it when values are written rarely, such as secrets and configuration, or when one DEK per value is a requirement. See Envelope encryption;
  • Store-less DEK reuse, a KmsAeadEnvelope with a DekReusePolicy: one DEK seals many values and is renewed by age or by count, so a write calls the KMS only to renew it. Values still carry their encrypted DEK, so nothing is stored apart from them, and reads decrypt through the DEK cache. Use it for high write rates where a KMS call per value costs too much. See DEK caching and reuse;
  • One fixed key, encrypt of AeadCipher or DeterministicCipher with one key that the KMS encrypts once and the DEK cache decrypts: values carry a 4-byte key id in Tink’s wire format instead of an encrypted DEK, and BigQuery and Tink read them with a keyset of that key. Use it for a column that BigQuery reads, with no key rotation. See One fixed key;
  • Keyring, the kms-aead-keyring crate: a keyring record per scope holds the encrypted DEK versions, and values carry a 4-byte key id in Tink’s wire format instead of an encrypted DEK. The record is the place for central rotation and retirement of keys, and for values that BigQuery and Tink read across rotations. See Keyring and field encryption.

Getting started

Cargo.toml:

[dependencies]
kms-aead = { version = "0.30", features = ["gcp-kms-encryption", "aws-lc"] }

The crate has no default features. A build makes three choices, and they do not constrain each other:

  1. the KMS providers, any number of them, or none for AEAD without a KMS;
  2. the TLS root store and the TLS crypto provider of each provider that has a choice;
  3. the crypto backends that run the AEAD algorithms, one or more.

Features

Every feature of both crates is in Cargo features.

Choosing a backend

The default features of the four cloud providers already build aws-lc-rs for TLS, so aws-lc is the backend that adds no second crypto library to a provider build. ring and rustcrypto work with every provider too, and a build may enable several backends at once. Each feature adds a type to kms_aead::backends, Ring, AwsLc or RustCrypto, and every type that seals or encrypts takes one as its backend type parameter:

fn example() -> kms_aead::KmsAeadResult<()> {
use kms_aead::backends::AwsLc;
use kms_aead::{AeadAlgorithm, AeadCipher};

let cipher = AeadCipher::<AwsLc>::new(AeadAlgorithm::Aes256Gcm)?;
let _ = cipher;
Ok(())
}

There is no default backend. Code generic over the backend bounds it with B: AeadBackend and nothing else, see Crypto backends.

With an envelope

The local KMS needs no cloud account, so it is the quickest way to try the library. An ephemeral KEK lives as long as the process:

use kms_aead::backends::Ring;
use kms_aead::formats::Envelope;
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{Encrypted, KmsAeadEnvelope};
use secret_vault_value::SecretValue;

#[tokio::main(flavor = "current_thread")]
async fn main() -> kms_aead::KmsAeadResult<()> {
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::new(provider)?;

let aad = b"orders/1042";
let secret = SecretValue::from("4111 1111 1111 1111");

let encrypted: Encrypted<SecretValue, Envelope> = envelope.encrypt(aad, &secret).await?;
let decrypted: SecretValue = envelope.decrypt(aad, &encrypted).await?;

assert_eq!(decrypted, secret);
Ok(())
}

To move to a cloud KMS, replace the provider, see KMS providers. The rest of the code stays the same.

With a keyring

Field encryption under a keyring is the kms-aead-keyring crate, see Keyring and field encryption. Its features are in Cargo features.

Cargo.toml:

[dependencies]
kms-aead = { version = "0.30", features = ["gcp-kms-encryption", "ring"] }
kms-aead-keyring = { version = "0.30", features = ["ring", "firestore"] }

A keyring on the memory store with a local KEK, for an application type Email. It needs no cloud credentials, and needs the admin feature for create, rotate and promote:

use kms_aead::backends::Ring;
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::KmsAeadResult;
use kms_aead_keyring::formats::Randomized;
use kms_aead_keyring::testing::MemoryKeyringStore;
use kms_aead_keyring::{
    Encrypted, EntityId, EntityKind, FieldAad, FieldName, FieldSpec, KeyId, Keyring, KeyringAdmin,
    KeyringAlgorithms, KeyringId, KeyringRegistry, KeyringRegistryOptions, Plaintext, Purpose,
    Sealer,
};
use secret_vault_value::SecretValue;

#[derive(Debug, Clone, PartialEq)]
struct Email(String);

impl Plaintext for Email {
    fn to_plaintext(&self) -> KmsAeadResult<SecretValue> {
        self.0.to_plaintext()
    }

    fn from_plaintext(plaintext: SecretValue) -> KmsAeadResult<Self> {
        String::from_plaintext(plaintext).map(Email)
    }
}

const TENANT: KeyringId = KeyringId::from_static("tenant-42");
const EMAIL: FieldSpec = FieldSpec::new(
    EntityKind::from_static("user"),
    FieldName::from_static("email"),
);

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
let provider =
    LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("tenant-kek".to_string())?)?;
let registry = KeyringRegistry::<MemoryKeyringStore, Ring>::new(
    MemoryKeyringStore::new(),
    KeyringRegistryOptions::new(),
)?;
let admin: KeyringAdmin<MemoryKeyringStore, LocalKmsProvider<Ring>, Ring> = registry
    .create(provider, TENANT, KeyringAlgorithms::new())
    .await?;
// The application's handle on the same keyring
let keyring: &Keyring<MemoryKeyringStore, LocalKmsProvider<Ring>, Ring> = admin.keyring();

// The AAD ties the value to user 42's email: `user/42/email`
let aad: FieldAad = EMAIL.aad(&EntityId::try_from("42")?);
let alice = Email("alice@example.com".to_string());
// One sealer per write of a record, for every encrypted field it holds
let sealer: Sealer<'_, MemoryKeyringStore, LocalKmsProvider<Ring>, Ring> = keyring.sealer().await;
let value: Encrypted<Email, Randomized> = sealer.encrypt(&aad, &alice).await?;
assert_eq!(value.key_id(), KeyId::new(1));

// A staged rotation keeps the previous version decrypting. One process has nothing to wait for,
// so it promotes at once
let staged: KeyId = admin.rotate(Purpose::Randomized).await?;
admin.promote_now(staged).await?;
assert_eq!(keyring.decrypt(&aad, &value).await?, alice);
registry.shutdown().await?;
Ok(())
}

Move envelope values to a keyring

Values that kms-aead’s KmsAeadEnvelope wrote, per call or store-less, move to keyring values in five steps:

  1. the model gains seal: SealMarker, and every record without one reads as SealMarker::ENVELOPE: through #[serde(default)], or a column default of its bytes, '\x0100000000';
  2. the field keeps its stored bytes, whose layout the marker names: envelope values under ENVELOPE, epoch 0, and keyring values under any other marker, since the epochs of a keyring start at 1;
  3. reads go through the marker: Keyring::decrypt_envelope_for_migration opens an envelope value, with the AAD and the algorithm the application used for it, and Keyring::decrypt a keyring value;
  4. the sweep’s query, seal < $1 with the current marker, finds every envelope record too, and the re-seal seals it as keyring values through a sealer and writes the marker of the sealer’s record;
  5. once no record holds ENVELOPE, the read path drops its envelope branch.

A range query never matches a record whose marker is missing: Firestore skips a document without the field, and < in SQL is never true on NULL. A PostgreSQL column added with a default holds it in every existing row. A BigQuery column holds NULL there until an UPDATE writes ENVELOPE, see BigQuery. Firestore documents written before the marker get ENVELOPE written into them first, or the migration’s first sweep scans the whole collection and tests doc.seal < current on each, since #[serde(default)] reads a missing marker as ENVELOPE.

The keyring’s provider decrypts the envelope values, so they must have been encrypted by the keyring’s KEK. decrypt_envelope_for_migration reads Tink’s KMS envelope, the layout kms-aead 0.30 writes. Values written by kms-aead 0.29 or earlier are upgraded in place first, with KmsAeadEnvelope::upgrade_legacy_value(aad, value) under kms-aead’s legacy-formats feature, see Upgrading stored values. The layout of a value is always the marker’s, never inferred from its bytes.

decrypt_envelope_for_migration decrypts whatever encrypted DEK an envelope value carries, under the keyring’s KEK. It knows no key version, and so no compromised flag and no destroyed state: keep its branch in the read path for the migration only.

Full example available here, run it with cargo run -p kms-aead-keyring --example migrate --features ring,admin,serde.

Migrating from 0.29

0.30 replaces the ring-only API with a choice of crypto backends, adds store-less DEK reuse, the DEK cache, deterministic encryption and the local KMS, and makes ring optional. It writes Tink’s KMS envelope format for every provider, so values written by 0.29 and earlier read only with the deprecated legacy-formats feature, which also rewrites them in the new format, see Old values. The default algorithm of the envelope is AES-256-GCM, see Default algorithm.

Every cipher text is an Encrypted<T, F>, see Formats. It has its own value() and into_value(), and so has EncryptedDataEncryptionKey. DataEncryptionKey no longer implements ValueStruct, and has its own value().

Your own provider

An application’s own implementation of the provider trait:

  • implements KmsAeadEncryptionProvider instead of KmsAeadRingEncryptionProvider;
  • adds fn kek(&self) -> &KekRef, with KekProvider::Other and a key name that identifies the key;
  • deletes generate_encryption_key when it returned the backend’s key. The replacement, generate_key_material(&self, len), has a default implementation that lets the backend generate the key, and is implemented only for a KMS generator;
  • returns EncryptedDataEncryptionKey::new(bytes) from encrypt_data_encryption_key, with the KEK version the KMS reported added by with_kek_version. A KMS that needs the key version to decrypt gets it from those bytes, as the Azure provider’s do.

The plaintext the provider encrypts is the DEK serialised as a Tink key, see Formats. The library never inspects the provider’s own bytes.

Errors

KmsAeadError is #[non_exhaustive], so an exhaustive match on it needs a _ arm. It has two new variants, UnsupportedAlgorithm and LegacyFormat. code() returns the code of any variant, and source() returns the root cause.

The From conversions of SDK errors into KmsAeadError are gone: gcloud_sdk::error::Error, gcloud_sdk::tonic::Status, the AWS SdkError, the hyper client error, azure_core::Error and SystemTimeError. Map an SDK error in the application.

The variant of a Google Cloud KMS or AWS KMS error follows its code. In 0.29 every gRPC status was a NetworkError and every AWS error an EncryptionError. A PermissionDenied or NotFound from Google Cloud KMS is an EncryptionError now, and a timeout, a connection failure or a ThrottlingException from AWS KMS a NetworkError. The codes stay the same. See Retries.

ConstantTimeEq is no longer implemented on the public types. == still compares in constant time. The Debug of Encrypted prints only the length, and == is gone from randomised values: only an Encrypted<T, Deterministic> has it.

AWS KMS decryption names the key

The AWS provider sends the configured key as KeyId on every decryption. In 0.29 a decryption left it out, so AWS KMS decrypted under whichever key the encrypted DEK named, for any key the principal may decrypt with. A 0.30 process refuses a DEK encrypted under another key with IncorrectKeyException. A deployment that relied on decrypting under a second key configures a provider per key.

An alias name such as alias/orders becomes an alias ARN, where 0.29 built a key ARN of it. Configure the key ARN rather than an alias, see AWS KMS.

Default algorithm

The default algorithm of KmsAeadEnvelope is AES-256-GCM, which every Tink implementation reads in a KMS envelope. The default of 0.29 was ChaCha20-Poly1305.

A value does not record its algorithm. Values sealed under the default of 0.29 open only with ChaCha20-Poly1305 configured, and an envelope on the new default fails them with DECRYPT. A 0.29 envelope that named no algorithm becomes:

use kms_aead::backends::Ring;
use kms_aead::providers::{GcpKmsKeyRef, GcpKmsProvider};
use kms_aead::{AeadAlgorithm, KmsAeadEnvelope, KmsAeadEnvelopeOptions};

async fn example(key_ref: GcpKmsKeyRef) -> kms_aead::KmsAeadResult<()> {
// 0.29: KmsAeadRingEnvelopeEncryption::new(provider).await?
let envelope = KmsAeadEnvelope::<GcpKmsProvider, Ring>::with_options(
    GcpKmsProvider::new(&key_ref).await?,
    KmsAeadEnvelopeOptions::new().with_algorithm(AeadAlgorithm::ChaCha20Poly1305),
)?;
let _ = envelope;
Ok(())
}

Configure it on every envelope that reads those values, on the one that upgrades them, see Old values, and on every envelope that writes new values beside them: a reader cannot tell the two algorithms apart. AES-256-GCM suits a column that holds no 0.29 values.

Old values

0.30 writes Tink’s KMS envelope, and encrypts every DEK but Azure’s as a serialised Tink key. 0.29 wrote envelope layout v1 and the encrypted DEK layout v1 [0xFF][0x01]…, and 0.28.1 and earlier a length-prefixed envelope, all with the raw DEK encrypted. 0.30 reads them only with the deprecated legacy-formats feature, and fails with LEGACY_FORMAT without it, see Formats.

The envelopes that read and upgrade those values keep the algorithm they were sealed with, see Default algorithm.

To move stored values to the new format:

  1. upgrade every process that reads the values to 0.30 with legacy-formats. 0.29 and earlier cannot read Tink’s format, so no process writes it before every reader has the upgrade;
  2. rewrite the stored values with upgrade_legacy_value and upgrade_legacy_encrypted_dek of KmsAeadEnvelope, one or two KMS calls per value, see Upgrading stored values. upgrade_legacy_value takes the value’s AAD, and fails with DECRYPT on a value that does not open under the envelope’s algorithm and that AAD;
  3. turn the feature off.

Encrypted::<T, Envelope>::separate reads Tink’s format only, with or without the feature, so code that separated stored 0.29 values runs after the sweep.

Stored values

Three types carry what the library writes to a data store and reads back:

  • Encrypted<T, F>: an encrypted value that decrypts to a T, in the layout of the format F;
  • Beacon<T>: a blind index of a T, stored beside its encrypted value for lookups;
  • Plaintext: the trait of every T, which fixes the bytes a value is sealed as.

The T is a type of the application, such as an Email newtype, so a column names what it holds: Encrypted<Email, Envelope> and Beacon<Email>. Neither type holds a T, only the bytes to store.

  • key_id() returns the KeyId that the TINK prefix names, the key to open the value with. The prefix is not authenticated: a changed key id fails to decrypt;
  • an Envelope value carries its encrypted DEK instead of a key id, and a Bare value names no key: the application keeps track of the key that opens it;
  • the randomised formats seal equal plaintexts into different values, so they have no ==. Compare value() to tell whether two values are the same stored bytes;
  • only Deterministic values are equal for equal plaintexts under one key and one AAD, which is what a lookup by the encrypted value needs, see Deterministic encryption;
  • Debug shows the length only.

Bytes in and out

value() and into_value() return the bytes to store, and to_hex_string() returns them as lowercase hex. The only ways back are Encrypted::try_from for bytes and Encrypted::try_from_hex_string for hex in either case. Both check the bytes against the layout of F before any KMS call, so a truncated or foreign value fails when it is read, with INVALID_CIPHER_TEXT_FORMAT, UNKNOWN_CIPHER_TEXT_LAYOUT, INVALID_HEX, or LEGACY_FORMAT for a layout of 0.29 or earlier without the legacy-formats feature. The check reads the framing only: a changed value fails to decrypt with DECRYPT.

use kms_aead::backends::Ring;
use kms_aead::formats::Randomized;
use kms_aead::{AeadAlgorithm, AeadCipher, Encrypted, KeyId};
use secret_vault_value::SecretValue;

fn main() -> kms_aead::KmsAeadResult<()> {
let cipher = AeadCipher::<Ring>::new(AeadAlgorithm::Aes256Gcm)?;
let dek = cipher.generate_dek()?;
let encrypted: Encrypted<SecretValue, Randomized> =
    cipher.encrypt(KeyId::new(1), b"users/1042/token", &SecretValue::from("token"), &dek)?;

// The key the prefix names
assert_eq!(encrypted.key_id(), KeyId::new(1));

// Hex for a text column, bytes for a binary one
let stored_hex: String = encrypted.to_hex_string();
let stored: Vec<u8> = encrypted.into_value();

let from_bytes = Encrypted::<SecretValue, Randomized>::try_from(stored)?;
let from_hex = Encrypted::<SecretValue, Randomized>::try_from_hex_string(&stored_hex)?;
assert_eq!(from_bytes.value(), from_hex.value());

// A prefix with nothing after it is no randomised value
assert!(Encrypted::<SecretValue, Randomized>::try_from(vec![0x01, 0, 0, 0, 1]).is_err());
Ok(())
}

Storing

Three features store Encrypted as bytes, and each one reads it back through TryFrom, so a malformed stored value fails in the decode:

  • serde: Serialize and Deserialize, a bytes value in Firestore and an array of numbers in serde_json;
  • postgres: ToSql and FromSql of postgres-types, for tokio-postgres, as BYTEA, and a slice as BYTEA[] for = ANY($1);
  • sqlx: sqlx’s Type, Encode, Decode and PgHasArrayType for PostgreSQL, as BYTEA. It depends on sqlx-core and sqlx-postgres only, so the application chooses sqlx’s runtime and TLS stack.

Beacon<T>

A beacon, or blind index, is a truncated HMAC-SHA256 of a T’s plaintext under a beacon key. It is stored beside the field’s encrypted value, which stays randomised, and a data store matches it by equality without the plaintext or a decryption:

[0x01][key id: u32 BE][HMAC-SHA256: the first ceil(bits / 8) bytes]
  • 0x01 is the version of the beacon layout;
  • key_id() returns the KeyId of the beacon key that calculated it, so that a column holds beacons of two keys during a re-index;
  • BeaconBits sets how many bits of the HMAC a beacon keeps, 1 to 256, BeaconBits::DEFAULT, 16, unless set. BeaconBits::new returns None outside that range;
  • value() and into_value() return the bytes to store, and Beacon::try_from reads them back, failing with INVALID_BEACON_FORMAT on bytes of another layout;
  • == and Hash compare the bytes, == in constant time, and Debug shows the key id only.
use kms_aead::backends::Ring;
use kms_aead::{Beacon, BeaconAlgorithm, BeaconBits, BeaconMac, KeyId};
use kms_aead::{KmsAeadResult, Plaintext};
use secret_vault_value::SecretValue;
#[derive(Debug, Clone, PartialEq)]
struct Email(String);
impl Plaintext for Email {
    fn to_plaintext(&self) -> KmsAeadResult<SecretValue> { self.0.to_plaintext() }
    fn from_plaintext(plaintext: SecretValue) -> KmsAeadResult<Self> {
        String::from_plaintext(plaintext).map(Email)
    }
}

fn main() -> KmsAeadResult<()> {
let mac = BeaconMac::<Ring>::new(BeaconAlgorithm::HmacSha256);
let beacon_key = mac.generate_dek()?;

let email = Email("alice@example.com".to_string());
let beacon: Beacon<Email> =
    mac.beacon(KeyId::new(1), b"users/email", BeaconBits::DEFAULT, &email, &beacon_key)?;

// [0x01][key id: 4 bytes][16 bits of HMAC: 2 bytes]
assert_eq!(beacon.key_id(), KeyId::new(1));
assert_eq!(beacon.value().len(), 7);

let read_back = Beacon::<Email>::try_from(beacon.value().to_vec())?;
assert_eq!(read_back, beacon);
Ok(())
}

Plaintext

Plaintext maps a type to the bytes it is sealed as, and back. Every T of Encrypted<T, F> and Beacon<T> implements it. An application type implements it by mapping to one of the built-in types, such as a newtype over String that is sealed as the same UTF-8 bytes:

use kms_aead::{KmsAeadResult, Plaintext};
use secret_vault_value::SecretValue;

#[derive(Debug, Clone, PartialEq)]
struct Email(String);

impl Plaintext for Email {
    fn to_plaintext(&self) -> KmsAeadResult<SecretValue> {
        self.0.to_plaintext()
    }

    fn from_plaintext(plaintext: SecretValue) -> KmsAeadResult<Self> {
        String::from_plaintext(plaintext).map(Email)
    }
}

fn main() -> KmsAeadResult<()> {
let email = Email("alice@example.com".to_string());
assert_eq!(Email::from_plaintext(email.to_plaintext()?)?, email);
Ok(())
}

A newtype over SecretValue is written the same way:

use kms_aead::{KmsAeadResult, Plaintext};
use secret_vault_value::SecretValue;

#[derive(Debug, Clone, PartialEq)]
struct Email(SecretValue);

impl Plaintext for Email {
    fn to_plaintext(&self) -> KmsAeadResult<SecretValue> {
        Ok(self.0.clone())
    }

    fn from_plaintext(plaintext: SecretValue) -> KmsAeadResult<Self> {
        Ok(Email(plaintext))
    }
}

fn main() -> KmsAeadResult<()> {
let email = Email(SecretValue::from("alice@example.com"));
let decrypted: Email = Email::from_plaintext(email.to_plaintext()?)?;
assert_eq!(decrypted.0.as_sensitive_str(), "alice@example.com");
Ok(())
}

It differs from the String newtype as follows:

  • the decrypted value is zeroised on drop, and Debug prints *** instead of it;
  • text is sealed as the same bytes as through String, so AEAD.DECRYPT_STRING still reads it;
  • there is no UTF-8 check on read, so bytes that are not UTF-8 decrypt without an error;
  • the text is reached through SecretValue’s accessors rather than as a &str: as_sensitive_str(), which panics on bytes that are not UTF-8, or sensitive_value_to_str(), which returns an error.

SecretValue suits values that are secrets or personal data, and String values that are used as text throughout.

The built-in types encode as follows. The encodings are fixed, so that other readers of the same values, such as BigQuery’s AEAD.DECRYPT_STRING, decode them:

  • the decrypted value belongs to the application, which protects it. Only SecretValue as T is zeroised on drop; String and Vec<u8> take over the decrypted buffer without a copy;

Envelope encryption

KmsAeadEnvelope seals values under data encryption keys (DEKs) on the crypto backend it is built with, and encrypts the DEKs with the KEK of its provider. A call that makes no KMS call is not async, and every call opens one DEBUG span, see Observability.

use kms_aead::backends::Ring;
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{AeadAlgorithm, KmsAeadEnvelope, KmsAeadEnvelopeOptions};
use secret_vault_value::SecretValue;

#[tokio::main(flavor = "current_thread")]
async fn main() -> kms_aead::KmsAeadResult<()> {
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
// AES-256-GCM by default
let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::new(provider)?;

// Or another algorithm
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::with_options(
    provider,
    KmsAeadEnvelopeOptions::new().with_algorithm(AeadAlgorithm::ChaCha20Poly1305),
)?;
let _ = envelope;
Ok(())
}

The value does not record the algorithm, so the writer and the reader of a value must be configured with the same one. The backend can differ, see Crypto backends. The default, AES-256-GCM, is read by every Tink implementation too, see Formats. Values that 0.29 and earlier sealed under their default open only with ChaCha20-Poly1305 configured, see Migrating from 0.29.

Encrypting values

encrypt seals a value under a new DEK, encrypts the DEK with one KMS call, and returns both in one Encrypted<T, Envelope>, where T is the type of the value. decrypt decrypts the DEK with one KMS call, opens the value and returns a T. A value with no type of its own is a SecretValue:

use kms_aead::backends::Ring;
use kms_aead::formats::Envelope;
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{Encrypted, KmsAeadEnvelope};
use secret_vault_value::SecretValue;

#[tokio::main(flavor = "current_thread")]
async fn main() -> kms_aead::KmsAeadResult<()> {
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::new(provider)?;

let aad = b"orders/1042";
let encrypted: Encrypted<SecretValue, Envelope> = envelope
    .encrypt(aad, &SecretValue::from("4111 1111 1111 1111"))
    .await?;

// The bytes to store, and the value read back from them
let stored: Vec<u8> = encrypted.into_value();
let read_back = Encrypted::<SecretValue, Envelope>::try_from(stored)?;

let decrypted: SecretValue = envelope.decrypt(aad, &read_back).await?;
assert_eq!(decrypted, SecretValue::from("4111 1111 1111 1111"));
Ok(())
}

The bytes in and out of an Encrypted are in Stored values.

The value is in Tink’s KMS envelope format for every provider, so Tink’s KmsEnvelopeAead reads it with the same KMS key and algorithm, see Formats.

A new DEK comes from the backend’s CSPRNG, or from the KMS generator when the provider is configured to use one, see KMS random generators.

Typed fields

encrypt and decrypt take a value of any type that implements Plaintext, such as an application’s Email newtype, and the result is an Encrypted<T, Envelope> that names the type. The calls run in the envelope’s mode, a DEK per value or store-less DEK reuse, and decrypt through the envelope’s DEK cache, whatever the type. Plaintext, the bytes of an Encrypted and how serde, tokio-postgres and sqlx store it are in Stored values.

One fixed key

AeadCipher::encrypt seals a field under a key the application holds, in Tink’s layout of a key whose output prefix is TINK, [0x01][key id: u32 BE] before the AEAD value: an Encrypted<T, Randomized>. DeterministicCipher::encrypt does the same for an Encrypted<T, Deterministic>. The key id is a KeyId, the application’s constant, and Tink and BigQuery read the values with a keyset of the one key under that id:

use kms_aead::backends::Ring;
use kms_aead::cache::{DekCache, DekCacheOptions};
use kms_aead::formats::{Randomized, TinkKeyType, TinkKeyset};
use kms_aead::providers::{GcpKmsKeyRef, GcpKmsProvider};
use kms_aead::{
    AeadAlgorithm, AeadCipher, DataEncryptionKey, Encrypted, EncryptedDataEncryptionKey, KeyId,
    KmsAeadEncryptionProvider, KmsAeadResult, Plaintext,
};
use secret_vault_value::SecretValue;

#[derive(Debug, Clone, PartialEq)]
struct Email(String);

impl Plaintext for Email {
    fn to_plaintext(&self) -> KmsAeadResult<SecretValue> {
        self.0.to_plaintext()
    }

    fn from_plaintext(plaintext: SecretValue) -> KmsAeadResult<Self> {
        String::from_plaintext(plaintext).map(Email)
    }
}

// The id of the one key, in every value and in the keyset
const EMAIL_KEY: KeyId = KeyId::new(1);

async fn example() -> KmsAeadResult<()> {
let key_ref = GcpKmsKeyRef::new(
    "my-project".to_string(),
    "europe-north1".to_string(),
    "my-key-ring".to_string(),
    "my-key".to_string(),
);
let provider = GcpKmsProvider::new(&key_ref).await?;
let cipher = AeadCipher::<Ring>::new(AeadAlgorithm::Aes256Gcm)?;
let cache = DekCache::new(DekCacheOptions::new())?;

// Once, by an administrative job: the key encrypted by Cloud KMS, stored in the settings
let (_, encrypted_dek): (DataEncryptionKey, EncryptedDataEncryptionKey) =
    cipher.generate_encrypted_dek(&provider).await?;

// On every write and read: the key decrypted through the cache, no KMS call while it is cached
let email = Email("alice@example.com".to_string());
let (encrypted, _) = cache
    .with_dek(&provider, &encrypted_dek, |dek| {
        cipher.encrypt(EMAIL_KEY, b"users/1042/email", &email, dek)
    })
    .await?;
let encrypted: Encrypted<Email, Randomized> = encrypted?;

let (decrypted, _) = cache
    .with_dek(&provider, &encrypted_dek, |dek| {
        cipher.decrypt(b"users/1042/email", &encrypted, dek)
    })
    .await?;
let decrypted: Email = decrypted?;
assert_eq!(decrypted, email);

// Once, for BigQuery: the keyset of the one key, encrypted by the same Cloud KMS key
let mut keyset = TinkKeyset::new(EMAIL_KEY);
let (added, _) = cache
    .with_dek(&provider, &encrypted_dek, |dek| {
        keyset.add_key(EMAIL_KEY, TinkKeyType::from(cipher.algorithm()), dek)
    })
    .await?;
added?;
let first_level_keyset: EncryptedDataEncryptionKey = provider
    .encrypt_data_encryption_key(&DataEncryptionKey::from(keyset.to_bytes()))
    .await?;
let _ = first_level_keyset;
Ok(())
}

BigQuery reads the column with KEYS.KEYSET_CHAIN over the encrypted keyset, passed as a BYTES query parameter, beside the key’s Tink URI as a STRING one, gcp-kms://projects/my-project/locations/europe-north1/keyRings/my-key-ring/cryptoKeys/my-key:

SELECT AEAD.DECRYPT_STRING(
  KEYS.KEYSET_CHAIN(@kms_key, @first_level_keyset),
  u.email,
  CONCAT('users/', CAST(u.id AS STRING), '/email'))
FROM users u;
  • BigQuery reads AES-256-GCM values with AEAD.DECRYPT_STRING and AEAD.DECRYPT_BYTES, and the AES-SIV values of DeterministicCipher with DETERMINISTIC_DECRYPT_STRING and DETERMINISTIC_DECRYPT_BYTES. KEYS.KEYSET_CHAIN decrypts with Cloud KMS only;
  • AeadCipher::decrypt reads the values Tink and BigQuery write under the same key and id. The caller picks the key by key_id(), which the prefix names without authenticating it;
  • a rotation needs a second key id, values of both ids in one column and a keyset of both keys. kms-aead-keyring keeps those versions.

Beacons

A beacon, or blind index, finds rows by a field’s value without decrypting the column, see Beacons.

AAD

The AAD is authenticated but not encrypted: a value opens only with the AAD it was sealed with, and a wrong AAD fails with DECRYPT. Use it to bind a value to its place, such as <table>/<row id>/<column>, so that a value copied into another row or column fails to open.

The AAD is not stored in the value, so the reader rebuilds it from the same data. It is never logged or put in an error, but it is not secret either: keep secrets in the value itself.

The keyring takes a structured AAD instead of free bytes, built from the field and the row, see Why the AAD is structured.

Working with DEKs yourself

The *_with_dek and *_with_encrypted_dek calls let the application keep one DEK for many values and store the encrypted DEK apart from them, such as one DEK per tenant or per file. The values are Encrypted<T, Bare>, with no encrypted DEK in them.

use kms_aead::backends::Ring;
use kms_aead::formats::Bare;
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{Encrypted, KmsAeadEnvelope};
use secret_vault_value::SecretValue;

#[tokio::main(flavor = "current_thread")]
async fn main() -> kms_aead::KmsAeadResult<()> {
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::new(provider)?;

// One KMS call: a new DEK and the same DEK encrypted
let (dek, encrypted_dek) = envelope.generate_encrypted_dek().await?;

// No KMS call: seal and open with the plaintext DEK
let first: Encrypted<SecretValue, Bare> =
    envelope.encrypt_with_dek(b"files/1/chunk/0", &SecretValue::from("first"), &dek)?;
let second: Encrypted<SecretValue, Bare> =
    envelope.encrypt_with_dek(b"files/1/chunk/1", &SecretValue::from("second"), &dek)?;
let decrypted: SecretValue = envelope.decrypt_with_dek(b"files/1/chunk/0", &first, &dek)?;
assert_eq!(decrypted, SecretValue::from("first"));

// Later, with only the encrypted DEK: the envelope decrypts it with the KMS
let decrypted: SecretValue = envelope
    .decrypt_with_encrypted_dek(b"files/1/chunk/1", &second, &encrypted_dek)
    .await?;
assert_eq!(decrypted, SecretValue::from("second"));
Ok(())
}

The calls are:

  • generate_encrypted_dek: a new DEK and the same DEK encrypted, one KMS call;
  • encrypt_with_dek and decrypt_with_dek: with a plaintext DEK, no KMS call;
  • encrypt_with_encrypted_dek and decrypt_with_encrypted_dek: with an encrypted DEK, decrypted through the envelope’s DEK cache, so one KMS call per call without a cache.

Be aware not to seal more than about 2^32 values under one DEK: every value takes a random 96-bit nonce, see Security considerations.

Storing encrypted DEKs

EncryptedDataEncryptionKey holds the bytes the provider returned, which also name the KMS key version where the KMS needs one to decrypt after a rotation. Store value() or to_hex_string(), and read them back with EncryptedDataEncryptionKey::from or try_from_hex_string():

use kms_aead::backends::Ring;
use kms_aead::providers::{KekVersion, LocalKekId, LocalKmsProvider};
use kms_aead::{EncryptedDataEncryptionKey, KmsAeadEnvelope};

#[tokio::main(flavor = "current_thread")]
async fn main() -> kms_aead::KmsAeadResult<()> {
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::new(provider)?;
let (_dek, encrypted_dek) = envelope.generate_encrypted_dek().await?;

let stored: Vec<u8> = encrypted_dek.value().clone();
let read_back_encrypted_dek = EncryptedDataEncryptionKey::from(stored);

let stored_hex: String = encrypted_dek.to_hex_string();
let read_back_hex_encrypted_dek = EncryptedDataEncryptionKey::try_from_hex_string(&stored_hex)?;

assert_eq!(read_back_encrypted_dek, read_back_hex_encrypted_dek);

// The KEK version beside it, for the check before an old KEK version is disabled
let stored_kek_version: Option<String> = encrypted_dek.kek_version().map(KekVersion::to_string);
let read_back_kek_version: Option<KekVersion> =
    stored_kek_version.map(KekVersion::try_from).transpose()?;
let read_back_encrypted_dek = match read_back_kek_version {
    Some(kek_version) => read_back_encrypted_dek.with_kek_version(kek_version),
    None => read_back_encrypted_dek,
};
assert_eq!(read_back_encrypted_dek.kek_version(), encrypted_dek.kek_version());
Ok(())
}

An encrypted DEK that the provider has just returned carries in kek_version() the version of the KEK that encrypted it, as the KMS reported it. It is None under AWS KMS, whose Encrypt response names no key material, and wherever the KMS reported no version. Decryption never needs it, and neither value() nor to_hex_string() holds it, so an encrypted DEK read back from them has none. Stored beside the encrypted DEK, it shows without a KMS call which DEKs are still under an old KEK version, see The check. with_kek_version puts it back on the encrypted DEK read from the bytes.

Equality and hashing take the bytes alone, so an encrypted DEK read back without its KEK version is the same key, to the DEK cache and in a map, as the one the provider returned with it.

The encrypted DEK is the one Tink stores in its KMS envelope, so Encrypted::join of a bare value and its encrypted DEK is an Encrypted<T, Envelope> that Tink reads. See Formats for each provider’s bytes.

Re-encrypting DEKs after a KEK rotation

A KEK rotation makes the KMS encrypt new DEKs under a new key version, and every DEK stored before it keeps decrypting with the old version only. reencrypt_encrypted_dek and reencrypt_dek move a stored DEK to the current version, so the old version can be retired while the application keeps reading and writing:

  1. rotate the KEK in the KMS, as the page of each provider describes;
  2. re-encrypt every stored DEK: the DEKs of the stored values, the DEKs stored apart from their values, and the record of each keyring under the KEK with KeyringAdmin::reencrypt_deks. Then export the keyrings’ keysets again and re-encrypt the application’s own encrypted keysets, see Encrypted keysets;
  3. check that the kek_versions_in_use of every keyring record lists the new version alone. Then, once no process holds an encrypted DEK from before step 2, disable the old version, and check that the KMS decrypts every stored DEK, every keyring’s DEKs with reencrypt_deks, and every encrypted keyset. A DEK or a keyset it refuses is one the sweep missed: enable the old version again, sweep again and check again. When to disable, and how the local KMS checks before it, are in The check;
  4. keep the old version disabled for as long as the backups of the stored values are kept, check once more, then destroy it.

A backup taken before the sweep holds the DEKs under the old version, so destroying the old version makes every such backup unreadable for good. Keyring records are the same, see Key lifecycle. What a rotation, a disabled version and a destroyed version are differs per KMS, see the page of each provider.

The sweep

reencrypt_encrypted_dek makes two KMS calls: the KMS decrypts the DEK with the version that encrypted it and encrypts it again with its current one. The AEAD bytes of a value stay as they are, so the sweep takes no AAD, opens nothing, and the value decrypts as before. Each distinct encrypted DEK is re-encrypted once and joined with each of its values, so the values a store-less envelope wrote under one DEK still share one afterwards:

use std::collections::HashMap;

use kms_aead::backends::AeadBackend;
use kms_aead::formats::Envelope;
use kms_aead::{
    Encrypted, EncryptedDataEncryptionKey, KmsAeadEncryptionProvider, KmsAeadEnvelope,
    KmsAeadResult,
};
use secret_vault_value::SecretValue;

/// The bytes to write back for each stored value in `rows`, beside the bytes read, with its DEK
/// under the KEK's current version. Each distinct encrypted DEK is re-encrypted once.
async fn reencrypt_values<P, B>(
    envelope: &KmsAeadEnvelope<P, B>,
    rows: &[Vec<u8>],
) -> KmsAeadResult<Vec<(Vec<u8>, Vec<u8>)>>
where
    P: KmsAeadEncryptionProvider + Send + Sync,
    B: AeadBackend,
{
    let mut reencrypted: HashMap<EncryptedDataEncryptionKey, EncryptedDataEncryptionKey> =
        HashMap::new();
    let mut updates = Vec::with_capacity(rows.len());
    for row in rows {
        let stored = Encrypted::<SecretValue, Envelope>::try_from(row.clone())?;
        let (bare, encrypted_dek) = stored.separate()?;
        let new_encrypted_dek = match reencrypted.get(&encrypted_dek) {
            Some(new_encrypted_dek) => new_encrypted_dek.clone(),
            None => {
                let new_encrypted_dek = envelope.reencrypt_encrypted_dek(&encrypted_dek).await?;
                reencrypted.insert(encrypted_dek, new_encrypted_dek.clone());
                new_encrypted_dek
            }
        };
        updates.push((row.clone(), Encrypted::join(&bare, &new_encrypted_dek)?.into_value()));
    }
    Ok(updates)
}

Write each value back only where the stored bytes are still the ones read, with a compare-and-set such as UPDATE orders SET card = $new WHERE id = $id AND card = $read, or the store’s own conditional write. An unconditional write puts back the value the sweep read over one the application wrote in the meantime, which is then lost. A row the application rewrote keeps its new value, and the check in step 3 finds it if its DEK is still under the old version.

reencrypt_dek does the same for one value. It gives each value an encrypted DEK of its own, so values that shared a DEK would then cost one KMS encryption each in the sweep and one KMS decryption each on a cache miss afterwards. The same reencrypt_encrypted_dek re-encrypts the DEKs stored apart from their values, such as those of the *_with_encrypted_dek calls, of beacons and of deterministic fields. A value or a DEK in a layout of 0.29 or earlier fails with LEGACY_FORMAT: upgrade_legacy_value and upgrade_legacy_encrypted_dek rewrite it in Tink’s format, with its DEK under the current version, see Upgrading stored values.

The DEK cache plays no part: the sweep decrypts through the provider and leaves the cache as it is, so it evicts no entry that serves reads. Every call encrypts again, also for a DEK already under the current version. The sweep needs KMS encrypt and decrypt on the KEK.

The kek_version() of the encrypted DEK that reencrypt_encrypted_dek returns names the KEK version the KMS encrypted it with. Under Cloud KMS, a sweep that ran before the new primary version had propagated shows the old version there, and the DEKs it names are re-encrypted again.

Encrypted keysets

An encrypted keyset is a KMS ciphertext as well, under the KEK version that encrypted it, and reencrypt_encrypted_dek refuses one with INVALID_KEY_FORMAT, since what the KMS decrypts from it is a serialised keyset. A sweep of the DEKs leaves every keyset under the old version, so a query or a reader that opens one fails once the old version is disabled:

  • a keyring’s export_bigquery_keyset and export_tink_keyset: export each keyset again, with the same selection, after reencrypt_deks and, under Cloud KMS, after the new primary version has propagated. The new export holds the same keys, encrypted under the KEK’s current version. Write its bytes wherever the old ones are kept: the query parameter of each KEYS.KEYSET_CHAIN, a column or a setting that holds the keyset, and the file or the setting a Tink reader opens. See BigQuery;
  • the application’s own encrypted keyset, such as first_level_keyset in One fixed key: the provider decrypts it and encrypts it again, and the new bytes replace the old ones wherever they are kept:
use kms_aead::{EncryptedDataEncryptionKey, KmsAeadEncryptionProvider, KmsAeadResult};

/// `first_level_keyset` encrypted again under the KEK version the provider encrypts with now.
async fn reencrypt_keyset<P: KmsAeadEncryptionProvider>(
    provider: &P,
    first_level_keyset: &EncryptedDataEncryptionKey,
) -> KmsAeadResult<EncryptedDataEncryptionKey> {
    let keyset = provider.decrypt_data_encryption_key(first_level_keyset).await?;
    provider.encrypt_data_encryption_key(&keyset).await
}

The check decrypts the bytes of a BigQuery keyset and of the application’s own keyset through the provider, as it does an encrypted DEK, with EncryptedDataEncryptionKey::from of the bytes. A Tink keyset is a google.crypto.tink.EncryptedKeyset around the KMS ciphertext, and its check is an open with the Tink reader that uses it.

Pacing

The sweep makes two KMS calls per distinct encrypted DEK, and the check one, on top of the calls the application makes. Under a KMS with a request quota, as the cloud KMSs have, pace the sweep below it: a fixed number of DEKs per second, or a pause after each batch, with room left for the application. A sweep over the quota fails with the KMS’s error, such as ResourceExhausted on GCP, and so do the application’s own calls meanwhile.

The check

Once the old version is disabled, the KMS refuses every DEK still under it, so the check decrypts each distinct encrypted DEK through the provider, never through the DEK cache, which would serve a missed DEK from memory. It needs no AAD and opens no value, and it runs online, under every provider. Any error counts as a missed DEK:

use std::collections::HashSet;

use kms_aead::backends::AeadBackend;
use kms_aead::formats::Envelope;
use kms_aead::{
    Encrypted, EncryptedDataEncryptionKey, KmsAeadEncryptionProvider, KmsAeadEnvelope,
    KmsAeadResult,
};
use secret_vault_value::SecretValue;

/// The distinct encrypted DEKs of the values in `rows` that the provider fails to decrypt.
async fn missed_deks<P, B>(
    envelope: &KmsAeadEnvelope<P, B>,
    rows: &[Vec<u8>],
) -> KmsAeadResult<Vec<EncryptedDataEncryptionKey>>
where
    P: KmsAeadEncryptionProvider + Send + Sync,
    B: AeadBackend,
{
    let mut encrypted_deks: HashSet<EncryptedDataEncryptionKey> = HashSet::new();
    for row in rows {
        let stored = Encrypted::<SecretValue, Envelope>::try_from(row.clone())?;
        let (_, encrypted_dek) = stored.separate()?;
        encrypted_deks.insert(encrypted_dek);
    }
    let mut missed = Vec::new();
    for encrypted_dek in encrypted_deks {
        if envelope
            .provider()
            .decrypt_data_encryption_key(&encrypted_dek)
            .await
            .is_err()
        {
            missed.push(encrypted_dek);
        }
    }
    Ok(missed)
}

A keyring’s record names the KEK version of each of its DEKs, as the KMS reported it, so a first check makes no KMS call and runs before the old version is disabled: kek_versions_in_use of the record that Keyring::reload returns must list the new version alone. Under Cloud KMS, a reencrypt_deks that ran before the new primary version had propagated leaves the old version listed. A None there is a version the KMS did not report, so the first check fails on it. Once the old version is disabled, KeyringAdmin::reencrypt_deks runs again: it decrypts every DEK in the record through the provider, and fails on one still under the old version. See Rotating the KEK. An application that stores the kek_version of its own DEKs beside them checks those the same way.

Under the local KMS the check needs no disable. A provider that lists the new version alone, as the sample above builds it, refuses every DEK under the old version, so the check runs before the deploy that drops the old version from the list, and a missed DEK costs no outage and no redeploy.

Three things keep using the old version after a rotation, and each sets when to sweep or to disable:

  • a store-less writer keeps sealing under its current DEK, encrypted under the old version, until its reuse policy renews the DEK or the DEK leaves its cache, at the cache’s TTL of 15 minutes by default. Start the sweep once every writer has renewed its DEK after the rotation took effect, under Cloud KMS once the new primary version had propagated, or the check finds the values written meanwhile;
  • every DEK cache serves the DEKs it holds, without a KMS call, until their entries expire. A value the sweep missed fails to decrypt in the application only once its entry has expired, see DEK caching. The check does not wait for that, since it never reads a cache;
  • a process keeps the encrypted DEKs it read before the sweep. A keyring’s cached record holds the ones it had before reencrypt_deks until it is refreshed, at a change signal of the store or once it is older than record_ttl, 5 minutes by default, and Cloud Storage and S3 send no signal, see Record cache. An encrypted DEK the application read from its settings at startup, as in One fixed key, stays as it was read. The DEK cache keys its entries by those bytes, so once an entry expires, the KMS decrypts the old bytes again and fails under a disabled old version, with no reload. Disable the old version no sooner than one record_ttl after the last reencrypt_deks, and only once every process has read its DEKs stored apart from their values again.

A KMS whose changes take time to propagate, such as Cloud KMS, can keep encrypting under the old version for a while after the rotation and keep decrypting under it for a while after it is disabled. Wait before the sweep and again before trusting the check, see the page of each provider.

Rolling back a rotation

A swept value’s DEK is under the new version only, so a rollback keeps the new version enabled: disabling it makes every swept value and every value written since the rotation unreadable, until it is enabled again. Three providers make the old version encrypt again:

  • Cloud KMS: make the old version the primary version again;
  • Azure Key Vault: pin the old version in AzureKmsKeyRef;
  • the local KMS: point with_encrypting_version at the old version.

Rolling back to the old version needs no new sweep. To retire the new version afterwards, run the procedure above with the old version as the current one.

The other two always encrypt under the latest key. Vault Transit encrypts under the latest version of the key, since the provider names no version in its request, and no older version becomes the latest again: a rotation is undone by rotating once more and sweeping to that third version. AWS KMS keeps every earlier key material decrypting and none can be disabled, so a rotation needs no rollback there.

DEK caching and reuse

Without a cache, every read of a value decrypts its DEK with one KMS call, and every encrypt encrypts a new DEK with another. The library has two ways to make fewer KMS calls:

  • DekCache, a cache of decrypted DEKs, which serves repeated reads of values under the same DEK without the KMS;
  • store-less DEK reuse, with a DekReusePolicy, where one DEK seals many values, so a write calls the KMS only when the DEK is renewed.

DEK cache

kms_aead::cache::DekCache holds plaintext DEKs a provider decrypted, keyed by the provider’s KEK and the encrypted DEK’s bytes. A per-call envelope has no cache unless the options give it one:

use kms_aead::backends::Ring;
use kms_aead::cache::{DekCache, DekCacheOptions};
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{KmsAeadEnvelope, KmsAeadEnvelopeOptions};
use std::num::NonZeroUsize;
use std::time::Duration;

fn main() -> kms_aead::KmsAeadResult<()> {
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
let cache = DekCache::new(
    DekCacheOptions::new()
        .with_ttl(Duration::from_secs(5 * 60))
        .with_max_entries(NonZeroUsize::new(10_000).expect("not zero")),
)?;

let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::with_options(
    provider,
    KmsAeadEnvelopeOptions::new().with_dek_cache(cache.clone()),
)?;
let _ = envelope;
Ok(())
}

decrypt, the *_with_encrypted_dek calls and a store-less encrypt decrypt through the envelope’s cache. Clone shares the same cache, so one cache may serve several envelopes and several KEKs: an entry serves only a lookup that names the same KEK, and a key decrypted under one KEK never reaches a caller with the provider of another.

The cache:

  • serves an entry for its TTL after it was inserted, however often it is used, 15 minutes by default;
  • holds at most max_entries entries, 1024 by default, and evicts the oldest entry past it;
  • makes one provider call for concurrent misses of the same key, and every caller receives its result, the key or the error;
  • keeps no entry for a failed decryption, so during a KMS outage every call fails as fast as the KMS does;
  • zeroises a key when its entry leaves the cache: once it is evicted, invalidated, cleared, or purged after it expired.

DekCache::disabled() holds nothing, and every lookup calls the provider. It is what a per-call envelope has by default.

Sizing

Size max_entries above the number of distinct DEKs read per TTL. With per-call envelopes every value has its own DEK, so a cache helps only values read more than once within the TTL. With store-less writers the number of DEKs is the number of writers times the renewals per TTL, which is small.

A longer TTL saves more KMS calls, and keeps DEKs in memory for longer, see Key lifetime.

Invalidation

A disabled KMS key or a revoked IAM grant reaches the cached keys only when their entries expire. To drop one at once, invalidate it with the envelope’s own KEK:

use kms_aead::backends::Ring;
use kms_aead::cache::{DekCache, DekCacheOptions};
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{KmsAeadEnvelope, KmsAeadEnvelopeOptions};
use kms_aead::KmsAeadEncryptionProvider;

#[tokio::main(flavor = "current_thread")]
async fn main() -> kms_aead::KmsAeadResult<()> {
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::with_options(provider,
    KmsAeadEnvelopeOptions::new().with_dek_cache(DekCache::new(DekCacheOptions::new())?))?;
let (_dek, encrypted_dek) = envelope.generate_encrypted_dek().await?;

// One encrypted DEK
envelope
    .dek_cache()
    .invalidate(envelope.provider().kek(), &encrypted_dek);

// Every DEK
envelope.dek_cache().clear();
Ok(())
}

Pass envelope.provider().kek() to invalidate, with the KmsAeadEncryptionProvider trait in scope: a KekRef built by hand that differs from it matches no entry.

Key lifetime

The cache runs no thread and no task of its own. Expired entries are dropped at the next call on the cache, at purge_expired, or when the last clone of the cache is dropped. With no calls, the bytes of an expired key stay in memory. An application whose process can sit idle while the cache holds keys, and that needs the TTL to bound their lifetime in memory, calls purge_expired on a timer of its own:

use kms_aead::cache::{DekCache, DekCacheOptions};
fn example() -> kms_aead::KmsAeadResult<()> {
let cache = DekCache::new(DekCacheOptions::new())?;

let purged = cache.clone();
tokio::spawn(async move {
    let mut interval = tokio::time::interval(std::time::Duration::from_secs(60));
    loop {
        interval.tick().await;
        purged.purge_expired();
    }
});
Ok(())
}

A key reaches the caller only inside the closure of DekCache::with_dek, and stays intact until the closure returns, whatever leaves the cache meanwhile. The closure must not keep a copy of the key: a copy taken out of it outlives the cache’s control of its lifetime.

Store-less DEK reuse

A KmsAeadEnvelope with a DekReusePolicy encrypts many values under one DEK and renews it at the first encryption past max_age, past max_uses or past max_bytes, whichever comes first. A renewal makes one KMS encrypt call. Each value still carries its encrypted DEK in Tink’s KMS envelope, so nothing is stored apart from the values, and values under earlier DEKs stay readable.

use kms_aead::backends::Ring;
use kms_aead::formats::Envelope;
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{DekReusePolicy, Encrypted, KmsAeadEnvelope, KmsAeadEnvelopeOptions};
use secret_vault_value::SecretValue;
use std::num::NonZeroU64;
use std::time::Duration;

#[tokio::main(flavor = "current_thread")]
async fn main() -> kms_aead::KmsAeadResult<()> {
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::with_options(
    provider,
    KmsAeadEnvelopeOptions::new().with_dek_reuse(
        DekReusePolicy::new()
            .with_max_age(Duration::from_secs(60 * 60))
            .with_max_uses(NonZeroU64::new(1_000_000).expect("not zero")),
    ),
)?;

// One KMS encryption for both values
let first: Encrypted<SecretValue, Envelope> =
    envelope.encrypt(b"events/1", &SecretValue::from("first")).await?;
let second: Encrypted<SecretValue, Envelope> =
    envelope.encrypt(b"events/2", &SecretValue::from("second")).await?;

// Read with any envelope over the same KEK and algorithm
let decrypted_first: SecretValue = envelope.decrypt(b"events/1", &first).await?;
let decrypted_second: SecretValue = envelope.decrypt(b"events/2", &second).await?;
assert_eq!(decrypted_first, SecretValue::from("first"));
assert_eq!(decrypted_second, SecretValue::from("second"));
Ok(())
}

The defaults are a max_age of 24 hours and a max_uses of 2^24. max_age must be longer than zero and max_uses at most 2^32, the bound for random 96-bit nonces under one key, otherwise the envelope fails to build with INVALID_DEK_REUSE_POLICY.

Volume limit

max_bytes counts the plaintext bytes sealed under the DEK. Its default depends on the algorithm:

AlgorithmDefault max_bytesMost allowed
AES-128-GCM, AES-256-GCM2^38 bytes (256 GiB)2^52 bytes
AES-256-GCM-SIVno limit beyond max_usesany
ChaCha20-Poly1305no limit beyond max_usesany

The default stays below the 2^38.5 bytes RFC 8446 allows under one AES-GCM key, and the most allowed is the 2^48 blocks of RFC 8452. AES-GCM-SIV and ChaCha20-Poly1305 have no volume bound beyond max_uses. The citations are in Data volume.

A max_bytes set in the policy replaces the default, under any algorithm. Above the most allowed, the envelope fails to build with INVALID_DEK_REUSE_POLICY.

A value that would take the count past max_bytes renews the DEK before it is sealed. A value longer than max_bytes alone is sealed under a new DEK of its own, as the per-call envelope does, and the current DEK stays in use for the next values.

The bounds count blocks of plaintext and AAD, and one more block per value, and max_bytes counts plaintext bytes only. At the default max_uses and an AAD of 16 bytes or less, the difference is at most 3 × 2^24 blocks beside the 2^34 blocks of the default.

The DEK lives in the cache

The envelope keeps only the encrypted DEK. Its plaintext lives in the envelope’s DekCache, which a store-less envelope always has: DekCache::new(DekCacheOptions::new()) unless the options give it another, and INVALID_DEK_REUSE_POLICY beside DekCache::disabled().

The first encryption after the DEK has left the cache renews it. So the DEK is renewed:

  • at the cache’s TTL, whatever max_age;
  • when the cache evicts it for capacity;
  • after invalidate with envelope.provider().kek(), or after clear.

In a cache shared with readers, size max_entries above the number of distinct DEKs read per TTL, or give the writer a cache of its own, otherwise reads evict the writer’s DEK and it renews more often than the policy says.

A writer that falls quiet leaves its DEK in memory until the cache’s next call or purge_expired, see Key lifetime. The values sealed while the cache holds the DEK are readable by whoever reads the process’s memory in that window.

Deterministic encryption

Feature deterministic.

Randomised encryption gives a different cipher text every time, even for the same value. A deterministic algorithm gives equal cipher texts for equal values under one key and one AAD, so a sealed column can be compared, joined or looked up by equality without opening it.

The library provides AES-SIV (RFC 5297) with a 64-byte key, DeterministicAlgorithm::Aes256Siv. Its name for FromStr and Display is aes-256-siv. DeterministicCipher takes a backend, as AeadCipher does, and draws its keys from the backend’s CSPRNG. Every backend seals and opens with the RustCrypto aes-siv crate, so a value sealed under one backend opens under any other.

AES-SIV is not a FIPS-approved mode. A FIPS deployment keeps deterministic fields outside its validated boundary, also on aws-lc-fips, where the keys come from the FIPS module’s DRBG.

Deterministic encryption fits exact-match lookups where the leak of equality is acceptable. When a field only needs lookups and its stored value should stay randomised, a beacon fits instead, see Beacon or deterministic field.

What it leaks

Be aware what equal cipher texts tell a reader of the stored data, without any key:

  • Equality: which rows hold the same value;
  • Frequency: how often each value occurs. On a column with few distinct values, such as a country, a status or a yes/no answer, the most frequent cipher text is the most frequent value, and the values can be read back from public statistics.

And since there is no nonce, a leaked deterministic key lets its holder test candidate values against the whole column offline.

So deterministic encryption fits fields that are looked up by equality and have high entropy, such as emails and external ids. Do not use it:

  • for a column with few distinct values or a skewed distribution;
  • when equality itself is sensitive;
  • when the value is never looked up by equality: randomised encryption leaks nothing of the kind.

The AAD narrows what leaks: values are equal only under the same AAD, so a per-tenant AAD keeps equal values of two tenants apart.

An AAD that a lookup can rebuild names the field and never the row, so a deterministic value also opens in any other row of the same field. A deterministic field never decides identity or authorisation on its own; where identity matters, the check reads a randomised copy of the field, bound to the row by its AAD.

Usage

DeterministicCipher seals and opens with a DataEncryptionKey of DeterministicAlgorithm::key_len() bytes, 64 for AES-SIV, and refuses a key of another length with INVALID_KEY_LENGTH, such as the 16 or 32 bytes of a randomised algorithm’s key. The application keeps track of which key serves which algorithm, as kms-aead-keyring does with its key ids.

use kms_aead::backends::Ring;
use kms_aead::formats::Deterministic;
use kms_aead::{DeterministicAlgorithm, DeterministicCipher, Encrypted, KeyId};
use secret_vault_value::SecretValue;

fn main() -> kms_aead::KmsAeadResult<()> {
let cipher = DeterministicCipher::<Ring>::new(DeterministicAlgorithm::Aes256Siv)?;
let dek = cipher.generate_dek()?;

let aad = b"customers/email";
let first: Encrypted<SecretValue, Deterministic> =
    cipher.encrypt(KeyId::new(1), aad, &SecretValue::from("user@example.com"), &dek)?;
let second: Encrypted<SecretValue, Deterministic> =
    cipher.encrypt(KeyId::new(1), aad, &SecretValue::from("user@example.com"), &dek)?;

// Equal values give equal cipher texts, to look up by
assert_eq!(first, second);
let decrypted: SecretValue = cipher.decrypt(aad, &first, &dek)?;
assert_eq!(decrypted, SecretValue::from("user@example.com"));
Ok(())
}

An Encrypted<T, Deterministic> is [0x01][key id: u32 BE][synthetic IV: 16][ciphertext]: Tink’s 5-byte TINK prefix that names the key by its KeyId, then the output of RFC 5297, so Tink and BigQuery read it with a keyset of that key, see One fixed key. Its equality compares in constant time, and its Debug prints only the length, since the bytes tell which values are equal.

Keys encrypted by a KMS

The envelope generates and decrypts deterministic keys with its provider:

use kms_aead::backends::Ring;
use kms_aead::formats::Deterministic;
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{DeterministicAlgorithm, DeterministicCipher, Encrypted, KeyId, KmsAeadEnvelope};
use secret_vault_value::SecretValue;

#[tokio::main(flavor = "current_thread")]
async fn main() -> kms_aead::KmsAeadResult<()> {
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::new(provider)?;
let algorithm = DeterministicAlgorithm::Aes256Siv;

// A new key, and the same key encrypted, to store
let (dek, encrypted_dek) = envelope.generate_encrypted_deterministic_dek(algorithm).await?;

// Later: decrypt the stored key
let decrypted_dek = envelope.decrypt_deterministic_dek(algorithm, &encrypted_dek).await?;

let cipher = DeterministicCipher::<Ring>::new(algorithm)?;
let sealed: Encrypted<SecretValue, Deterministic> =
    cipher.encrypt(KeyId::new(1), b"aad", &SecretValue::from("value"), &dek)?;
let decrypted: SecretValue = cipher.decrypt(b"aad", &sealed, &decrypted_dek)?;
assert_eq!(decrypted, SecretValue::from("value"));
Ok(())
}

decrypt_deterministic_dek calls the provider every time and does not go through the envelope’s DEK cache. To cache deterministic keys, use DekCache::with_dek, which holds the keys of both kinds of algorithm.

DeterministicCipher::generate_encrypted_dek does the same with any provider.

Beacons

A beacon, or blind index, finds rows by a field’s value without decrypting the column: an HMAC-SHA256 of the value under a beacon key, truncated, stored beside the encrypted field. A query calculates the beacon of the value it looks for and matches it by equality. Beacon<T> holds the bytes to store, and the beacon key is a 32-byte key encrypted by the KMS, as a DEK is:

use kms_aead::backends::Ring;
use kms_aead::formats::Envelope;
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{
    Beacon, BeaconAlgorithm, BeaconBits, BeaconMac, Encrypted, KeyId, KmsAeadEnvelope,
    KmsAeadResult, Plaintext,
};
use secret_vault_value::SecretValue;

#[derive(Debug, Clone, PartialEq)]
struct Email(String);

// The application's id of its beacon key, which every beacon names
const EMAIL_BEACON_KEY: KeyId = KeyId::new(1);

impl Email {
    // The beacon of an email matches regardless of case
    fn new(email: &str) -> Self {
        Email(email.to_lowercase())
    }
}

impl Plaintext for Email {
    fn to_plaintext(&self) -> KmsAeadResult<SecretValue> {
        self.0.to_plaintext()
    }

    fn from_plaintext(plaintext: SecretValue) -> KmsAeadResult<Self> {
        String::from_plaintext(plaintext).map(Email)
    }
}

#[tokio::main(flavor = "current_thread")]
async fn main() -> KmsAeadResult<()> {
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::new(provider)?;

// Once, by an administrative job: the beacon key, stored beside the application's settings
let (_, encrypted_dek) = BeaconMac::<Ring>::new(BeaconAlgorithm::HmacSha256)
    .generate_encrypted_dek(envelope.provider())
    .await?;

// On every write: the field and its beacon
let email = Email::new("Alice@Example.com");
let encrypted: Encrypted<Email, Envelope> =
    envelope.encrypt(b"users/1042/email", &email).await?;
let beacon: Beacon<Email> = envelope
    .beacon(EMAIL_BEACON_KEY, b"users/email", BeaconBits::DEFAULT, &email, &encrypted_dek)
    .await?;

// A lookup: the beacon of the value looked for, then a decryption of each matching row
let probe: Beacon<Email> = envelope
    .beacon(
        EMAIL_BEACON_KEY,
        b"users/email",
        BeaconBits::DEFAULT,
        &Email::new("alice@example.com"),
        &encrypted_dek,
    )
    .await?;
assert_eq!(probe, beacon);
let decrypted: Email = envelope.decrypt(b"users/1042/email", &encrypted).await?;
assert_eq!(decrypted, email);
Ok(())
}
  • the context, users/email here, names the field and never a row, so that equal values in one field give equal beacons. A beacon of one field never matches a beacon of another;
  • the key id, a KeyId, is the application’s number for the beacon key, written into every beacon so that a column can hold beacons of two keys at once;
  • the beacon key is decrypted through the envelope’s DEK cache, as a DEK is.

Beacon<T> is stored as Encrypted is, with the serde, postgres and sqlx features, and read back through TryFrom, which checks its layout, see Stored values. See Formats for its bytes.

What a beacon leaks

A beacon column leaks to anyone who reads it, without any key:

  • Equality: which rows are likely to hold the same value;
  • Frequency: how often each value occurs, as far as the bits tell values apart.

And a leaked beacon key lets its holder test candidate values against the whole column offline.

So beacons fit fields that are looked up and have many distinct values, such as emails and external ids. Do not use them for low-cardinality fields, such as a status, a country or a yes/no answer, whose values the frequencies give away.

Bits

BeaconBits sets how many bits of the HMAC a beacon keeps, 1 to 256, BeaconBits::DEFAULT, 16, unless set. With n distinct values in a column and b bits, about n / 2^b values share each beacon:

  • fewer bits: more values share a beacon, so a lookup returns more rows, which the application decrypts and filters by the plaintext. A column of short beacons leaks less;
  • more bits: fewer rows to filter, down to one per value once 2^b is far above n, and the column then leaks which rows hold equal values as a deterministic column does.

An equal beacon never proves an equal value: a lookup always decrypts the rows it found and compares the plaintexts. The bits enter the HMAC, so beacons of one value under different bits never match: after a change of a column’s bits, its stored beacons match no lookup until a re-index computes them again. The numbers of the default for a column of 1,000,000 emails are in Beacon or deterministic field.

Normalisation

A beacon is the HMAC of the bytes the Plaintext type encodes, so Alice@Example.com and alice@example.com give different beacons unless the type normalises the value. Normalising is the application’s job: the newtype normalises when it is made, as Email::new lowercases above, and every write and every lookup goes through it.

BigQuery

BigQuery’s SQL has no HMAC-SHA256 with a KMS-encrypted DEK, so a query in BigQuery cannot calculate a beacon. It matches beacons the application calculated and passed in as query parameters.

Rotating a beacon key

Rotating a beacon key in store-less mode is manual. Generate the new key and keep both, write beacons under the new one, query with a beacon under each key until a re-index has rewritten every stored beacon, then drop the old key. Beacon::key_id tells which key wrote a stored beacon. kms-aead-keyring does this with key versions, see Beacons.

Beacon or deterministic field

A deterministic field also finds rows by equality, by its cipher text:

BeaconDeterministic field
Stored valueRandomised, so its AAD can name the row, and a value copied into another row fails to openEqual for equal values, so its AAD names the field and never the row, and a value copied into another row opens there
MatchThe truncated HMAC, with deliberate collisionsAlways the exact value

With the default 16 bits, there are 65,536 possible beacons. A column of 1,000,000 distinct emails gives about 1,000,000 / 65,536, or 15, emails per beacon, so a lookup of one email returns about 15 rows. The application decrypts them and keeps the one equal to the email it looks for.

Code generic over the backend

The backend types implement AeadBackend, a sealed trait in kms_aead::backends. Its items are the constant NAME, the backend’s name in spans and logs: ring, aws-lc or rustcrypto, and generate_random_bytes. Code that works with any backend bounds its type parameter with AeadBackend and nothing else:

use kms_aead::backends::{AeadBackend, Ring};
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{KmsAeadEnvelope, KmsAeadResult};
use secret_vault_value::SecretValue;

struct Orders<B> {
    envelope: KmsAeadEnvelope<LocalKmsProvider<B>, B>,
}

impl<B: AeadBackend> Orders<B> {
    fn new() -> KmsAeadResult<Self> {
        let provider = LocalKmsProvider::ephemeral(LocalKekId::try_from("orders".to_string())?)?;
        Ok(Self {
            envelope: KmsAeadEnvelope::new(provider)?,
        })
    }

    async fn round_trip(&self, card: &SecretValue) -> KmsAeadResult<SecretValue> {
        let sealed = self.envelope.encrypt(b"orders/1042", card).await?;
        self.envelope.decrypt(b"orders/1042", &sealed).await
    }
}

#[tokio::main(flavor = "current_thread")]
async fn main() -> KmsAeadResult<()> {
let orders = Orders::<Ring>::new()?;
let card = SecretValue::from("4111 1111 1111 1111");
assert_eq!(orders.round_trip(&card).await?, card);
Ok(())
}

Cross-backend compatibility

Every backend writes the same bytes for the same algorithm, so a value sealed by one backend opens with any other that implements its algorithm. A writer on Ring and a reader on AwsLc work together, and moving an application from one backend to another needs no migration of its data:

use kms_aead::backends::{Ring, RustCrypto};
use kms_aead::formats::Bare;
use kms_aead::{AeadAlgorithm, AeadCipher, Encrypted};
use secret_vault_value::SecretValue;

fn main() -> kms_aead::KmsAeadResult<()> {
let writer = AeadCipher::<Ring>::new(AeadAlgorithm::Aes256Gcm)?;
let reader = AeadCipher::<RustCrypto>::new(AeadAlgorithm::Aes256Gcm)?;

let dek = writer.generate_dek()?;
let cipher_text: Encrypted<SecretValue, Bare> =
    writer.encrypt_bare(b"aad", &SecretValue::from("secret"), &dek)?;

let decrypted: SecretValue = reader.decrypt_bare(b"aad", &cipher_text, &dek)?;
assert_eq!(decrypted, SecretValue::from("secret"));
Ok(())
}

ring

ChaCha20-Poly1305, AES-128-GCM and AES-256-GCM. It has no AES-256-GCM-SIV. ring does not zeroise its expanded key schedules, so they stay in freed memory after each call.

aws-lc-rs and FIPS

aws-lc builds aws-lc-rs with every algorithm. It is the backend that adds no second crypto library to a build with a cloud provider, since the providers already build aws-lc-rs for TLS.

aws-lc-fips runs the same backend on the AWS-LC FIPS module, and builds only the FIPS module, so it does not need aws-lc. It needs CMake and Go to build. Be aware it moves every user of aws-lc-rs in the build to the FIPS module, the rustls aws-lc-rs provider included. A build with both features compiles both C libraries, and aws-lc-rs runs on the FIPS one. AES-256-GCM is the algorithm for FIPS deployments. AES-SIV, the deterministic algorithm, is not FIPS-approved, see Deterministic encryption.

aws-lc-rs copies the key into an AEAD context that AWS-LC allocates with its own allocator, which overwrites every allocation with zeros before freeing it. The expanded key schedule does not stay in freed memory after a call, as long as the application leaves AWS-LC’s allocator in place. The record keys AES-256-GCM-SIV derives for each call live on the stack, and AWS-LC does not clear them.

RustCrypto

Every algorithm, in pure Rust, with getrandom as the CSPRNG. It needs no C compiler. The feature turns on the crates’ zeroize features, so their key objects, and the Poly1305 and POLYVAL keys each call derives, are zeroised when dropped.

Each provider names its configured KEK on every decryption, so a DEK encrypted under another KEK fails at the KMS and never opens a value. provider.kek() returns that KEK as a KekRef: the KMS and the key name. It is also the provider and key field of the KMS spans and the key of the DEK cache. Nothing else is checked: an encrypted DEK carries no context that the KMS authenticates, see Security considerations.

KMS random generators

By default a DEK comes from the CSPRNG of the crypto backend. The GCP and AWS providers can take it from the KMS instead, at the cost of one more KMS request per new DEK:

  • GCP: GcpKmsProviderOptions::new().with_use_kms_random_gen(true), Cloud KMS GenerateRandomBytes at the HSM protection level;
  • AWS: AwsKmsProviderOptions::new().with_use_kms_random_gen(true), AWS KMS GenerateRandom.

Azure, Vault Transit and the local KMS always use the backend’s CSPRNG. Nonces always come from the backend’s CSPRNG.

Your own provider

An application can implement KmsAeadEncryptionProvider for a KMS of its own, or as a wrapper around another provider. The implementation:

  • returns from kek() a KekRef with KekProvider::Other and a key name that identifies the key across every KMS instance it may address. A wrapper returns the inner provider’s kek();
  • names that KEK to the KMS on every decryption;
  • adds to the encrypted DEK that encrypt_data_encryption_key returns, with with_kek_version, the KEK version the KMS’s response names, never the one it expects, and none when the response names none;
  • keeps key material, plaintext or encrypted, out of its errors’ Display and Debug.

generate_key_material has a default implementation that returns Ok(None), so the backend generates the key.

Authentication

GcpKmsProvider::new and with_options build a Cloud KMS client with the application default credentials. They look for credentials in the following places, preferring the first location found:

  • A JSON file whose path is specified by the GOOGLE_APPLICATION_CREDENTIALS environment variable;
  • A JSON file in a location known to the gcloud command-line tool using gcloud auth application-default login;
  • On Google Compute Engine, Cloud Run, GKE, etc., the metadata server.

For local development don’t confuse gcloud auth login with gcloud auth application-default login, since the first one authorises only the gcloud tool to access the Cloud Platform.

GcpKmsProvider::with_client takes a client the application built itself, for other credentials.

The principal needs cloudkms.cryptoKeyVersions.useToEncrypt and useToDecrypt on the key, as in the roles/cloudkms.cryptoKeyEncrypterDecrypter role, and cloudkms.locations.generateRandomBytes on the location when the KMS generator is on.

Key versions and rotation

A rotation adds a version to the CryptoKey and makes it the primary version, by hand or on the key’s rotation schedule. New DEKs are encrypted under the primary version from then on, and Cloud KMS decrypts every DEK with the version that encrypted it, for as long as that version is enabled.

To retire the old version, disable it once the sweep has reached every value, see Re-encrypting DEKs after a KEK rotation: decryptions under it fail, and enabling it again restores them. Destroying it schedules its destruction, 30 days later by default, and until then the version can be restored.

Changing the primary version and disabling a version are eventually consistent in Cloud KMS, see Cloud KMS resource consistency. Until a new primary version has propagated, Encrypt may still use the previous one, and a disabled version “typically remains usable for encrypting and decrypting data for up to 1 minute after it is disabled”, for several hours in exceptional cases. So:

  • start the sweep only once the new primary version has propagated. The kek_version() of the encrypted DEK an encryption returns, and the kek_version field of the KMS encrypt DEK span, name the version Cloud KMS encrypted with, the N of cryptoKeyVersions/N, see Observability. A keyring whose reencrypt_deks ran before the new primary version had propagated still lists the old version among its kek_versions_in_use: run reencrypt_deks again, see Rotating the KEK;
  • run the check only once the disable has propagated, and run it again before destroying the version. A check inside that window passes on DEKs that are still under the old version.

Enabling a version is strongly consistent: an enabled version is available at once, so enabling the old version again after a failed check takes effect immediately.

Errors

The code of a failed KMS call is the gRPC status code, such as PermissionDenied or NotFound. Which codes are a NetworkError and which an EncryptionError is in Retries.

Authentication and region

AwsKmsProvider::new loads the AWS configuration from the environment, as the AWS SDK does: environment variables, the shared config and credentials files, the instance or container role, etc. It sends no request, so missing credentials or an unreachable endpoint fail the first encryption or decryption.

Without aws_region in the key reference, the provider takes the region of the AWS configuration it loads. Set one with AwsKmsKeyRef::new(..).with_aws_region(region).

The principal needs kms:Encrypt and kms:Decrypt on the key, and kms:GenerateRandom when the KMS generator is on.

Key ARN and aliases

A decryption names the configured key to AWS KMS, so a DEK encrypted under another key fails with IncorrectKeyException, even when the principal may decrypt with that key.

Configure the key ARN rather than an alias: a DEK encrypted under an alias that later moves to another key fails to decrypt with IncorrectKeyException.

The provider turns the key id into an ARN with the region and the account: an alias name into an alias ARN, a key id into a key ARN, and an ARN stays as it is. That ARN always starts with arn:aws:, so outside the aws partition, such as in GovCloud or China, give the full ARN.

Key versions and rotation

AWS KMS rotates the key material of a key, on its rotation schedule or on demand, and keeps every earlier key material for as long as the key exists. A DEK encrypted before a rotation decrypts afterwards. An encryption’s response names no key material, so the kek_version() of the encrypted DEK it returns is None.

Key material that AWS KMS generated cannot be disabled or deleted on its own. The sweep of Re-encrypting DEKs after a KEK rotation is optional for it: it moves each DEK to the current key material, and with nothing to disable, the check and the destruction do not apply.

Imported key material is deleted in two ways: by DeleteImportedKeyMaterial, for the material a KeyMaterialId names or the current one without it, and at its expiry. ExpirationModel defaults to KEY_MATERIAL_EXPIRES, and at its ValidTo, at most 365 days after the import, AWS KMS deletes the material without any call. Either way the key moves to PendingImport, and AWS KMS refuses every operation with it, whichever material a DEK is under, until the same material is imported again. Import with KEY_MATERIAL_DOES_NOT_EXPIRE, or import again before ValidTo, and keep a copy of every material to import again.

A sweep therefore retires no imported key material from a key in use, and with every kek_version None, neither a keyring record nor a stored kek_version shows which DEKs are under which material. After a deletion or an expiry, import the material again and decrypt every stored DEK: each keyring’s with reencrypt_deks, the application’s own as in The check. An error means the key is still in PendingImport: ListKeyRotations lists each material with its import state, and the one still missing is imported again.

Errors

An error AWS KMS returned keeps its AWS error code, such as IncorrectKeyException or NotFoundException, and the message AWS KMS returned, and its root cause is the SDK error. Which errors are a NetworkError and which an EncryptionError is in Retries.

Options

Encrypted DEKs

Key Vault decrypts only with the key version that encrypted, so the provider’s encrypted DEK carries it before Key Vault’s encrypted DEK, in the library’s own layout, see Formats. No Tink client exists for Azure, so Tink does not read the values of this provider, and the plaintext Key Vault encrypts is the raw DEK of 16, 32 or 64 bytes, as in 0.29, rather than the DEK as Tink serialises it. Every wrap algorithm takes it, A256Kw too, which takes only multiples of 8 bytes. Store the encrypted DEK as it is, see Envelope encryption.

Key versions and rotation

A rotation adds a version to the key, by hand or by the key’s rotation policy. Without a key version in AzureKmsKeyRef, the latest version encrypts new DEKs; with one, that version does, so move it to the new version before a sweep. A sweep with a provider pinned to the old version re-encrypts under the old version. The kek_version() of the encrypted DEK an encryption returns is the version Key Vault encrypted with, read from the kid of its response.

Once the sweep has reached every value, see Re-encrypting DEKs after a KEK rotation, disable the old version: Key Vault refuses to decrypt under it, and enabling it again restores it. Key Vault deletes a key with all its versions and never one version alone, so the old version stays disabled rather than destroyed.

Errors

A failed request carries Key Vault’s error code, such as Forbidden or KeyNotFound, or AZURE_STATUS_<status> when the response has none. Which statuses are a NetworkError and which an EncryptionError is in Retries. A decryption of an encrypted DEK in another layout fails with AZURE_ENCRYPTED_DEK_FORMAT, before any request.

HcVaultTransitProvider::new reads its options from the variables the Vault CLI reads, with HcVaultTransitProviderOptions::from_env: VAULT_ADDR (required), VAULT_TOKEN, VAULT_NAMESPACE, VAULT_CACERT and VAULT_CLIENT_TIMEOUT. The options are:

  • address: the Vault server, such as https://vault.example.com:8200;
  • token: sent with every request. Without one the requests carry no token, which is what a Vault Agent or Vault Proxy with use_auto_auth_token expects;
  • namespace: the Vault Enterprise namespace of the mount;
  • ca_certificate: a PEM file with CA certificates for a server whose certificate comes from a private CA. The file adds to the root store and does not replace it, unlike VAULT_CACERT in the Vault CLI, so a server with a certificate from any public CA in the root store is trusted as well;
  • timeout: the time limit for one request, from opening the connection to the last byte of the response, 60 seconds by default.

The provider sends no request when it is created, so a wrong token or an unreachable server fail the first encryption or decryption. An http address to a host other than localhost or a loopback address logs a WARN event at creation, since the token and the DEKs then cross the network unencrypted.

The token needs update on <mount>/encrypt/<key> and <mount>/decrypt/<key>.

Key versions and rotation

The encrypted DEK is the Transit ciphertext, such as vault:v1:.... It names the key version, so it still decrypts after the key is rotated. The KMS spans record that version as kek_version, and so does the kek_version() of the encrypted DEK an encryption returns: the N of vault:vN:, as min_decryption_version counts it.

The decrypt names the configured key in its URL, so Vault refuses a ciphertext of another key.

A rotation is <mount>/keys/<key>/rotate, and the new version encrypts every DEK after it. Once the sweep has reached every value, see Re-encrypting DEKs after a KEK rotation, disable the old versions by setting min_decryption_version in the key’s configuration to the new version: Vault then refuses to decrypt under older versions, with VAULT_STATUS_400, and lowering it again restores them. Once nothing needs them, the backups included, min_available_version and a trim of the key delete the older versions for good.

Errors

A response with an error status is VAULT_STATUS_<status>. VAULT_HTTP and VAULT_TIMEOUT are for a request that got no complete response, and VAULT_RESPONSE, VAULT_RESPONSE_TOO_LARGE and VAULT_CIPHERTEXT for a response or an encrypted DEK that cannot be read. Which codes are a NetworkError and which an EncryptionError is in Retries. Invalid options fail at creation with VAULT_INVALID_OPTIONS, or VAULT_TLS when the TLS configuration cannot be built.

Local KMS

LocalKmsProvider encrypts DEKs with a key encryption key the process holds, with AES-256-GCM on the backend it is built with. It is in every build, with no feature, for:

  • development and tests without a cloud KMS;
  • single-host installs where the operator protects the KEK.

kms-aead builds one only when the application calls one of its constructors; no provider falls back to it. Each constructor logs one INFO event naming the KEK id, its versions and where each version came from (ephemeral, file, env or secret), never the key.

KEK ids and versions

A LocalKekId names the KEK: 1 to 255 bytes of ASCII alphanumerics, -, _ and .. Every encrypted DEK records it, and a decryption refuses a DEK encrypted under another id. The id is also the key of the DEK cache, so one id must name one set of KEK material: two providers with the same id and different keys share cache entries.

A provider holds one or more LocalKek versions of 32 bytes each. The highest version encrypts new DEKs unless with_encrypting_version names another, and every version it holds decrypts. Each encrypted DEK records its version, so adding a new version keeps the DEKs encrypted under older ones readable.

A KEK comes from one of:

  • LocalKek::from_secret: bytes the application already holds, such as a key an operator unseals with their own tool (systemd-creds, a TPM, sops, age);
  • LocalKek::from_file: the standard base64 of the 32 bytes in a file, trailing whitespace allowed. The file must be a regular file of at most 256 bytes. No permission or ownership check runs: restricting who can read or replace the file is the operator’s job;
  • LocalKek::from_env: the standard base64 of the 32 bytes in an environment variable. Be aware the variable stays in the process environment for the life of the process: the same user can read it through /proc/<pid>/environ, and every child process inherits it.

Errors name the file or the variable, never its content.

Tests and development

An ephemeral provider has one random version-1 KEK that lives as long as the provider, so the DEKs it encrypts cannot be decrypted once the process exits. It suits tests:

use kms_aead::backends::Ring;
use kms_aead::providers::{LocalKekId, LocalKmsProvider};

    .encrypt(b"orders/1042", &SecretValue::from("secret"))
    .await?;

}

To rotate, add kek-v2 the same way and list both versions, as the next section describes.

Key versions and rotation

Every version in the provider’s list decrypts, and the highest one encrypts unless with_encrypting_version names another. The kek_version() of the encrypted DEK an encryption returns is the version that encrypted, in decimal. A process that does not list a version fails on a DEK under it with LOCAL_KEK_UNKNOWN_VERSION, so a rotation without downtime takes two deploys:

  1. list the new version in every process, with with_encrypting_version keeping the current one encrypting;
  2. once every process lists the new version, drop with_encrypting_version, or point it at the new version, so the new version encrypts.
use std::num::NonZeroU32;

use kms_aead::backends::Ring;
use kms_aead::providers::{LocalKek, LocalKekId, LocalKekVersion, LocalKmsProvider};
use secret_vault_value::SecretValue;

fn example(
    kek_v1: SecretValue,
    kek_v2: SecretValue,
) -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
let v1 = LocalKekVersion::from(NonZeroU32::try_from(1)?);
let v2 = LocalKekVersion::from(NonZeroU32::try_from(2)?);

// The first deploy: version 2 decrypts, version 1 still encrypts
let provider = LocalKmsProvider::<Ring>::new(
    LocalKekId::try_from("orders".to_string())?,
    vec![
        LocalKek::from_secret(v1, kek_v1)?,
        LocalKek::from_secret(v2, kek_v2)?,
    ],
)?
.with_encrypting_version(v1)?;
let _ = provider;
Ok(())
}

A version that is not in the list fails with_encrypting_version with LOCAL_KEK_VERSIONS.

Then sweep, see Re-encrypting DEKs after a KEK rotation, and check with a provider that lists the new version alone, before the deploy that drops the old version, so that a DEK the sweep missed fails the check and no read in the application. Dropping the old version from the list disables it, and listing it again restores it. Destroying it means destroying every copy of its material, backups included.

Limits

  • No IAM, no audit log and no HSM. Protecting the KEK, at rest and in backups, is the operator’s job;
  • Every DEK encryption is one AES-256-GCM encryption with a random 96-bit nonce, so a KEK version is safe for about 2^32 encryptions. With the per-call envelope every value costs one encryption: a host sealing 1,000 values per second spends 2^32 encryptions in 50 days. Use DEK reuse so that one encryption serves many values, and add a new KEK version before the budget is spent;
  • Crypto-shredding means destroying every copy of the KEK, backups included;
  • DEKs encrypted by a local KEK cannot be exported to BigQuery, which decrypts with Cloud KMS.

Errors

An encryption fails with RANDOM_GENERATOR when the backend’s CSPRNG fails. A decryption fails with LOCAL_ENCRYPTED_DEK_FORMAT when the encrypted DEK is not in the local layout, LOCAL_KEK_ID_MISMATCH when it was encrypted under another KEK id, LOCAL_KEK_UNKNOWN_VERSION when the provider does not hold its version, and DECRYPT when it is not authentic under that version.

Creating a provider fails with INVALID_LOCAL_KEK_ID for an invalid id, LOCAL_KEK_VERSIONS when the versions are empty or list one version twice, and LOCAL_KEK_SOURCE or LOCAL_KEK_LENGTH when a KEK cannot be read or is not 32 bytes.

Keyring and field encryption

The kms-aead-keyring crate encrypts fields of application records under a keyring: the record of one scope’s key versions, such as a tenant’s, kept in a keyring store. Each key version is a data encryption key (DEK) encrypted by a KEK in the KMS, with a lifecycle state.

Compared to an envelope, a keyring value carries a 4-byte key id instead of its encrypted DEK:

  • no KMS encryption on write, and one KMS decryption per key version per DEK cache TTL, on write and read;
  • 33 bytes of overhead per value, 21 for deterministic values, see Formats of Encrypted;
  • central staged rotation, retirement, destruction and a compromised flag, for every process that uses the keyring;
  • deterministic fields that a data store finds by equality, across rotations;
  • beacons, blind indexes that a data store matches by equality beside randomised fields;
  • values in Tink’s wire format, which Tink and BigQuery read too.

The price is one more piece of infrastructure, the keyring store, which holds one small JSON document per keyring. See Choosing a mode for the comparison with the envelope modes of kms-aead.

The registry and its handles

A first keyring, on the memory store with a local KEK, is in With a keyring.

KeyringRegistry::create creates the record, with one active version of each purpose its KeyringAlgorithms name, and fails with RecordExists when there is one already. open_or_create creates it on the first start and opens it on every later one, and admin only opens it. The three return a KeyringAdmin. KeyringRegistry::open returns a Keyring, and fails with RecordMissing when there is no record; it is the application’s call:

use firestore::FirestoreDb;
use kms_aead::backends::Ring;
use kms_aead::providers::{GcpKmsKeyRef, GcpKmsProvider};
use kms_aead_keyring::store::FirestoreKeyringStore;
use kms_aead_keyring::{Keyring, KeyringId, KeyringRegistry, KeyringRegistryOptions};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
let key_ref = GcpKmsKeyRef::new(
    "my-project".to_string(),
    "europe-north1".to_string(),
    "my-key-ring".to_string(),
    "my-key".to_string(),
);
let registry = KeyringRegistry::<FirestoreKeyringStore, Ring>::new(
    FirestoreKeyringStore::new(FirestoreDb::new("my-project").await?),
    KeyringRegistryOptions::new(),
)?;
let keyring: Keyring<FirestoreKeyringStore, GcpKmsProvider, Ring> = registry
    .open(GcpKmsProvider::new(&key_ref).await?, KeyringId::from_static("tenant-42"))
    .await?;
registry.shutdown().await?;
Ok(())
}

The registry takes the store and the backend as the type parameters of KeyringRegistry<S, B>, and each call takes the provider, so that the handles are Keyring<S, P, B> and KeyringAdmin<S, P, B>.

A Keyring and a KeyringAdmin of one keyring in one registry share its cached record and its watch, so a write through the KeyringAdmin is seen by every Keyring at once. KeyringAdmin::keyring() returns the Keyring it holds, for id, record, reload, encryption and sweeps inside an administrative job. The example in With a keyring takes its Keyring there too, since the ephemeral local KEK has no second copy to open the keyring with: LocalKmsProvider is not Clone.

Keyring::sealer takes the cached record, and the Sealer seals under that record’s active versions; decrypt opens under the version the value names. A write takes one sealer and seals every encrypted field of the record through it, so that the seal marker it stores beside them names the versions they are under, see The seal marker. Neither calls the store while the cached record is fresh, nor the KMS while the version’s DEK is in the DEK cache, see Record cache.

The bytes of values, key ids and records are in Formats.

Applications and administration

A keyring has two sides, each with its own handle and its own rights:

  • the application decrypts and runs sweeps on a Keyring, which KeyringRegistry::open returns in every build, and encrypts, computes beacons and re-seals on the Sealer the Keyring hands out for each write;
  • the administration creates keyrings, rotates, promotes, retires and destroys versions, flags compromised ones, re-encrypts DEKs and exports keysets, on a KeyringAdmin, which KeyringRegistry::create, open_or_create and admin return with the admin feature.

The application builds without the admin feature and runs under a principal with the rights of its row only:

An application opens only keyrings that exist: open on a keyring the store holds no record of fails with KeyringError::RecordMissing. So the administration creates each keyring before an application opens it:

  • from infrastructure: a job, a CLI or a deployment step, built with the admin feature and run with the administrative rights, calls create or open_or_create;
  • or from an application that provisions lazily, such as one keyring per tenant on the tenant’s first request. Such an application enables admin and is given the administrative rights deliberately, and is then trusted as the administration is, see Keyring limits.

Key versions and lifecycle

The record

A keyring record holds:

  • the keyring id, the scope it encrypts for: 1 to 128 ASCII alphanumerics, -, _ and ., except . and .. and ids that start and end with __. Such an id is a Firestore document id, a PostgreSQL key, a part of a GCS object name or an S3 object key, and a BigQuery string without escaping. It is an identifier, not a secret, and appears in spans and errors;
  • the KEK of the provider the keyring was created with;
  • the algorithms new versions use, one per purpose;
  • the seal epoch, which every write that makes a version active moves on by one, and which the application stores beside its records as a SealMarker, see Sweeps;
  • every key version ever created, in creation order, each with its encrypted DEK, its state and, once it was active, its seal range: the markers of the records sealed under it, see Records under a version.

Every store keeps it as the same JSON document, see Keyring records for the document and the rules every read checks. A record that breaks one fails with RecordInvalid, naming the rule and never the bytes.

The kek field is informational: it catches a keyring opened with the wrong provider, with KekMismatch, and is no security control, since a writer of the record sets it as freely as any other field. What refuses a DEK encrypted under another KEK is the KMS, since every decryption names the configured KEK.

Keyring::record() returns the cached record, to inspect versions and states, such as record.pending(Purpose::Randomized) for the version a rotation staged. An administrative job reads it as admin.keyring().record().

Key ids

Every value carries the key id of the version that sealed it, and the id names the version’s purpose: randomised, deterministic or beacon. So a value of one purpose never opens under a version of another, and the purpose of a value is known from its bytes, see Keyring key ids. The keyring numbers the versions of each purpose from its first id: randomised versions are 1, 2, 3, …, deterministic ones 2147483649, 2147483650, … and beacon ones 1073741825, 1073741826, …. Ids are never reused: a destroyed version keeps its id in the record.

A key id is a kms_aead::KeyId, which the keyring re-exports. value.key_id() reads the key id of a stored value, and version.algorithm().purpose() the purpose of a version. An operation that names a reserved key id fails with ReservedKeyId before any store call.

States

                       promote                          retire           destroy
  rotate ──▶ Pending ──────────▶ Active ──▶ DecryptOnly ──────▶ Retired ─────────▶ Destroyed
                │                   ▲            ▲                 │                   ▲
                │       create ─────┘            └────reinstate────┘                   │
                └───────────────────────────────destroy────────────────────────────────┘
  • Pending: staged by a rotation. Decrypts, and never encrypts until it is promoted. At most one per purpose;
  • Active: encrypts new values and decrypts. At most one per purpose;
  • DecryptOnly: decrypts only. Every version a promotion replaced;
  • Retired: refused on read with KeyVersionRetired. The encrypted DEK stays in the record, so reinstate can undo it;
  • Destroyed: the encrypted DEK is removed from the record, and reads fail with KeyVersionDestroyed.

A promotion moves the previous active version to DecryptOnly, and so does mark_compromised on an active version. Any state right of Active may also be compromised. The flag is set by mark_compromised, with a time and an optional note, and never clears. Pending and Active are never compromised: a compromised active version moves to DecryptOnly in the same write that flags it.

KeyringRegistry::create starts each purpose with an active version. Every later version starts as pending, except the replacement mark_compromised adds for an active version, which is active at once.

  • rotate and change_algorithm while the purpose has a pending version fail with Transition::Rotate, naming that version. Promote or destroy it first;
  • retire, mark_compromised and reinstate refuse a pending version, which never sealed a value. destroy it instead.

Each call reads the record, applies the change and writes it with a compare-and-swap, reading again after a conflict up to KeyringOptions::cas_retries times, KeyringOptions::DEFAULT_CAS_RETRIES by default, before RecordConflict.

States move forward only: nothing returns to Pending, and Pending moves only to Active or Destroyed. A running process refuses a record that moves a version or the seal epoch backwards, see Record cache.

Staged rotation

A rotation is two calls, so that no process meets a value under a version it does not know yet:

  1. rotate(purpose) stages the version. Every process decrypts under it once its record refreshes, and none encrypts under it;
  2. after a wait, promote(key_id) makes it active. Processes seal under it from their next refresh, and every process that reads those values already has the version.

Promote only after the longest time any process may run without a successful refresh of its record, counted from KeyVersion::staged_at(). For a healthy process that time is at most record_ttl, KeyringRegistryOptions::DEFAULT_RECORD_TTL by default. A process whose revalidations fail keeps its cached record for as long as they fail, and logs a WARN on each failure: “The keyring record could not be revalidated; the cached record stays in use”. A deployment whose instances can take hours to update or to reach the store waits as long. Alert on that WARN: an instance that logs it is one a promotion can leave behind.

promote holds the promotion back for the registry’s record_ttl from staged_at(): before that it fails with PromotionTooEarly, whose remaining is the time left, so the job can sleep that long and call it again. The guard covers healthy processes only. promote_now skips it, for a fleet known to have refreshed since the rotation, such as one restarted since, and for a compromise that cannot wait.

The guard waits the record_ttl of the registry the KeyringAdmin was opened from. Nothing in the record carries the TTL the other processes run with, so the administrative job’s registry needs the longest record_ttl in the fleet. The guard also compares this host’s clock with the staged_at() the staging host’s clock wrote, and a skew between the two clocks shortens or lengthens the wait by as much.

An instance that has not seen the version when it reads a value under it treats the key id as unknown and reloads its record once, at most once per reload_min_interval. When the store answers, the read succeeds after the reload; when it does not, the read fails with KeyVersionUnknown. The wait before promote is what keeps that path rare.

use std::sync::Arc;

use kms_aead::backends::Ring;
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead_keyring::testing::MemoryKeyringStore;
use kms_aead_keyring::{
    KeyId, KeyVersionState, KeyringAdmin, KeyringAlgorithms, KeyringError, KeyringId,
    KeyringRecord, KeyringRegistry, KeyringRegistryOptions, Purpose, Rotation,
};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
let provider =
    LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("tenant-kek".to_string())?)?;
let registry = KeyringRegistry::<MemoryKeyringStore, Ring>::new(
    MemoryKeyringStore::new(),
    KeyringRegistryOptions::new(),
)?;
let admin: KeyringAdmin<MemoryKeyringStore, LocalKmsProvider<Ring>, Ring> = registry
    .open_or_create(provider, KeyringId::from_static("tenant-42"), KeyringAlgorithms::new())
    .await?;

// The administrative job stages the version
let staged: KeyId = admin.rotate(Purpose::Randomized).await?;
let record: Arc<KeyringRecord> = admin.keyring().record();
let pending = record
    .pending(Purpose::Randomized)
    .ok_or("no pending version")?;
assert_eq!(pending.state(), KeyVersionState::Pending);

// Inside the record TTL from `pending.staged_at()`, `promote` refuses and says how long is left
assert!(matches!(
    admin.promote(staged).await,
    Err(KeyringError::PromotionTooEarly(error))
        if error.remaining <= KeyringRegistryOptions::DEFAULT_RECORD_TTL
));

// The job waits that long and promotes it; `promote_now` stands in for the wait here
let rotation: Rotation = admin.promote_now(staged).await?;
assert_eq!(rotation.current, staged);
assert_eq!(rotation.previous, Some(KeyId::new(1)));
registry.shutdown().await?;
Ok(())
}

Compromised versions

mark_compromised on the active version replaces it with a version that is active at once, not pending. Sealing under a compromised key has to stop at each process’s next refresh, and a wait before the replacement takes over would leave the leaked key sealing new values for that long. The cost is the one staged rotation avoids: a process that has not seen the replacement yet reloads its record once, rate-limited, when it meets a value under it. A pending version of the purpose stays pending, to be promoted or destroyed as planned.

The replacement needs a new DEK encrypted. When the KMS cannot encrypt it, in an outage or without the encrypt right, the flag is written alone, a WARN is logged, and the call returns Ok(None): the purpose then has no active version, and encrypt fails with NoActiveVersion until a version is promoted. Once the KMS answers, rotate and promote_now restore one, or promote_now on the pending version if the purpose has one: promote would refuse with PromotionTooEarly for up to record_ttl from the staging. A compromised flag is never held back by the KMS.

destroy and dangerously_destroy_all_versions remove encrypted DEKs from this record only. A backup of the record still holds them, and the KMS still decrypts them as long as the KEK version that encrypted them exists, see Crypto-shredding.

Reading a compromised version

KeyringOptions::compromised_reads decides what decrypt does with a value under a compromised version:

  • CompromisedReadPolicy::Block, KeyringOptions::DEFAULT_COMPROMISED_READS: fails with KeyVersionCompromised, decided on the cached record before any decryption;
  • CompromisedReadPolicy::Allow: decrypts, with one WARN event per value. Use it for the time of a sweep when availability matters more, and be aware the leaked DEK can forge values under that id meanwhile.

decrypt_with_trust opens the value whatever the policy, and returns a Decrypted with the value, the key id of the version that opened it and its KeyTrust, Trusted or Compromised. It is the call for a sweep. A compromised version’s DEK is decrypted by the provider for that call only and never returns to the DEK cache.

Memory

MemoryKeyringStore loses its records when the process exits, and with them the encrypted DEK of every version: a value sealed under a keyring in it, and kept anywhere that outlives the process, never decrypts again. Use it for tests, or for values that never outlive the process.

It lives in kms_aead_keyring::testing for that reason, and is compiled in every build. Clone shares the same records. It keeps each record as its JSON document, as the other stores do, and signals a watch on every write.

Firestore

The record of a keyring is the document kms_keyrings/<keyring id>, whose fields are those of the record’s JSON. with_collection takes another collection than FirestoreKeyringStore::DEFAULT_COLLECTION, as firestore-rs’s FirestoreCollectionId. A create fails when the document exists, and an update carries the update time it read as its precondition.

FirestoreDb is the firestore crate’s own client: the application builds it with the project, database and credentials it chooses. The version of the firestore crate is part of this crate’s API under the firestore feature.

Each store holds one listen stream, with a target on the document of each keyring it watches. Firestore’s point-in-time recovery restores an earlier record. Be aware the firestore crate logs every listen event at trace level on its firestore target, documents included, so that level writes encrypted DEKs to the log. Keep it off where the log leaves the administration’s reach.

PostgreSQL

One row per keyring, in a table the operator creates. The library runs no migrations. The table, kms_keyrings unless with_table names another:

CREATE TABLE kms_keyrings (
    id         TEXT PRIMARY KEY,
    record     JSONB NOT NULL,
    revision   BIGINT NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
  • the rights of the application and the administration on the table are in Store rights;
  • the table name is unqualified, so the connection’s search_path selects the schema;
  • every write sends NOTIFY <table>, '<keyring id>' when it commits, through pg_notify in the same statement;
  • PostgreSQL lets any session notify any channel. A keyring revalidates at most once per reload_min_interval however many signals arrive, so a stray NOTIFY costs one read.

The store connects through tokio-postgres, with a tokio_postgres::Config and a TLS connector the application chooses. NoTls for a local database:

    .with_table(PostgresTable::try_from("tenant_keyrings".to_string())?);

Ok(())
}

tokio-postgres-rustls’s MakeRustlsConnect for production, here with the platform’s root certificates:

use kms_aead_keyring::store::PostgresKeyringStore;
use rustls::{ClientConfig, RootCertStore};
use tokio_postgres::Config;
use tokio_postgres_rustls::MakeRustlsConnect;

}

postgres-native-tls’s MakeTlsConnector works the same way for the platform TLS library.

The store opens at most two connections, whatever the number of keyrings on it:

  • the query connection, on the first read or write. When it is lost, the call that finds it lost fails, and the next call connects again. Concurrent calls wait for one attempt;
  • the listener connection, on the first watch, shared by every keyring that watches. It closes when the last watch is dropped. When it is lost, every keyring hears of it, the store reconnects after a delay that doubles from 0.5 to 30 seconds, and the keyrings revalidate.

Clones of the store share both connections. Set connect_timeout on the Config to bound each attempt: calls wait for the attempt in progress.

The postgres feature also enables kms-aead’s postgres feature, which gives Encrypted tokio-postgres’s ToSql and FromSql as BYTEA, see Encrypted fields.

Cloud Storage

Each record is the object kms-keyrings/<keyring id>.json in a bucket, through the google.storage.v2 gRPC API. with_prefix sets another prefix than GcsKeyringStore::DEFAULT_PREFIX; one that should read as a folder ends with /. A write is conditional on the generation the writer read, and a revalidation reads the object only when its generation changed.

S3-compatible servers

A server is S3-compatible for this store when it passes the store conformance suite, kms-aead-keyring/tests/store_conformance.rs. Its checks include the ones a compare-and-swap needs from the server: it refuses a create over an existing object, an update at a stale ETag, and an update of an object that does not exist. A server that writes the object in the last case, as some MinIO releases do, recreates a deleted record on the next administrative write. To run the suite against a server, with the credentials of the environment:

KEYRING_S3_ENDPOINT=http://minio:9000 KEYRING_S3_BUCKET=my-keyrings \
  cargo test -p kms-aead-keyring --features s3 --test store_conformance s3:: -- --ignored

Set the server’s endpoint on the client, and force_path_style(true) when it serves buckets by path, as MinIO does by default. aws-sdk-s3 adds a CRC checksum to every upload by default, which some S3-compatible servers do not accept, and every write of the record then fails there. request_checksum_calculation(RequestChecksumCalculation::WhenRequired) sends a checksum only where the operation requires one, which the store’s PutObject does not:

use aws_config::BehaviorVersion;
use aws_sdk_s3::config::RequestChecksumCalculation;
use kms_aead_keyring::store::{S3BucketName, S3KeyringStore};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
let config = aws_config::defaults(BehaviorVersion::latest())
    .endpoint_url("http://minio:9000")
    .load()
    .await;
let client = aws_sdk_s3::Client::from_conf(
    aws_sdk_s3::config::Builder::from(&config)
        .force_path_style(true)
        .request_checksum_calculation(RequestChecksumCalculation::WhenRequired)
        .build(),
);
let store = S3KeyringStore::new(client, S3BucketName::try_from("my-keyrings".to_string())?);
let _ = store;
Ok(())
}

Your own store

KeyringStore is a trait with four methods, load, revalidate, compare_and_swap and watch, which returns None for a store without push, a Revision type and a KIND, such as StoreKind::Other("spanner"), for spans and errors. When implementing it:

  • write each method as an async fn whose future is Send;
  • read a stored document with KeyringRecord::from_json and write one with KeyringRecord::to_json, so the document is the one every store keeps and every read checks it;
  • return the client’s errors as KeyringError::Store, with the client’s error as the root cause. Never format the record or the request into an error and never log either, since both carry encrypted DEKs.

MemoryKeyringStore is the reference implementation, see its source, and the conformance suite holds the checks every store passes.

Record cache

Each Keyring keeps its record in the process, and the decrypted DEKs of its versions in kms-aead’s DEK cache. encrypt, decrypt and beacon read both, so the hot path calls neither the store nor the KMS.

How the record is refreshed

  • Age: the first call that finds the record older than record_ttl revalidates it with a conditional read, while the other calls keep using it;
  • Change signals: on a store with push, a signal causes a revalidation, at most once per reload_min_interval. Signals inside the interval collapse into the next one;
  • Unknown key ids: a value with a key id the record does not have causes one reload, which concurrent misses share, at most once per reload_min_interval. Values with random key ids then cost at most one store read per interval. A re-seal of a value under a version the record holds as pending reloads the same way, and shares the same interval: another process sealed it, so it saw the version active;
  • Own writes: a KeyringAdmin call takes the record it wrote. Every Keyring of the same keyring in the registry shares that cached record, so the process that promotes a version seals under it at once.

Keyring::reload reads the record now, past the TTL and the rate limit, for operators and tests.

How late a change is seen

A change written by another process, such as a staged version, a promotion or a compromised flag, reaches a running process:

  • with push: within reload_min_interval of the signal, about 5 seconds by default;
  • without push, on Cloud Storage and S3, with watch off, or while the listener is disconnected: once the cached record is older than record_ttl, at most 5 minutes by default;
  • not until the store answers again, while its revalidations fail: it keeps its cached record, see below.

So record_ttl is the bound to set for how long a compromised version may keep being read somewhere in the fleet, and the least wait between staging a version and promoting it, see Staged rotation. Writers on the old record keep sealing under the previous version until their record refreshes, and those values decrypt, since the previous version is DecryptOnly.

When the store fails or misbehaves

  • A failed revalidation keeps the cached record in use, logs a WARN, “The keyring record could not be revalidated; the cached record stays in use”, and is retried after reload_min_interval. A process that logs it is one that misses every change until the store answers again, so alert on it;
  • a record that went missing from the store keeps the cached one in use, with a WARN. New processes fail at open with RecordMissing;
  • a refreshed record is taken only if it moves every version forward from the cached one: no version missing, no changed algorithm or creation time, no compromised flag cleared, no state moved back against the lifecycle, such as a version back to Pending, no seal epoch below the cached one, which would give records sealed under different versions one marker, and no seal range moved back or started or ended at or below the cached epoch, which would leave the records this process sealed under a version outside its range. Otherwise the process keeps its record and logs an ERROR naming the first rule broken. reload and a write of a KeyringAdmin return RecordRegressed in that case.

The last rule is the detection of a rewritten or restored record in a running process. A process that starts after such a write has no record to compare with and takes it.

DEK eviction

Taking a refreshed record evicts from the DEK cache every key it takes out of use: versions retired, destroyed or newly compromised, and the old bytes of a re-encrypted one. mark_compromised evicts the key from its own process before it returns.

The DEK cache drops expired keys only when it is called. A process that can sit idle while it holds keys calls keyring.dek_cache().purge_expired() on a timer of its own, so the cache’s TTL bounds how long a key stays in memory, see Key lifetime.

Encrypted fields and AAD

Encrypted values

A keyring value is kms-aead’s Encrypted<T, Randomized>, re-exported by the keyring: the bytes to store, which decrypt to a T. T is any type that implements Plaintext, usually an application newtype such as Email, so a field names what it holds. Its layout is in Formats of Encrypted. The keyring seals and opens it with kms-aead’s AeadCipher::encrypt and decrypt under the key of the version, the calls an application with one fixed key makes itself.

  • value() and into_value() return the bytes;
  • key_id() returns the key id of the version that sealed it;
  • Encrypted::try_from(bytes), serde and tokio-postgres check stored bytes against the layout when the value is made, and fail on bytes that are no keyring value before any decryption;
  • decrypt checks the key id first, and fails with ReservedKeyId on a reserved id and with KeyPurposeMismatch on a deterministic one, before any store or KMS call;
  • Debug shows the length only. A randomised value has no ==: two values of one plaintext differ.

The plaintext types and their encodings are in Stored values.

AAD

The default AAD of a value is its place in the application’s model, <kind>/<id>/<field>, such as user/42/email:

  • EntityKind, such as user;
  • EntityId, the row’s id, which binds the value to its row;
  • FieldName, such as email.

Each part is 1 to 255 bytes of UTF-8 without /, NUL or another ASCII control character. An id that holds / is encoded by the application first, with percent-encoding for example.

A FieldSpec names the kind and the field once, as a constant, and FieldSpec::aad(&id) builds the AAD of one row. from_static checks a kind or field name at compile time when it initialises a constant.

So a value opens only in its own row and field. A value copied into another row fails with KeyringError::KmsAead with code DECRYPT. And since the AAD names the logical place, not the physical one, a value moves between tables and data stores without being encrypted again.

An EntityId can be personal data, so no span, event or error of the crate carries it.

Deterministic fields have an AAD without the entity id, see Deterministic fields, and beacons a context without it, see Beacons.

Why the AAD is structured

kms-aead’s AeadCipher and KmsAeadEnvelope take the AAD as any impl AsRef<[u8]>: the application chooses the bytes and rebuilds them itself on every read. The keyring’s encrypt and decrypt take a FieldAad instead, which only a FieldSpec builds:

  • field binding: the default AAD names the kind and the field, so a value copied into another field of the same row fails to open;
  • row binding: it names the entity id, so a value copied into another row fails to open. The application’s own id, such as a user id, is the EntityId;
  • deterministic fields: a deterministic AAD must not hold the row id, or equal plaintexts in different rows give different values and equality lookups never match. DeterministicAad is a separate type, with no entity id and no constructor from arbitrary bytes, see Deterministic fields;
  • BigQuery: BigQuery decrypts in SQL, so the AAD has to be one SQL can rebuild from the row. <kind>/<id>/<field> is this crate’s convention, which CONCAT('user/', u.id, '/email') rebuilds; BigQuery itself prescribes no format;
  • Tink: Tink takes any AAD bytes. The requirements of a Tink field are on the algorithm and the KEK, not on the AAD;
  • the interop requirement: a FieldAad carries the Interop of its FieldSpec, so sealing checks the field’s requirements whichever way the AAD was built. Free bytes would name no field and skip that check.

The application’s own context

There are three ways to put the application’s own data, such as a user id or a tenant, into the AAD:

  • spec.aad(&id) with the application’s id as the EntityId. The id follows the EntityId rules: 1 to 255 bytes of UTF-8 without /, NUL or another ASCII control character. It is treated as personal data and never logged;
  • FieldAad::with_context(bytes) appends / and any bytes, such as a tenant or a schema version. A value sealed with a context opens only with the same one. The context may itself hold /, so keep the contexts of one field apart yourself. A BigQuery reader appends the same bytes in SQL, CONCAT('user/', u.id, '/email/tenant-7');
  • FieldSpec::custom_aad(bytes) takes any bytes, with no structure, in place of the default AAD. It gives up field binding and row binding, unless the bytes name the field and the row themselves, and BigQuery readability: on a field declared with Interop::BigQuery it fails with KeyringError::CustomAadUnsupported, since SQL cannot rebuild such bytes. On a Tink field or a field without interop it keeps the field’s algorithm and KEK checks.

Deterministic fields

Feature deterministic, to create deterministic key versions. The deterministic types exist in every build, so values pass through a process without the feature.

Deterministic fields fit exact-match lookups where the leak of equality is acceptable. When a field only needs lookups and its stored value should stay randomised, a beacon fits instead.

What they leak

A deterministic column leaks equality and frequency to anyone who reads it, and a leaked deterministic DEK lets its holder test candidate values offline, see What it leaks in kms-aead.

The AAD of a deterministic field names its kind and field and no entity, see AAD, so a deterministic value also opens in any row of the same kind and field, and a deterministic field never decides identity or authorisation on its own.

A deterministic value is an Encrypted<T, Deterministic>, a type of its own, so it is never handed to decrypt by mistake. Unlike a randomised value it has == and Hash, which compare the bytes. AES-SIV runs on the RustCrypto aes-siv crate whatever the keyring’s AEAD backend.

decrypt_deterministic applies the compromised read policy, and decrypt_deterministic_with_trust reports the version’s trust, as their randomised counterparts do.

AAD

The AAD of a deterministic value is <kind>/<field>, such as user/email, built by FieldSpec::deterministic_aad(). It holds no entity id, otherwise equal plaintexts in different rows would give different values and an equality query would find nothing.

DeterministicAad::with_context(bytes) appends / and a context, such as a tenant id, to keep the values of two scopes apart. A context that differs per row defeats equality across rows, so it is a constant for the field. There is no constructor from arbitrary bytes: a deterministic value exists to be queried, and the query rebuilds its AAD.

Beacons

A beacon, or blind index, finds rows by a field’s value without decrypting the column: a truncated HMAC-SHA256 of the value, stored beside the field’s randomised value, which a data store matches by equality. The keyring computes beacons under its beacon versions, of the purpose Purpose::Beacon, which rotate like any other.

kms-aead’s Beacons describes the primitive, Beacon<T> and BeaconBits, with keys the application keeps itself, and Formats its bytes.

A deterministic field also finds rows by equality, by its encrypted value, see Beacon or deterministic field.

What a beacon leaks

A beacon column leaks likely equality and frequency to anyone who reads it, and a leaked beacon key lets its holder test candidate values offline, see What a beacon leaks in kms-aead.

A beacon is computed in a field’s context, <kind>/<field> such as user/email, with no entity id: equal values in different rows give equal beacons, which is what a lookup matches. A beacon of one field never matches a beacon of another.

Usage

A keyring with beacon versions names their algorithm in its KeyringAlgorithms: HMAC-SHA256, the one BeaconAlgorithm has. Bits

FieldSpec::with_beacon_bits sets how many bits of the HMAC the field’s beacons keep, BeaconBits::DEFAULT, 16, unless set; what the bits trade is in Bits. The bits enter the HMAC, so after a change of a field’s bits, its stored beacons match no probe until a re-index computes them again. A beacon is the HMAC of the bytes the Plaintext type encodes, so the field’s newtype normalises the value, as Email::new lowercases above, see Normalisation.

BigQuery

The keyring never exports beacon keys to BigQuery: export_bigquery_keyset of the beacon purpose fails with ExportAlgorithmUnsupported, see Exporting a keyset to BigQuery. A BigQuery query matches beacons the application computed, see BigQuery in kms-aead.

Rotating beacon versions

A beacon version rotates as the other purposes do, see Staged rotation, and a column holds beacons of several versions while it is re-indexed:

  1. rotate(Purpose::Beacon) stages the version. beacon_probes returns a probe under it from the next refresh of each process, so lookups find the beacons computed under it before every process has seen the promotion;
  2. after the wait, promote it. Writes compute beacons under it from each process’s next refresh;
  3. lookups use beacon_probes throughout: one probe per pending, active or decrypt-only beacon version, compromised ones included, newest first;
  4. the promotion moved the keyring’s seal epoch on, so every row written before it has a SealMarker below the current one, and a re-index sweep visits them, see Sweeps. It computes each row’s beacon again under the active version of its sealer and writes the sealer’s marker; a row without a beacon gets the marker alone;
  5. once the sweep reports no failure and that query returns nothing, retire the old version, and its probe drops out of every lookup.

beacon.key_id() reads the key id of a stored beacon, so that the sweep recomputes only the beacons under an older version. Beacon versions are rotated by policy and on compromise only: each one adds a probe to every lookup until the re-index is done.

BigQuery and Tink interop

Keyring values are in Tink’s wire format, so Tink and BigQuery’s AEAD functions read the values the keyring writes, and the keyring reads theirs, given the same keys under the same key ids.

Wire format

Every value starts with Tink’s 5-byte TINK prefix, a version byte 0x01 and the key id, followed by what the version’s algorithm writes, see Formats of Encrypted. These are the layouts of Tink’s AEAD and deterministic AEAD primitives, and of BigQuery’s AEAD.ENCRYPT and DETERMINISTIC_ENCRYPT. A randomised version with another algorithm, such as ChaCha20-Poly1305, writes the same prefix before its own body, which only kms-aead reads.

The prefix is not authenticated. A value relabelled with another key id selects another version, whose key the body does not open under.

AAD in SQL

Both default AADs are UTF-8 text, so SQL rebuilds them from the row with no byte escaping:

-- Randomised: <kind>/<id>/<field>
AEAD.DECRYPT_STRING(keyset, u.email_enc, CONCAT('user/', u.id, '/email'))

-- Deterministic: <kind>/<field>
DETERMINISTIC_DECRYPT_STRING(keyset, u.email_det, 'user/email')

keyset is KEYS.KEYSET_CHAIN(@kms_key, @keyset) over an export of the keyring’s versions, see Exporting a keyset to BigQuery. SQL cannot rebuild an AAD of the application’s own bytes, so FieldSpec::custom_aad fails on a field declared with Interop::BigQuery, see Why the AAD is structured.

The plaintext encodings are the ones SQL reads: String and Json<T> with AEAD.DECRYPT_STRING, the integers with a CAST of it, and Vec<u8> with AEAD.DECRYPT_BYTES. An application type reads as the type it encodes as, such as Email as a String.

Fields BigQuery reads

BigQuery decrypts through KEYS.KEYSET_CHAIN, which implements AES-256-GCM and AES-SIV only and decrypts with Cloud KMS only. A field BigQuery also decrypts is declared with FieldSpec::with_interop(Interop::BigQuery), and the keyring then refuses to seal it unless:

  • a randomised value is sealed under an AES-256-GCM version, the default of a new keyring;
  • a deterministic value is sealed under an AES-SIV version;
  • the KEK is in Google Cloud KMS.

The check runs on a sealer’s encrypt and encrypt_deterministic, before sealing, and fails with KeyringError::Interop naming the first requirement broken. Values already written always decrypt: only sealing checks. So a change_algorithm away from AES-256-GCM, or a keyring on another KMS, fails the next write of the field instead of silently writing values BigQuery cannot read.

Fields Tink reads

A field that Tink also decrypts, with the keyset of export_tink_keyset, is declared with FieldSpec::with_interop(Interop::Tink). The keyring then refuses to seal it unless:

  • a randomised value is sealed under an AES-128-GCM, AES-256-GCM or AES-256-GCM-SIV version;
  • a deterministic value is sealed under an AES-SIV version;
  • the KEK has a Tink key URI: a Cloud KMS key, an AWS KMS key named by its ARN, or a Vault Transit key.

ChaCha20-Poly1305 is left out, since Tink for Python and C++ do not read it in a keyset. The check and its errors are the ones of Interop::BigQuery, with Interop::Tink in the error.

Exporting a keyset to BigQuery

Feature bigquery-export. It builds on kms-aead’s GCP provider with no TLS root store, so the application also enables kms-aead’s gcp-kms-encryption, or another root store feature of kms-aead’s GCP provider.

BigQuery reads keyring values through KEYS.KEYSET_CHAIN, which takes a Tink keyset encrypted by a Cloud KMS key. KeyringAdmin::export_bigquery_keyset builds that keyset from the keyring’s versions, on a keyring whose provider is GcpKmsProvider, under the bigquery-export feature, which implies admin. The bytes it returns are the Cloud KMS ciphertext of Tink’s serialised Keyset message, encrypted with no associated data, without the EncryptedKeyset message Tink’s own keyset readers take, see Exporting a keyset to Tink:

The selection:

  • KeysetSelection::Readable(purpose): every version of the purpose that decrypts and is not compromised, the pending one included, with the active version as the primary. BigQuery opens a value under the key its prefix names, so one keyset reads a column written across rotations. It fails with NoActiveVersion when the purpose has none;
  • KeysetSelection::Single(key_id): the one version as the primary, also when it is compromised. It is the keyset of DETERMINISTIC_ENCRYPT, which encrypts under the primary, for the probe of one version, and of a read through a compromised version. A retired, destroyed or unknown version fails as a read under it does, and a pending one with KeyVersionPending, since BigQuery would seal under it.

Beacon versions are never exported: a selection of the beacon purpose fails with ExportAlgorithmUnsupported. BigQuery’s SQL cannot compute a beacon either, see BigQuery in kms-aead.

The type parameter of a EncryptedKeyset is its encoding, from the encodings module, which names the reader of its bytes. The EncryptedKeyset<encodings::BigQuery> this export returns:

  • value() and into_value(): the encrypted keyset, as a BYTES column or query parameter holds it;
  • key_uri(): Tink’s key URI of the Cloud KMS key, gcp-kms://projects/…/cryptoKeys/…, the first argument of KEYS.KEYSET_CHAIN, as a STRING query parameter;
  • key_ids(): the key ids of the versions inside, in ascending order.

The export selects its versions from the record in the store, read at the time of the call, not from the record the process has cached. A version another process flagged compromised is therefore left out of a Readable keyset, even before this process’s cached record refreshes. The read is checked as a revalidation is: a stored record that moves a version backwards fails the export with RecordRegressed, and a missing one with RecordMissing.

A keyset is a copy of the record at the time of the export. A Readable keyset exported while a version is pending already holds it, so the order of a rotation is: rotate, export the Readable keysets again, wait, promote. Values sealed under the new version then read in BigQuery from the first one. After mark_compromised, whose replacement is active at once, the replacement’s values do not read, and the compromised version stays in a keyset exported before it, until the keyset is exported again.

A KEK rotation changes no key inside a keyset and leaves the keyset under the KEK version that encrypted it at the export, so KEYS.KEYSET_CHAIN fails once that version is disabled. Export every keyset again after reencrypt_deks, once the new primary version has propagated, and replace the old bytes in every query and column that holds them before the old version is disabled, see Encrypted keysets.

Queries

Every value reaches the query as a parameter: @kms_key is the export’s key_uri(), each keyset parameter its value(), and @email the address an equality query looks for:

-- Randomised values, with a Readable(Randomized) keyset
SELECT AEAD.DECRYPT_STRING(
  KEYS.KEYSET_CHAIN(@kms_key, @keyset), u.email_enc, CONCAT('user/', u.id, '/email'))
FROM users u;

-- Deterministic values, with a Readable(Deterministic) or Single keyset
SELECT DETERMINISTIC_DECRYPT_STRING(KEYS.KEYSET_CHAIN(@kms_key, @keyset), u.email_det, 'user/email')
FROM users u;

-- An equality query: one probe per deterministic version, each with its Single keyset
SELECT u.id
FROM users u
WHERE u.email_det IN (
  DETERMINISTIC_ENCRYPT(KEYS.KEYSET_CHAIN(@kms_key, @keyset_d2), @email, 'user/email'),
  DETERMINISTIC_ENCRYPT(KEYS.KEYSET_CHAIN(@kms_key, @keyset_d1), @email, 'user/email')
);

The probes in BigQuery are those of the active and decrypt-only versions. A pending version has no Single keyset, and no value is sealed under it before its promotion.

The requirements:

  • the keyring’s KEK is a Cloud KMS key, and the query runs in the KMS key’s location;
  • the exported versions are AES-256-GCM or AES-SIV. Any other algorithm fails with ExportAlgorithmUnsupported, before any KMS call;
  • the field is declared with Interop::BigQuery, so that the keyring never seals it under a version the keyset could not hold, see Fields BigQuery reads;
  • the principal that queries has decrypt on the KMS key, and the one that exports has encrypt and decrypt on it. The export is a KeyringAdmin call, see KMS rights.

How it behaves

The crate’s live test runs the export and the queries against Cloud KMS and BigQuery:

  • a value whose key id is not in the keyset fails to decrypt, and reads as NULL under SAFE.AEAD.DECRYPT_STRING;
  • the keyset is encrypted with no associated data, since KEYS.KEYSET_CHAIN decrypts with none. What the KMS decrypts from it is a serialised Tink keyset, which is no serialised Tink key, so copied into a record as a version’s encrypted DEK it opens nothing and fails with INVALID_KEY_FORMAT;
  • the export decrypts each selected version through the provider and never through the DEK cache, so the keys stay in the process for the call only. Its span records dek_cache as bypassed.

Cloud KMS encrypts at most 64 KiB of plaintext, which a keyset reaches at several hundred versions.

Exporting a keyset to Tink

export_tink_keyset exports the same versions as Tink’s encrypted keyset, which Tink for Java, Go and Python open with KeysetHandle.read and their own KMS client. It is a KeyringAdmin call, needs the admin feature only, and runs on a keyring with any provider whose KEK has a Tink key URI. The bytes are a google.crypto.tink.EncryptedKeyset around the KMS ciphertext of the serialised keyset, see Tink keysets and the TINK prefix.

key_uri() is the URI of Tink’s KMS client:

  • gcp-kms://projects/…/cryptoKeys/… for a Cloud KMS key;
  • aws-kms://arn:aws:kms:… for an AWS KMS key named by its ARN;
  • hcvault://<host>/…/keys/<name> for a Vault Transit key, which Tink for Go reads. Tink for Java and Python have no Vault Transit client.

An Azure Key Vault key, a local or an application’s own KEK, and an AWS key named without its ARN have no Tink client. The export fails on them with KeyringError::Interop, Interop::Tink and InteropRequirement::Kek, before any store or KMS call.

After a KEK rotation, a Tink keyset is exported again and replaces the old one wherever a Tink reader opens it, as a BigQuery keyset does, see Encrypted keysets.

Operations

Running a keyring in production: how often to rotate, how sweeps move values to the active versions, the migration from envelope values, and what to do when a key leaks.

Rotation cadence

A rotation is staged: rotate, export the BigQuery keysets again, wait for every process to see the pending version, then promote. How often to rotate follows from the nonce and volume bounds of each purpose, and deterministic and beacon versions rotate rarely, since each adds a probe to every lookup until a sweep. See Rotation cadence.

Rotating the KEK

The KEK rotates in the KMS on its own schedule, and reencrypt_deks moves the record’s DEKs to its current version without changing any value, before the old KEK version is disabled. See Rotating the KEK.

Sweeps

A sweep re-seals stored values under the active versions, after a rotation, after a compromise and to migrate envelope values: a job the application runs on a schedule, which finds the records behind by their seal marker. Sweeps has the mechanism, and the sweeps by store have the queries and writes of Firestore, PostgreSQL and BigQuery.

Migrating from envelope values

Values that KmsAeadEnvelope wrote move to keyring values in five steps, with the seal marker telling the two layouts apart and a sweep re-sealing the envelope values. See Move envelope values to a keyring.

Emergency runbook

What to do when a plaintext DEK, an encrypted DEK or the record leaks, after a KMS IAM over-grant, a version the administrative job did not create, a deleted or corrupted record and a KMS outage, and how to crypto-shred a scope. See Emergency runbook.

Rotation

Rotation cadence

A rotation is staged: rotate(purpose) adds a pending version, which every process decrypts under once its record refreshes, and promote(key_id) makes it active once every process has had time to see it, see Staged rotation. The previous version keeps decrypting. Nothing is lost while the change propagates: processes on the old record seal under the previous version until their record refreshes, and those values decrypt.

The administrative job runs a rotation in steps, on its KeyringAdmin, see Applications and administration:

  1. rotate(purpose);
  2. export the Readable BigQuery keysets again, which then hold the pending version;
  3. wait the longest time any process may run without a successful refresh of its record, counted from staged_at(), and check that no process logged “The keyring record could not be revalidated” meanwhile;
  4. promote(key_id). Until record_ttl has passed since staged_at() it fails with PromotionTooEarly, whose remaining is the time left. promote_now(key_id) skips that guard, for a fleet known to have refreshed since the rotation or a compromise that cannot wait.

The rotate example runs the whole cycle, and a KEK re-encryption after it, on the memory store and the local KMS: cargo run -p kms-aead-keyring --example rotate --features ring,admin.

How often:

  • A randomised DEK with random 96-bit nonces is good for about 2^32 values, see Nonces. The library cannot count the values a fleet seals, so estimate them: at 550 values per second a version reaches 2^32 in 90 days. Rotate every 30 to 90 days, sooner at higher rates. AES-128-GCM, AES-256-GCM, AES-256-GCM-SIV and ChaCha20-Poly1305 all take a 12-byte nonce, so the same cadence applies to each;
  • AES-GCM also bounds the data sealed under one key: RFC 8446, section 5.5, allows 2^38.5 bytes for an AE advantage of about 2^-57. The keyring does not count bytes, since its DEKs are shared across processes, so schedule rotation to stay below 2^38 bytes per version under AES-GCM, the default max_bytes of a store-less envelope. AES-256-GCM-SIV and ChaCha20-Poly1305 need no volume bound beyond the count of values;
  • a deterministic version has no nonce, so it is rotated by policy and on compromise only. Every deterministic rotation adds a probe to each equality query until a full sweep re-seals every row, see Queries across rotations, so rotate deterministic versions rarely;
  • a beacon version likewise, since every beacon rotation adds a probe to each lookup until a re-index, see Rotating beacon versions.

After a promotion, export the Single BigQuery keysets of the new deterministic version, since a pending version has none.

Rotation does not touch values already written. A sweep re-seals them: a job that runs on a schedule until its SweepReport shows nothing scanned. Retiring the old version is a separate step of the administrative job, once the sweep is done and the old version’s range query returns nothing: retire, and later destroy.

Rotating the KEK

The KEK rotates in the KMS on its own schedule. After a rotation, reencrypt_deks() decrypts every DEK in the record and encrypts it again under the KEK’s current version. No value changes. A keyring that is not re-encrypted keeps working as long as the old KEK versions stay enabled in the KMS.

reencrypt_deks is a KeyringAdmin call and runs in the administrative job, like every call that encrypts a DEK.

The record keeps the KEK version of each encrypted DEK, as the KMS reported it when it encrypted the DEK: KeyVersion::kek_version. reencrypt_deks returns one DekReencryption per version, with the KEK version its DEK was under and the one the KMS encrypted it with now, and kek_versions_in_use of the record lists every KEK version the record’s DEKs are under. Before the old KEK version is disabled, the record that Keyring::reload returns must list the new version alone, which needs no KMS call. Once the old version is disabled, reencrypt_deks runs again: it decrypts every DEK through the KMS and fails on one the KMS no longer decrypts. Here with the local KMS, rotated from version 1 to version 2, where dropping version 1 from the provider stands for disabling it:

use std::num::NonZeroU32;

        LocalKek::from_secret(v2, SecretValue::new(vec![0x02; 32]))?,

)?;
let admin = registry.admin(rotated, TENANT).await?;

let record = admin.keyring().reload().await?;

    kek_id,
    vec![LocalKek::from_secret(v2, SecretValue::new(vec![0x02; 32]))?],

Under Cloud KMS, a reencrypt_deks that ran before the new primary version had propagated reports the old version as the one the DEK is under now, and the record keeps listing it: run reencrypt_deks again once the rotation has propagated. Under Vault Transit, min_decryption_version disables every version below it at once, which is why the check asks for the new version alone.

The whole procedure, with the application’s own DEKs and keysets, is in Re-encrypting DEKs after a KEK rotation.

A KEK version the KMS did not report

A None among the versions in use stands for the DEKs whose KMS reported no version: every DEK under AWS KMS, and under a KMS with versions, a version that is unknown, as with an application’s own provider that returns none. reencrypt_deks keeps such a DEK at None, so the check before the disable never passes, and the check once the old version is disabled is the only one:

  1. run reencrypt_deks after the rotation;
  2. disable the old version in the KMS;
  3. run reencrypt_deks again. It decrypts every DEK through the KMS, so an error is a DEK the KMS no longer decrypts: enable the old version again, and go back to step 1.

Between steps 2 and 3, a DEK still under the old version fails in the application too, once its DEK cache entry has expired. Under AWS KMS only imported key material can be removed, see AWS KMS.

Sweeps

A sweep re-seals stored values under the active versions: after a rotation, to retire the old version, after a compromise, and to migrate envelope values. It is a job the application runs, a CLI or a Kubernetes Job, never a task inside the library: only the application knows its tables, its queries and its write rules. The job runs on a schedule, and again until its SweepReport shows nothing scanned. A run that stops part-way or fails on some records needs no checkpoint: the next run’s marker query returns exactly the records it did not write. Retiring the old version is a separate step of the administrative job, see Rotation cadence.

The seal marker

A keyring record counts a seal epoch, which moves on by one with every administrative write that makes a version active:

CallSeal epoch
create, and open_or_create when it creates1
promotemoves on by one
mark_compromised of the active version, with its replacementmoves on by one
mark_compromised that writes the flag alone, or of any other versionunchanged
rotate, change_algorithmunchanged: the version they add is pending
retire, reinstate, destroy, reencrypt_deks, dangerously_destroy_all_versionsunchanged

A write moves the epoch once, however many versions it makes active. KeyringRecord::seal_marker() returns it as a SealMarker:

[0x01][seal epoch: u32 BE]

Markers compare as their epochs do, and so do their bytes, in Firestore, PostgreSQL and BigQuery alike. SealMarker::ENVELOPE is epoch 0, 01 00 00 00 00, the marker of a record of envelope values, below the marker of every keyring.

Each record of the application keeps the marker in one field beside its encrypted fields. A write that touches any encrypted field of a record takes one Sealer from keyring.sealer(), seals all of the record’s encrypted fields again through it, computes its beacons again, and stores sealer.record().seal_marker() in the same write, as write_user does in Running a sweep. The sealer keeps the record it took from the cache, so the marker names the epoch whose active versions the fields are under, also when the cache refreshes during the write.

A marker read from keyring.record() names whichever record the cache held when it was read. Read before the sealing, it can name an older epoch than the versions the fields are under, which puts the record outside the range of those versions. Read after, it can name a newer one, and the record then drops out of every sweep.

Finding records behind

The records a sweep still has to visit are those whose marker is below the current one:

  • seal < $1 with the marker of keyring.record().seal_marker(), on one indexed field, in every store;
  • row.seal < current in Rust, on a record read back before its re-seal.

The query also matches a record with nothing to re-seal: after a rotation of a purpose the record holds no value of, such as a beacon rotation for a record without beacons, its marker is below the current one all the same. The re-seal then writes the sealer’s marker alone, without decrypting anything or calling the KMS, and the record matches once.

Each process stamps the epoch of the record it caches. A process that has not refreshed its record since a promotion seals under the previous version and stamps the previous epoch, so its writes stay in the query and the next sweep visits them. So the final check that the query returns nothing runs once the longest time any process may run without a successful refresh of its record has passed since the promotion.

The marker comes from the cached record, so a job that starts right after a promotion in another process calls reload() first.

Records under a version

KeyVersion::seal_range() returns the markers of the records that can hold a value under the version, as a SealRange:

  • start(), the epoch of the write that made the version active;
  • end(), the epoch of the first write after it stopped being active that moved the epoch on, or None while there was none: the active version, and a version flagged compromised while it was active, until a version is next made active.

A version that was never active, pending or destroyed while pending, has no range, and neither has an unknown key id: record.version(key_id) is None. The queries:

Firestore takes both bounds on the one field and serves them from its ascending index on seal, and an open range is one filter:

use firestore::{FirestoreDb, FirestoreResult};
use futures_util::stream::{self, BoxStream, StreamExt};
use kms_aead::backends::Ring;
use kms_aead::providers::GcpKmsProvider;
use kms_aead_keyring::store::FirestoreKeyringStore;
use kms_aead_keyring::sweep::{SealMarker, SealRange};
use kms_aead_keyring::{KeyId, KeyVersion, Keyring};
use serde::{Deserialize, Serialize};

#[derive(Serialize, Deserialize)]
struct UserDoc {
    #[serde(rename = "_firestore_id", skip_serializing)]
    id: String,
    #[serde(default)]
    seal: SealMarker,
}

/// The users that can hold a value under `key_id`, as a stream: a range can hold millions.
async fn users_under<'a>(
    db: &'a FirestoreDb,
    keyring: &Keyring<FirestoreKeyringStore, GcpKmsProvider, Ring>,
    key_id: KeyId,
) -> Result<BoxStream<'a, FirestoreResult<UserDoc>>, Box<dyn std::error::Error>> {
    // The store's record: a compromise or promotion in another process is in it
    let range: Option<SealRange> = keyring
        .reload()
        .await?
        .version(key_id)
        .and_then(KeyVersion::seal_range);
    let Some(range) = range else {
        // Never active: no record holds a value under it
        return Ok(stream::empty().boxed());
    };
    let users: BoxStream<'a, FirestoreResult<UserDoc>> = db
        .fluent()
        .select()
        .from("users")
        .filter(|q| {
            q.for_all([
                q.field("seal").greater_than_or_equal(range.start()),
                range.end().and_then(|end| q.field("seal").less_than(end)),
            ])
        })
        .obj()
        .stream_query_with_errors()
        .await?;
    Ok(users)
}

The range serves two decisions:

  • after mark_compromised, the range of the compromised version returns every record to re-seal and decide on, see The trust of re-sealed values. The writes of processes that have not seen the compromise yet are in it too: they seal under the version and stamp an epoch below the range’s end. Run the query again once the longest time any process may run without a successful refresh of its record has passed since the compromise, for the writes of the last of them. A version flagged compromised after it stopped being active moves no epoch, and keeps the range it had;
  • before retire, and again before destroy, the query of the version returning nothing shows that no record holds a value under it. That check needs one record at most: limit(1) in Firestore, EXISTS in SQL.

One epoch counts the activations of every purpose of the keyring, so a range can match a record with no field of the version’s purpose, such as a record without beacons in the range of a beacon version. Its re-seal finds every value current and writes the marker alone. No range holds SealMarker::ENVELOPE, since every range starts at epoch 1 or later. Records of several keyrings in one table add the keyring’s id to the query, as the sweep’s query does, see Sweeps by store.

Re-sealing a value

Sealer::reseal(aad, value) returns None for a value under the active randomised version of the sealer’s record, without decrypting it or calling the KMS. A value under an older version the sealer’s record holds, a decrypt-only version with a higher key id than the active one included, is read with decrypt_with_trust and sealed again under the active version. The Resealed it returns holds the new value and the trust of the version the old value was read under, so the compromised-value decision stays with the caller, see The trust of re-sealed values. reseal_deterministic does the same for deterministic values, under the deterministic feature.

A sealer never seals a value back under an older version. A value under a version that is pending in the sealer’s record, or missing from it, was sealed by a process with a newer record, and a sealer taken before a mark_compromised would otherwise move it back under the compromised version. The re-seal fails with KeyringError::SealerOutdated, after reloading the cached record when it lacks the version or holds it as pending, under the same rate limit as decrypt’s reload for a key id it lacks. The sealer keeps its own record, so that its marker still names every version the write seals under. The write is safe to retry: it takes a new sealer and runs again, and the new sealer, taken from the reloaded record, finds the value current or seals it under its active version. Inside reload_min_interval of another such reload the cached record may not have moved yet, and the retry fails the same way until it does. When the store’s record itself holds the version as pending, as for a value from another keyring whose key id is pending here or after a restore from an older backup, every retry fails with SEALER_OUTDATED, at no more than one store read per reload_min_interval. A key id the reloaded record lacks too fails with KeyVersionUnknown.

A beacon cannot be re-sealed: it is a MAC of the plaintext. sealer.is_current(beacon.key_id()) applies the same rule to it: true under the active beacon version of the sealer’s record, and the beacon stays as it is; false under an older one, and the field is read with decrypt_with_trust, whose plaintext gives both the value under the active version, through the sealer’s encrypt, and the beacon under the active beacon version, through its beacon(field, &plaintext); and SealerOutdated under a version newer than the sealer’s record.

When nothing needs a re-seal, the write still stores the sealer’s marker, conditional on the record as the sweep read it, and the re-seal returns ResealOutcome::Skipped.

Running a sweep

sweep::run drives the application’s re-seal over a stream of candidates, with at most concurrency in flight, and counts what happened. sweep::run_batched cuts the same stream into batches, re-sealed and written back one batch per call, as BatchedSweepOptions sets: 100 candidates a batch and 4 batches in flight by default, DEFAULT_BATCH_SIZE and DEFAULT_CONCURRENCY. The stream returns each candidate as a Result, so that the query that finds them can fail into the report rather than end the sweep in silence. A sweep is data plane: it takes a Keyring and needs the application’s rights only, since a re-seal encrypts under a DEK the record already holds. The rotation before it and the retire after it are the administrative job’s, on a KeyringAdmin. Here over an in-memory table, with both in one process:

        .lock()
        .unwrap()

The SweepReport counts every candidate once in scanned, and once in resealed, skipped or failed. A candidate the stream returns as an error is counted in scanned and failed, and logged at WARN with the error’s Display; a stream whose query cannot go on returns its error and ends. A re-seal that fails does not stop the sweep either: it is counted in failed and logged at WARN with the candidate’s Display and the error’s Display. A re-seal that fails with SealerOutdated is one of them: a process with a newer record rewrote the record after the query returned it. The record is counted as failed, and the next run’s query no longer returns it, because the process that sealed it stamped a newer marker. A value under a version the store’s record itself holds as pending, such as a value from another keyring whose key id is pending here, fails in every run instead. A candidate is the application’s own type, such as a record id, a struct of key columns or the record itself, and its Display names the record and nothing else. A record id is often an entity id, so read the sweep’s log as an administrative log.

The stream returns Result<T, E> and the re-seal Result<ResealOutcome, E>, with the application’s own error type, any type that implements Display. The keyring’s calls inside it return a KeyringError, and a From impl on the application’s error lets ? convert it, as the examples on Firestore, PostgreSQL and BigQuery do with an error of their data store; a re-seal with no errors of its own returns KeyringResult<ResealOutcome>, as above. The error’s Display is the application’s text and goes to the log as it is, so it carries no value, secret or personal data. The report counts failures and keeps no error: an application that wants the errors themselves records them inside its re-seal.

Retiring the old version is not the sweep’s: once a run reports nothing scanned and the range query of the old version returns nothing, the administrative job retires it, see Rotation cadence. Keep it retired for a while before destroy: reinstate brings a retired version back for a value that turned up after all, while a destroyed one is gone.

Sweeps by store

At millions of records a sweep streams its candidates from the store in one query and never holds its result in memory, and it writes them back in batches. Every example, on Firestore, PostgreSQL and BigQuery, has the same five properties:

  • it resumes without a checkpoint: the query is the checkpoint, since a re-sealed record no longer matches it, so a cancelled or failed run is started again over the same query;
  • a concurrent writer wins: the write is conditional on the record the sweep read, and a record that changed in between is Skipped. The application’s own write re-seals every field under the active versions anyway;
  • concurrency bounds the batches in flight, and with them the load on both the store and the KMS. The DEK cache keeps each version’s key, so a sweep makes one KMS decrypt per key version and cache TTL, never one per record. The keys of a compromised version are the exception: they are decrypted for every value and never cached;
  • each write stores the marker of the sealer that re-sealed the record, so the record lies in the range of every version it is under;
  • it runs on a schedule until a run reports nothing scanned. The retire, and later the destroy, of the old version are the administrative job’s, see Rotation cadence.

The examples keep one keyring’s records in a collection or table. Each keyring counts its own epochs, so records of several keyrings in one table keep their keyring’s id beside the marker, and the query compares within one keyring, tenant = $2 AND seal < $1, on an index over both fields: a composite index in Firestore.

The trust of re-sealed values

A sweep reads every field with decrypt_with_trust, and reports in ResealOutcome::Resealed whether the KeyTrust of any of them is compromised. A value read under a compromised version is untrusted data: whoever holds the leaked DEK can have forged it. Re-sealing it under a new version makes it read as trusted everywhere afterwards.

So after a compromise the application decides per record before it re-seals:

  • a quarantine field beside the marker, for a person to review;
  • a comparison against a backup taken before the compromise;
  • or acceptance, when forged values do no harm.

SweepReport::resealed_from_compromised counts the records that went through that decision, or fewer on the BigQuery MERGE path, whose batches with a conflict count as skipped.

Sweeps on Firestore

A sweep of a Firestore collection: the seal marker as a field, the query for the documents behind, and the conditional write back. The mechanism is in Sweeps, and the example has the five properties of Sweeps by store: it resumes without a checkpoint, a concurrent writer wins, concurrency bounds the load, each write stores the marker of its sealer, and it runs on a schedule until a run scans nothing.

The marker is a bytes field, seal, and the query is one range filter on it. Firestore indexes a field ascending and descending by default, and the query needs the ascending index only, so an exemption keeps just that one:

gcloud firestore indexes fields update seal --collection-group=users --index=order=ASCENDING

The query streams with stream_query_with_errors(), so that a document that does not read is a failed candidate, and the sweep never ends early on it. sweep::run_batched cuts the documents into batches of 500, each re-sealed through one sealer and written back in one BatchWrite.             SweepError::Write(None) => f.write_str("its write returned no status"),
        }
    }
}

/// Re-seals every user whose marker is below the current one, in batches of [`BATCH_SIZE`] with
/// [`CONCURRENCY`] in flight, and returns the sweep's report.
async fn sweep_users(
    keyring: &UsersKeyring,
    writer: &FirestoreSimpleBatchWriter,
) -> Result<SweepReport, FirestoreError> {
    let current: SealMarker = keyring.record().seal_marker();
    let candidates = writer
        .db
        .fluent()
        .select()
        .fields(paths!(UserFields::{email, seal}))
        .from(USERS)
        .filter(|q| q.field("seal").less_than(current))
        .obj::<UserDoc>()
        .stream_query_with_errors()
        .await?
        .err_into::<SweepError>();
    let report: SweepReport = sweep::run_batched(
        keyring.id(),
        candidates,
        BatchedSweepOptions::new()
            .with_batch_size(BATCH_SIZE)
            .with_concurrency(CONCURRENCY),
        |docs: Vec<UserDoc>| reseal_batch(keyring, writer, docs),
    )
    .await;
    Ok(report)
}

/// The AAD the application gave its envelope values.
fn envelope_aad(id: &str) -> Vec<u8> {
    format!("users:{id}:email").into_bytes()
}

/// `email`, the stored bytes of user `id` under the marker `seal`, under the active version of
/// `sealer`, and the outcome of its re-seal. A keyring value under that version comes back as it
/// is, with `ResealOutcome::Skipped`.
async fn reseal_email(
    keyring: &UsersKeyring,
    sealer: &UsersSealer<'_>,
    id: &str,
    seal: SealMarker,
    email: &[u8],
) -> KeyringResult<(Encrypted<Email, Randomized>, ResealOutcome)> {
    let aad = EMAIL.aad(&EntityId::try_from(id)?);
    if seal == SealMarker::ENVELOPE {
        let value = Encrypted::<Email, Envelope>::try_from(email.to_vec())?;
        let opened: Email = keyring
            .decrypt_envelope_for_migration(&envelope_aad(id), &value, ENVELOPE_ALGORITHM)
            .await?;
        // Envelope values name no key version, so the record carries no trust to decide on
        let resealed = ResealOutcome::Resealed {
            from_compromised: false,
        };
        return Ok((sealer.encrypt(&aad, &opened).await?, resealed));
    }
    let email = Encrypted::<Email, Randomized>::try_from(email.to_vec())?;
    let resealed: Option<Resealed<Email, Randomized>> = sealer.reseal(&aad, &email).await?;
    Ok(match resealed {
        Some(resealed) => {
            let from_compromised = matches!(resealed.trust, KeyTrust::Compromised(_));
            (resealed.value, ResealOutcome::Resealed { from_compromised })
        }
        // The value is current: the record gets the marker alone
        None => (email, ResealOutcome::Skipped),
    })
}

/// Re-seals a batch of documents through one sealer and writes them back in one `BatchWrite`,
/// each write stamped with the sealer's marker and conditional on the update time the query read.
/// A batch is not atomic: a conflict fails its own write only.
async fn reseal_batch(
    keyring: &UsersKeyring,
    writer: &FirestoreSimpleBatchWriter,
    docs: Vec<UserDoc>,
) -> Result<Vec<(UserDoc, Result<ResealOutcome, SweepError>)>, SweepError> {
    let sealer: UsersSealer<'_> = keyring.sealer().await;
    let seal: SealMarker = sealer.record().seal_marker();
    let mut batch = writer.new_batch();
    let mut done: Vec<(UserDoc, Result<ResealOutcome, SweepError>)> =
        Vec::with_capacity(docs.len());
    let mut queued: Vec<(UserDoc, ResealOutcome)> = Vec::with_capacity(docs.len());
    for doc in docs {
        let queue = async {
            let (email, outcome) =
                reseal_email(keyring, &sealer, &doc.id, doc.seal, &doc.email).await?;
            writer
                .db
                .fluent()
                .update()
                .fields(paths!(UserFields::{email, seal}))
                .in_col(USERS)
                .precondition(FirestoreWritePrecondition::UpdateTime(doc.updated.into()))
                .document_id(&doc.id)
                .object(&UserFields { email, seal })
                .add_to_batch(&mut batch)?;
            Ok::<ResealOutcome, SweepError>(outcome)
        };
        match queue.await {
            Ok(outcome) => queued.push((doc, outcome)),
            Err(error) => done.push((doc, Err(error))),
        }
    }
    if queued.is_empty() {
        return Ok(done);
    }
    let response: FirestoreBatchWriteResponse = batch.write().await?;
    done.extend(queued.into_iter().enumerate().map(|(index, (doc, outcome))| {
        let code: Option<Code> = response
            .statuses
            .get(index)
            .and_then(|status| Code::try_from(status.code).ok());
        let outcome = match code {
            Some(Code::Ok) => Ok(outcome),
            // A write since the query: the writer re-sealed the document itself
            Some(Code::FailedPrecondition) => Ok(ResealOutcome::Skipped),
            _ => Err(SweepError::Write(code)),
        };
        (doc, outcome)
    }));
    Ok(done)
}

The retry limit ends retries, not a request: a request on a connection that never answers, the candidate query included, waits until HTTP/2 keep-alive drops the connection, so the job timeout of the scheduler that runs the sweep is what bounds a run.

A range filter never matches a document without the field. #[serde(default)] reads a document written before the marker as SealMarker::ENVELOPE, and the query finds it only once its seal holds those bytes, see Move envelope values to a keyring.

A partitioned query does not fit the sweep: PartitionQuery takes no filter, so its workers would read every document, the current ones included.

The marker takes 10 bytes of a document: the field name as a 5-byte string and the 5 bytes of the value. Its entry in the ascending index takes the size of the document’s name, of its parent’s name, of the field name and of the value, plus 32 bytes, by Firestore’s storage size rules: about 70 bytes for a short document id in a top-level collection. 10 million documents hold about 0.1 GB of markers and 0.7 GB of index, about $0.13 a month at about $0.18 per GiB.

The sweep_firestore example runs this sweep end to end, from the writes to the report, on the Firestore emulator. Its memory holds the batches in flight only, so it runs the same over millions of documents. A stream that ends early, on a deadline or an error, leaves the documents it did not reach below the current marker, and the next run of the sweep finds them.

Sweeps on PostgreSQL

A sweep of a PostgreSQL table: the seal marker as a column, the query for the rows behind, and the conditional write back. The mechanism is in Sweeps, and the example has the five properties of Sweeps by store: it resumes without a checkpoint, a concurrent writer wins, concurrency bounds the load, each write stores the marker of its sealer, and it runs on a schedule until a run scans nothing.

The marker is a BYTEA column with a btree index. Its default, the bytes of SealMarker::ENVELOPE, gives the rows written before the column a marker too:

ALTER TABLE users ADD COLUMN seal BYTEA NOT NULL DEFAULT '\x0100000000';
CREATE INDEX users_seal ON users (seal);

The candidates are one query, seal < $1 with no ORDER BY, so the planner is free to read them from the index on seal, and query_raw streams its rows: memory holds the batches in flight only. The query holds its connection for as long as it streams, so the UPDATEs go through a second one. sweep::run_batched cuts the candidates into batches of 1000 rows, each re-sealed through one sealer and written back in one UPDATE over arrays of the ids, the new values and the values it read. The UPDATE is conditional on the bytes it read, which a write of any other process changes, since every randomised value has its own nonce. A process that has not seen the promotion yet still seals under the old version and stamps the old epoch, which the row holds already, so the marker alone does not detect its write:

/// Re-seals every user whose marker is below the current one, read through `reader` and written
/// back through `writer` in batches of [`BATCH_SIZE`] with [`CONCURRENCY`] in flight, and returns
/// the sweep's report.
async fn sweep_users(
    keyring: &UsersKeyring,
    reader: &Client,
    writer: &Client,
) -> Result<SweepReport, tokio_postgres::Error> {
    let current: SealMarker = keyring.record().seal_marker();
    // A row whose id does not read is a failed candidate. An error of the stream itself is one
    // failed candidate and ends the stream: once its connection drops, the stream returns that
    // error on every poll and never its end.
    let candidates = reader
        .query_raw("SELECT id, email, seal FROM users WHERE seal < $1", [current])
        .await?
        .scan(
            false,
            |ended: &mut bool, row: Result<Row, tokio_postgres::Error>| {
                if *ended {
                    return future::ready(None);
                }
                *ended = row.is_err();
                future::ready(Some(row))
            },
        )
        .map(|row: Result<Row, tokio_postgres::Error>| {
            let row: Row = row?;
            Ok::<UserRow, SweepError>(UserRow {
                id: row.try_get("id")?,
                row,
            })
        });
    let report: SweepReport = sweep::run_batched(
        keyring.id(),
        candidates,
        BatchedSweepOptions::new()
            .with_batch_size(BATCH_SIZE)
            .with_concurrency(CONCURRENCY),
        |batch: Vec<UserRow>| reseal_batch(keyring, writer, batch),
    )
    .await;
    Ok(report)
}

/// Re-seals a batch of rows through one sealer, and writes it back in one `UPDATE` that stamps
/// the sealer's marker and is conditional, row by row, on the bytes the query read.
async fn reseal_batch(
    keyring: &UsersKeyring,
    client: &Client,
    batch: Vec<UserRow>,
) -> Result<Vec<(UserRow, Result<ResealOutcome, SweepError>)>, SweepError> {
    let sealer: UsersSealer<'_> = keyring.sealer().await;
    let seal: SealMarker = sealer.record().seal_marker();
    let mut done: Vec<(UserRow, Result<ResealOutcome, SweepError>)> =
        Vec::with_capacity(batch.len());
    let mut queued: Vec<(UserRow, ResealOutcome)> = Vec::with_capacity(batch.len());
    let mut ids: Vec<i64> = Vec::with_capacity(batch.len());
    let mut read_emails: Vec<Vec<u8>> = Vec::with_capacity(batch.len());
    let mut emails: Vec<Encrypted<Email, Randomized>> = Vec::with_capacity(batch.len());
    for user in batch {
        match reseal_row(keyring, &sealer, &user).await {
            Ok((read_email, email, outcome)) => {
                ids.push(user.id);
                read_emails.push(read_email);
                emails.push(email);
                queued.push((user, outcome));
            }
            Err(error) => done.push((user, Err(error))),
        }
    }
    let written: HashSet<i64> = client
        .query(
            "UPDATE users SET email = batch.email, seal = $4
             FROM unnest($1::BIGINT[], $2::BYTEA[], $3::BYTEA[]) AS batch(id, email, read_email)
             WHERE users.id = batch.id AND users.email = batch.read_email
             RETURNING users.id",
            &[&ids, &emails, &read_emails, &seal],
        )
        .await?
        .iter()
        .map(|row| row.try_get("id"))
        .collect::<Result<HashSet<i64>, tokio_postgres::Error>>()?;
    done.extend(queued.into_iter().map(|(user, outcome)| {
        // A row the `UPDATE` did not return changed since the query: its writer re-sealed it
        let outcome = if written.contains(&user.id) {
            outcome
        } else {
            ResealOutcome::Skipped
        };
        (user, Ok(outcome))
    }));
    Ok(done)
}

Sweeps on BigQuery

A sweep of a BigQuery table, in two paths: one UPDATE in SQL for the fields BigQuery reads, and a Rust path for the rest. The mechanism is in Sweeps. The Rust path has the five properties of Sweeps by store, and the SQL path states its own below.

The marker is a BYTES column. BigQuery gives a column added to a table NULL in the rows already there, so the column’s default goes with a write of SealMarker::ENVELOPE into them:

ALTER TABLE users ADD COLUMN seal BYTES;
ALTER TABLE users ALTER COLUMN seal SET DEFAULT b'\x01\x00\x00\x00\x00';
UPDATE users SET seal = b'\x01\x00\x00\x00\x00' WHERE seal IS NULL;

A field BigQuery reads, declared with Interop::BigQuery, is re-sealed by one UPDATE in SQL, with no Rust loop and no value leaving BigQuery. Its parameters come from a Readable(Purpose::Randomized) export, see Exporting a keyset to BigQuery: @kms_key is the export’s key_uri(), @keyset its value(), and @seal the bytes of its marker, keyset.seal_marker().value():

UPDATE users
SET
  email = AEAD.ENCRYPT(
    KEYS.KEYSET_CHAIN(@kms_key, @keyset),
    AEAD.DECRYPT_BYTES(
      KEYS.KEYSET_CHAIN(@kms_key, @keyset), email, CAST(CONCAT('user/', id, '/email') AS BYTES)),
    CAST(CONCAT('user/', id, '/email') AS BYTES)),
  seal = @seal
WHERE seal < @seal AND seal > b'\x01\x00\x00\x00\x00';

AEAD.DECRYPT_BYTES, and AEAD.ENCRYPT of bytes, take the AAD as BYTES, the UTF-8 of the same text. AEAD.ENCRYPT seals under the keyset’s primary, which a Readable export sets to the active version of the record it reads from the store, and EncryptedKeyset::seal_marker() is that record’s marker. So every row the statement re-seals lies in the range of the primary, as a row written through a Sealer does. A keyset exported before a promotion has the previous version as its primary and the previous epoch’s marker, and the rows it re-seals stay in the next sweep’s query, so the sweep exports its keyset after the promotion. The export is a KeyringAdmin call of the administrative job.

The statement re-seals every encrypted field of the row, since the marker it writes covers all of them. Fields of several purposes are sealed under one Readable keyset each, and the statement stamps the marker only when their seal_marker() is the same; otherwise it exports them again. A row with a beacon, which SQL does not compute, goes through the Rust path below, and so does a row under SealMarker::ENVELOPE, the lowest marker, which the statement leaves out: an envelope value does not open under a keyring’s keyset.

This sweep:

  • resumes without a checkpoint: the statement is atomic, a failed one changed nothing, and the next run’s WHERE finds every row it did not write;
  • loses no concurrent write: BigQuery runs DML under snapshot isolation, and of two conflicting statements on the same rows one fails and runs again, and its WHERE then sees the other’s marker;
  • makes no KMS call per record: BigQuery opens the keyset through Cloud KMS for the statement;
  • runs on a schedule until it re-seals no row. The administrative job retires the old version once its range query, SELECT COUNT(*) FROM users WHERE seal >= @start AND (@end IS NULL OR seal < @end), returns 0.

A Readable keyset leaves a compromised version out, so the values under it fail AEAD.DECRYPT_BYTES and the whole statement with them. After a compromise those rows go through the Rust path below, where the sealer’s reseal reports their trust.

Other fields, such as ChaCha20-Poly1305 values or values under a custom AAD, are re-sealed in Rust. BigQuery runs only a few DML statements on one table at a time, so the write is one MERGE per batch of rows rather than one UPDATE per row, conditional on the bytes each row held:

MERGE users u
USING UNNEST(@rows) p
ON u.id = p.id AND u.phone = p.old_phone
WHEN MATCHED THEN UPDATE SET phone = p.phone, seal = @seal;

The rows stream from the application’s BigQuery client, one query of SELECT id, phone, seal FROM users WHERE seal < @current with the current marker, and sweep::run_batched cuts them into batches. Each batch is re-sealed through one sealer, and the client runs the MERGE with @seal bound to the marker of the sealer’s record. Every row of a batch goes into @rows, the current ones with their bytes as they are, so that each gets the marker:

        self.0.to_plaintext()
    }

    fn from_plaintext(plaintext: SecretValue) -> KmsAeadResult<Self> {
        String::from_plaintext(plaintext).map(Phone)
    }
}

/// A row of `SELECT id, phone, seal FROM users WHERE seal < @current`.
struct UserRow {
    id: String,
    /// An envelope value under `SealMarker::ENVELOPE`, a keyring value under any other marker.
    phone: Vec<u8>,
    seal: SealMarker,
}

/// The row id, and nothing of its columns.
impl Display for UserRow {
    fn fmt(&self, f: &mut Formatter<'_>) -> fmt::Result {
        write!(f, "users/{}", self.id)
    }
}

/// One element of `@rows`: a row with the bytes it held and the bytes to write.
struct PhoneUpdate {
    id: String,
    old_phone: Vec<u8>,
    phone: Encrypted<Phone, Randomized>,
}

/// The AAD the application gave its envelope values.
fn envelope_aad(id: &str) -> Vec<u8> {
    format!("users:{id}:phone").into_bytes()
}

/// `phone`, the stored bytes of user `id` under the marker `seal`, under the active version of
/// `sealer`, and the outcome of its re-seal. A keyring value under that version comes back as it
/// is, with `ResealOutcome::Skipped`.
async fn reseal_phone(
    keyring: &UsersKeyring,
    sealer: &UsersSealer<'_>,
    id: &str,
    seal: SealMarker,
    phone: &[u8],
) -> KeyringResult<(Encrypted<Phone, Randomized>, ResealOutcome)> {
    let aad = PHONE.aad(&EntityId::try_from(id)?);
    if seal == SealMarker::ENVELOPE {
        let value = Encrypted::<Phone, Envelope>::try_from(phone.to_vec())?;
        let opened: Phone = keyring
            .decrypt_envelope_for_migration(&envelope_aad(id), &value, ENVELOPE_ALGORITHM)
            .await?;
        // Envelope values name no key version, so the record carries no trust to decide on
        let resealed = ResealOutcome::Resealed {
            from_compromised: false,
        };
        return Ok((sealer.encrypt(&aad, &opened).await?, resealed));
    }
    let phone = Encrypted::<Phone, Randomized>::try_from(phone.to_vec())?;
    let resealed: Option<Resealed<Phone, Randomized>> = sealer.reseal(&aad, &phone).await?;
    Ok(match resealed {
        Some(resealed) => {
            let from_compromised = matches!(resealed.trust, KeyTrust::Compromised(_));
            (resealed.value, ResealOutcome::Resealed { from_compromised })
        }
        // The value is current: the row gets the marker alone
        None => (phone, ResealOutcome::Skipped),
    })
}

/// Re-seals the `rows` of the query in batches, one sealer per batch, and writes each batch
/// through `merge`, which runs the `MERGE` with `@seal` bound to the marker it is given, the
/// marker of the batch's sealer, and returns its number of affected rows. `ClientError` is the
/// error of the application's BigQuery client, which a row that did not read returns and a
/// `KeyringError` converts into, and its `Display` is the text the sweep logs for a failure.
async fn sweep_phones<Rows, Merge, Merged, ClientError>(
    keyring: &UsersKeyring,
    rows: Rows,
    merge: Merge,
) -> SweepReport
where
    Rows: Stream<Item = Result<UserRow, ClientError>>,
    Merge: Fn(Vec<PhoneUpdate>, SealMarker) -> Merged,
    Merged: Future<Output = Result<u64, ClientError>>,
    ClientError: From<KeyringError> + Display,
{
    let options: BatchedSweepOptions = BatchedSweepOptions::new()
        .with_batch_size(BATCH_SIZE)
        .with_concurrency(CONCURRENCY);
    sweep::run_batched(keyring.id(), rows, options, |batch: Vec<UserRow>| {
        let merge = &merge;
        async move {
            let sealer: UsersSealer<'_> = keyring.sealer().await;
            let mut done: Vec<(UserRow, Result<ResealOutcome, ClientError>)> =
                Vec::with_capacity(batch.len());
            let mut queued: Vec<(UserRow, ResealOutcome)> = Vec::with_capacity(batch.len());
            let mut updates: Vec<PhoneUpdate> = Vec::with_capacity(batch.len());
            for row in batch {
                match reseal_phone(keyring, &sealer, &row.id, row.seal, &row.phone).await {
                    Ok((phone, outcome)) => {
                        updates.push(PhoneUpdate {
                            id: row.id.clone(),
                            old_phone: row.phone.clone(),
                            phone,
                        });
                        queued.push((row, outcome));
                    }
                    Err(error) => done.push((row, Err(error.into()))),
                }
            }
            let merged: u64 = merge(updates, sealer.record().seal_marker()).await?;
            // A `MERGE` returns a count, not the rows: a batch with one row a concurrent writer
            // changed counts every row as skipped
            let all_written = u64::try_from(queued.len()) == Ok(merged);
            done.extend(queued.into_iter().map(|(row, outcome)| {
                (row, Ok(if all_written { outcome } else { ResealOutcome::Skipped }))
            }));
            Ok(done)
        }
    })
    .await
}

fn main() {}

A batch is re-sealed sequentially inside its call, and concurrency bounds the batches in flight, which BigQuery’s limit on concurrent DML per table sets low. The five properties hold per batch: a row that a concurrent writer changed fails the ON condition and stays in the query for the next run.

A MERGE returns a count, not the rows it changed, so a batch with one such row counts all its rows as Skipped, the ones it wrote included. Its re-seals from a compromised version then drop out of SweepReport::resealed_from_compromised, although they went through the trust decision below, so on this path that count is a lower bound.

The marker takes 7 bytes of a row: its 5 bytes and the 2 BigQuery counts for every BYTES value. Measured on BigQuery, 100,000 markers held 700,000 bytes, and the sweep’s query processed 700,000 bytes, the seal column alone. BigQuery does not cluster a BYTES column, so the query reads the whole column: about 70 MB at 10 million rows, about $0.0004 per query at $6.25 per TiB on demand, and its storage about $0.0013 a month at $0.02 per GiB.

The sweep_bigquery example runs the UPDATE above end to end, from the writes to the count of re-sealed rows, against Cloud KMS and BigQuery. It writes the rows through the Storage Write API, and the UPDATE re-seals them straight after: DML can modify rows recently written through its gRPC interface.

Emergency runbook

Rehearse each on a staging keyring, on a schedule, and record how long propagation took.

A plaintext DEK leaked

Or is suspected to have.

  1. mark_compromised(key_id, note): the version is flagged and, if active, replaced in one write by a version that is active at once. The replacement skips the staged wait on purpose: sealing under the leaked key stops at each process’s next refresh, and a process that has not seen the replacement yet reloads its record once, rate-limited, when it meets a value under it. When the KMS cannot encrypt a new DEK, the flag lands alone and encrypt fails with NoActiveVersion; once the KMS answers, rotate and promote_now at once, since nothing seals under the purpose meanwhile, or promote_now the pending version if the purpose has one. promote would refuse with PromotionTooEarly for up to record_ttl from the staging. A pending version itself is never compromised: destroy it instead;
  2. every process stops using the key within the bound of the record cache, and its DEK is evicted from the DEK cache. With the default Block policy values under the version stop decrypting through decrypt. Set Allow for the time of the sweep if availability matters more, and be aware the leaked DEK can forge values under its id meanwhile;
  3. sweep the records in the compromised version’s range, see Records under a version, reading them with decrypt_with_trust, and decide per record on the values read through the compromised version, see The trust of re-sealed values. Run the range query again once every process has had time to refresh its record, for the writes of processes that had not seen the flag yet;
  4. export the BigQuery keysets again: a Readable keyset leaves the compromised version out. Delete the Single keyset of the compromised version once the sweep is done;
  5. retire the version once the sweep is done and its range query returns nothing.

Rotation protects nothing already copied: backups, point-in-time recovery and data exports still hold values the leaked DEK opens. Treat them as exposed and revoke the secrets inside them.

A KMS IAM over-grant

  1. Fix the IAM binding, back to the split in KMS rights;
  2. rotate the KEK in the KMS and reencrypt_deks();
  3. with KMS data-access logs enabled in advance, list the Decrypt calls the wrong principal made: every encrypted DEK they decrypted is a leaked DEK, see above. Without those logs, every version is a leaked DEK.

An encrypted DEK or the keyring record leaked

Harmless by itself, since decrypting needs the KMS. If the attacker may also gain Decrypt on the KEK, follow the IAM over-grant steps. If the attacker may also write the keyring store, see the next case and the store-writer threat in Keyring deployment.

A version the administrative job did not create

This case starts from the ERROR event of a refused record that moves backwards, or from a version in the record that the administrative job’s log does not show. The event’s rule names the version that moved backwards, except the seal epoch moved back, which names none: compare the versions of the record in the store with the job’s log to find the one it did not create. Either means that something other than the job wrote the record: a restore, which the next case covers, or a writer of the store.

  1. If the version is active, mark_compromised it, so that nothing new is sealed under it from each process’s next refresh. If it is pending, destroy it;
  2. retire and then destroy the version, after a sweep if values were sealed under it;
  3. check the KMS audit log for the Encrypt call that encrypted its DEK. None means its encrypted DEK was copied or relabelled from another version, of this keyring or of another under the same KEK, which the KMS decrypts as it would the original; one from a principal other than the administrative job is an IAM over-grant, see above;
  4. audit who can write the keyring store: the application has no write, and only the administrative job should.

The keyring record was deleted or corrupted

Running processes keep their cached record and log a WARN; new processes fail at open with RecordMissing or RecordInvalid.

  1. Restore the record from the store’s backup: Firestore point-in-time recovery, a PostgreSQL backup, or a noncurrent version of the Cloud Storage or S3 object. The encrypted DEKs inside are still valid under the KEK;
  2. repeat on the restored record every administrative call made after the copy was taken, from the administrative job’s log, before starting new processes.

A running process refuses a restored copy that is older than its cached record and logs an ERROR, while new processes take it. Values are never lost with the record as long as a copy of it exists. Without any copy they are gone, so keep versioning on the bucket and back up the table.

Crypto-shredding

To make a scope’s values unrecoverable:

  • with a KEK per scope: destroy the KEK’s versions in the KMS. Every encrypted DEK of the scope is then unrecoverable, backups included;
  • with a shared KEK: dangerously_destroy_all_versions, which destroys every version of the keyring in one write, so that it encrypts and decrypts nothing from then on. A backup of the record still holds the encrypted DEKs, which the KMS opens as long as the KEK version that encrypted them exists, so then either delete the record and every backup of it, or destroy that KEK version: on GCP, Vault Transit and the local KMS, rotate the KEK, reencrypt_deks every other keyring under it, then destroy the previous KEK version. On AWS rotated key material is never destroyed, so only the deletion of the KMS key itself shreds.

A deployment that needs shredding guarantees uses a KEK per scope.

A KMS outage

DEKs in the cache serve reads and writes until their TTL. A longer DEK cache TTL buys time at the cost of a longer life of plaintext keys in memory. No decryption, encryption or rotation succeeds until the KMS returns, and errors carry the provider’s message. mark_compromised still lands the flag.

Tink’s KMS envelope

KmsAeadEnvelope::encrypt writes Tink’s KMS envelope, and Encrypted::join writes it from a bare value and an encrypted DEK. separate reads it back:

use kms_aead::backends::Ring;
use kms_aead::formats::Envelope;
use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{Encrypted, KmsAeadEnvelope};
use secret_vault_value::SecretValue;

#[tokio::main(flavor = "current_thread")]
async fn main() -> kms_aead::KmsAeadResult<()> {
let provider = LocalKmsProvider::<Ring>::ephemeral(LocalKekId::try_from("example".to_string())?)?;
let envelope = KmsAeadEnvelope::<LocalKmsProvider<Ring>, Ring>::new(provider)?;
let encrypted: Encrypted<SecretValue, Envelope> =
    envelope.encrypt(b"aad", &SecretValue::from("secret")).await?;

let (bare, encrypted_dek) = encrypted.separate()?;
let joined = Encrypted::<SecretValue, Envelope>::join(&bare, &encrypted_dek)?;
assert_eq!(joined.value(), encrypted.value());
Ok(())
}
  • w is 1 to 4,096 bytes, the limit of every Tink implementation, on write and on read;
  • the encrypted DEK is the provider’s EncryptedDataEncryptionKey, the KMS ciphertext of the serialised DEK, or of the raw DEK for Azure;
  • the AAD goes to the DEK’s AEAD only. The KMS encryption of the DEK has no AAD, as in Tink, so Tink’s AWS client sends no encryption context and its GCP client no additional authenticated data;
  • the rest is a Bare value.

Tink keysets and the TINK prefix

Two items describe the TINK-prefixed values:

  • kms_aead::KeyId: the key id of Tink’s output prefix of type TINK, [0x01][key id: u32 BE], the start of every Randomized and Deterministic value and of every beacon. It picks the key that opens the value, and Tink and BigQuery pick the key of a keyset by it. It is not authenticated;
  • kms_aead::formats::TinkKeyset: a serialised google.crypto.tink.Keyset of enabled, symmetric, TINK-prefixed keys, the bytes tinkey writes for the same keys. Encrypted by a Cloud KMS key, it is the keyset of BigQuery’s KEYS.KEYSET_CHAIN: an application writes it for its one key, see One fixed key, and a keyring exports it for its versions.

TinkKeyset::into_encrypted_bytes writes the keyset encrypted by a KMS key, as Tink writes an encrypted keyset: a google.crypto.tink.EncryptedKeyset whose encrypted_keyset, field 2, is the KMS ciphertext of the serialised keyset, encrypted with no associated data. Tink’s binary keyset writers leave out keyset_info, field 3, and so does the library. Tink’s KeysetHandle.read reads it with the KMS client of KekRef::tink_key_uri, which Tink has for GCP and AWS keys, and Tink for Go for Vault Transit keys too. A keyring exports it for its versions, see Exporting a keyset to Tink.

A Bare value is Tink’s AEAD output under a key with the output prefix RAW, and the part of every Envelope value after the encrypted DEK. It names no key: the application keeps track of the key that opens it.

The check reads the framing only, and whether the bytes are authentic is known when they are decrypted. With legacy-formats, an Envelope value also holds the envelope layout v1 of 0.29 and the length-prefixed envelope, checked by their lengths, so a column decodes its old rows into the same type until they are upgraded, see Upgrading stored values. Without the feature, Encrypted::try_from refuses them with LEGACY_FORMAT. separate refuses them in every build. The layout of 32-bit targets before 0.24.0 has Tink’s framing, so it reads as an Envelope value in every build, and KmsAeadEnvelope::decrypt opens it with legacy-formats.

The plaintext inside is the encoding of the value’s Plaintext type: UTF-8 for String, the bytes themselves for Vec<u8> and SecretValue, true or false for bool, decimal ASCII for the integers, and compact JSON for Json<T>. See Stored values.

Beacons

A Beacon<T> is a prefix and a truncated HMAC-SHA256:

[0x01][key id: u32 BE][HMAC-SHA256: the first ceil(bits / 8) bytes]
  • 0x01 is the version of the beacon layout. A later layout takes another first byte, so that beacons of both layouts can share a column during a re-index;
  • the key id names the beacon key that calculated the beacon;
  • the HMAC keeps its first bits bits, and the unused low bits of the last byte are zero. A beacon is 6 to 37 bytes.

The HMAC covers the bits, the context and the plaintext, as the Plaintext type encodes it:

HMAC-SHA256(key, [bits: u16 BE][context length: u32 BE][context][plaintext])

so that beacons of two fields, or of two bit counts, never match. Beacon::try_from checks the prefix and that 1 to 32 bytes of HMAC follow, and fails with INVALID_BEACON_FORMAT otherwise.

Keyring key ids

kms-aead-keyring writes the key id of a version into the TINK prefix of every value and beacon under it. The two high bits of the id are the purpose, and the rest is the ordinal:

BitsMeaning
31set for deterministic versions
30set for beacon versions
0 to 29the ordinal, from 1, counted per purpose

So the ids of each purpose are:

  • randomised: 1, 2, 3, …;
  • deterministic: 2147483649, 2147483650, …;
  • beacon: 1073741825, 1073741826, ….

An id whose ordinal is 0, such as 0, 2^30 and 2^31, and an id with both high bits set are reserved: a value that carries one fails with ReservedKeyId. A value whose id is of another purpose than the call fails with KeyPurposeMismatch. Both fail before any store or KMS call. Ids are never reused: a destroyed version keeps its id in the record. A key id goes up to 2^32 - 1, so a SQL column holding one is a BIGINT.

Seal markers

A seal marker is the seal epoch of the keyring record a write sealed a record’s fields under, which the application stores beside them:

[0x01][seal epoch: u32 BE]

5 bytes in all, so that markers compare as their epochs do, and so do their bytes as Firestore, PostgreSQL and BigQuery compare them. SealMarker::ENVELOPE, 01 00 00 00 00, is epoch 0, the marker of a record of envelope values. SealMarker::try_from fails with InvalidSealMarker on bytes of any other length or first byte. The serde feature stores a marker as bytes, an array of numbers in serde_json, and the postgres and sqlx features as BYTEA. See Sweeps for the query it serves.

KeyVersion::seal_range() returns the markers of a version’s seal_epochs as a SealRange: start(), and end(), None while the range is open. A record whose fields were sealed through one Sealer, and which stores the marker of the sealer’s record, lies in the range of every version its fields are under. See Records under a version for the query it serves.

Telling layouts apart

The first bytes of a stored value:

First bytesLayout
00 00 00 00the length-prefixed envelope of 0.28.1 and earlier
00, then a length of 1 to 4,096Tink’s KMS envelope, or the 4-byte length prefix of 32-bit targets before 0.24.0
01envelope layout v1 of 0.29, or a TINK-prefixed value
FF 01encrypted DEK layout v1 of 0.29

Only the decrypted DEK tells a Tink envelope from the 32-bit layout before 0.24.0: a raw key of 16 or 32 bytes against a serialised Tink key, whose lengths differ. An encrypted DEK of AWS, Azure or the local KMS also starts with 0x01, and Tink’s LEGACY and CRUNCHY output prefixes with 0x00.

A column that holds two layouts:

  • Tink envelopes and TINK-prefixed values: the first byte, 0x00 or 0x01;
  • Tink envelopes and 0.29 envelopes: the first byte, 0x00 or 0x01;
  • Tink envelopes and 0.28.1 envelopes: the first four bytes;
  • 0.29 envelopes and TINK-prefixed values: no byte tells them apart, so the layout is recorded outside the value, such as in another column;
  • bare values and any other layout: a bare value has no framing, and its random nonce can start with any byte, so a column of bare values holds no other layout;
  • encrypted DEKs of 0.29 and of 0.30: 0xFF 0x01 starts no encrypted DEK of a built-in provider, so the library tells them apart for those. It never inspects the bytes of an application’s own provider: strip the header [0xFF][0x01][k][key version] of its 0.29 keys before reading them.

Values written by 0.29 and earlier

The layouts of 0.29 and earlier are read only with the deprecated legacy-formats feature:

  • KmsAeadEnvelope::decrypt reads the three envelope layouts, which Encrypted<T, Envelope> holds with the feature;
  • the *_with_encrypted_dek calls and the DEK cache read the encrypted DEK layout v1 of 0.29 and raw encrypted DEKs.

Encrypted::separate never reads the older envelope layouts: for Azure, the encrypted DEK they hold needs the provider to become its bytes.

Without the feature, reading them fails with KmsAeadError::LegacyFormat, the code LEGACY_FORMAT, and one of:

  • KmsAeadLegacyFormat::EnvelopeV1;
  • KmsAeadLegacyFormat::LengthPrefixedEnvelope;
  • KmsAeadLegacyFormat::EncryptedDekV1;
  • KmsAeadLegacyFormat::RawEncryptedDek, for an encrypted DEK that decrypts to the raw key. The values of 32-bit targets before 0.24.0 fail with it, since their framing is Tink’s.

The error never echoes the bytes read. With the feature, the first read of each layout in a process logs one WARN event that names the upgrade methods. Without it, the KMS AEAD decrypt spans of such values record error_code=LEGACY_FORMAT, see Observability.

Upgrading stored values

With legacy-formats, two methods of KmsAeadEnvelope rewrite a stored value in Tink’s format, and return None when it already is in it, so a sweep writes only the rows that change:

  • upgrade_legacy_value, for envelope values;
  • upgrade_legacy_encrypted_dek, for encrypted DEKs stored apart, such as the bytes of 0.29’s to_bytes.

Each decrypts the DEK with the provider, without the DEK cache, and encrypts it again as a serialised Tink key when it was in an older layout: one KMS call for a current value, two for an old one. A value in Tink’s framing needs the decryption to be told from the 32-bit layout before 0.24.0. The AEAD bytes stay as they are.

An upgraded DEK is encrypted under the KEK’s current version, so the upgrade also does what reencrypt_dek and reencrypt_encrypted_dek do for a value or a DEK already in Tink’s format, see Re-encrypting DEKs after a KEK rotation. Those two refuse a layout of 0.29 or earlier with LEGACY_FORMAT, so a sweep after a KEK rotation upgrades a value in an old layout and re-encrypts the DEK of a value in Tink’s format.

The envelope’s algorithm is the one the values were sealed with: ChaCha20-Poly1305 for values that 0.29 and earlier sealed under their default. A raw DEK does not record its algorithm, and the encrypted DEK of the upgrade records it as a Tink key type, so upgrade_legacy_value takes the value’s AAD and opens the value before it writes anything. Under another algorithm or another AAD it fails with DECRYPT. upgrade_legacy_encrypted_dek has no value to open, so it records the envelope’s algorithm for any key of its length. Be aware not to upgrade a DEK stored apart under another algorithm than its values were sealed with: use upgrade_legacy_value wherever the values are at hand.

A sweep over stored rows:

use kms_aead::backends::AeadBackend;
use kms_aead::formats::Envelope;
use kms_aead::{Encrypted, KmsAeadEncryptionProvider, KmsAeadEnvelope, KmsAeadResult};
use secret_vault_value::SecretValue;

/// A stored envelope value and the AAD it was sealed under.
struct Row {
    aad: Vec<u8>,
    value: Vec<u8>,
}

/// Rewrites the envelope values of `rows` in Tink's format, and returns how many changed.
#[allow(deprecated)]
async fn upgrade_values<P, B>(
    envelope: &KmsAeadEnvelope<P, B>,
    rows: &mut [Row],
) -> KmsAeadResult<usize>
where
    P: KmsAeadEncryptionProvider + Send + Sync,
    B: AeadBackend,
{
    let mut upgraded = 0;
    for row in rows.iter_mut() {
        let stored = Encrypted::<SecretValue, Envelope>::try_from(row.value.clone())?;
        if let Some(value) = envelope.upgrade_legacy_value(&row.aad, &stored).await? {
            row.value = value.into_value();
            upgraded += 1;
        }
    }
    Ok(upgraded)
}

use kms_aead::providers::{LocalKekId, LocalKmsProvider};
use kms_aead::{AeadAlgorithm, AeadCipher, KmsAeadEnvelopeOptions};
#[tokio::main(flavor = "current_thread")]
async fn main() -> KmsAeadResult<()> {

// A value as 0.28.1 wrote it: [w: u64 BE][encrypted raw key][cipher text]

let dek = cipher.generate_dek()?;

legacy.extend_from_slice(encrypted_dek.value());
legacy.extend_from_slice(bare.value());

    provider,

Upgrade every reader to 0.30 before the sweep writes: 0.29 and earlier cannot read Tink’s format.

Deprecation

Reading the layouts of 0.29 and earlier is deprecated since 0.30.0 and will be removed in a later breaking release, together with the legacy-formats feature and the upgrade methods, which carry #[deprecated] from their first release, so every call site warns. Without the feature, the older layouts keep failing with LEGACY_FORMAT.

Error handling

Every fallible call returns KmsAeadResult<T>, whose error is kms_aead::errors::KmsAeadError:

  • SystemError: the configuration or the environment, such as invalid provider options or a KMS client that cannot be built;
  • NetworkError: a KMS that could not be reached, did not answer in time, failed on its side or limited the rate of requests. The same call may succeed later;
  • EncryptionError: encrypting or decrypting a value or a DEK failed, a stored value could not be read, or a KMS refused the request, such as a denied permission or a disabled key. The same call fails the same way again;
  • UnsupportedAlgorithm: the backend does not implement the algorithm, from constructors only;
  • LegacyFormat: a stored value in a layout of 0.29 or earlier, which only the legacy-formats feature reads, see Formats.

The enum is #[non_exhaustive], so a match on it needs a _ arm.

What errors never carry

No error carries plaintext, key material in any form, plaintext or encrypted, AAD content or cipher text bytes, in Display or in Debug. An application can log errors with {} and {:?}.

message is meant for a person reading logs. public holds the code, the part safe to return to the application’s own callers, and with the serde feature it is Serialize and Deserialize. std::error::Error::source() returns the root cause, the error of the SDK or library that failed, when there is one.

Observability

The library uses tracing. Every envelope call and every KMS call opens one span at the DEBUG level, and the spans carry what a call used besides how long it took: the mode, the algorithm and backend, whether the DEK came from the cache, the KMS key and its version, and the error code.

The spans are:

  • KMS AEAD encrypt: the envelope’s encrypt, encrypt_with_dek and encrypt_with_encrypted_dek;
  • KMS AEAD decrypt: the envelope’s decrypt, decrypt_with_dek and decrypt_with_encrypted_dek;
  • KMS AEAD generate DEK: generate_encrypted_dek and generate_encrypted_deterministic_dek;
  • KMS AEAD decrypt DEK: decrypt_deterministic_dek;
  • KMS AEAD re-encrypt DEK: reencrypt_dek and reencrypt_encrypted_dek;
  • KMS AEAD beacon: the envelope’s beacon;
  • KMS encrypt DEK: each provider’s encryption of a DEK;
  • KMS decrypt DEK: each provider’s decryption of a DEK;
  • KMS random: a call to the GCP or AWS KMS generator, when the provider uses it.

The KMS spans nest inside the envelope span, so a DEK the envelope had to decrypt shows its KMS call as a child, and a DEK served by the cache shows none. AeadCipher and DeterministicCipher open no spans: they run once per value inside the caller’s span.

What is never logged

No span field or event carries:

  • plaintext, DEKs in any form, plaintext or encrypted, or KEK material;
  • AAD content, which can hold entity ids and so personal data;
  • cipher text bytes;
  • the length of a value or of its AAD. For AES-256-GCM the plaintext length is the value’s length minus a fixed overhead, and a length tells short values such as yes, no or a country code apart.

Key identifiers are recorded: KEK names, key versions and local KEK ids. A KEK name identifies the project, the location and the key, and a per-tenant KEK name carries the tenant id, so treat the key field accordingly in a trace pipeline.

Errors follow the same rules, see Error handling.

Security considerations

Threat model

Envelope encryption protects stored values from whoever can read the store but cannot use the KEK: a database dump, a backup, a replica, a data export or an operator with read access to the tables. Opening a value needs a KMS decryption, and the KMS checks the caller’s permission and, for the cloud KMSs, writes an audit log entry.

It does not protect values from:

  • a process, or whoever controls it, that may decrypt with the KEK: it can read every value it can fetch;
  • whoever can read the memory of a process while it holds plaintext DEKs, in the DEK cache or as a store-less writer’s DEK;
  • a reader of the store learning which values are equal, for values sealed with deterministic encryption.

The AAD protects a value from being moved: a value copied into another row or column, with an AAD that names its place, fails to open there. The AAD itself is not encrypted, and neither is the length of the encrypted DEK at the start of Tink’s KMS envelope, which is not authenticated either.

An encrypted DEK carries no context that the KMS authenticates. Whoever can write where encrypted DEKs are stored, such as a database table or a keyring store, can copy an encrypted DEK to another record or relabel it, and the KMS decrypts it for any principal allowed to decrypt with that KEK. The controls for this are in the deployment:

  • write access to the stored keys is kept apart from the right to decrypt with the KEK;
  • each isolation boundary, such as a tenant or an environment, has a KEK of its own, so a DEK copied across it fails to decrypt;
  • the KMS audit log of decrypt calls, turned on where the KMS leaves it off by default, shows which principal decrypted which key.

The local KMS has no IAM, no audit log and no HSM, see its limits.

Nonces

Every AEAD algorithm takes a random 96-bit nonce from the backend’s CSPRNG for each value, and writes it in front of the cipher text. NIST SP 800-38D allows 2^32 encryptions under one key with random 96-bit nonces, and the library applies the same bound to every algorithm:

  • the per-call envelope seals one value per DEK, so the bound does not apply to it;
  • a store-less envelope renews its DEK at max_uses, 2^24 by default and at most 2^32;
  • with encrypt_with_dek and AeadCipher, the application counts the values it seals under one key, and moves to a new key before 2^32;
  • the local KMS seals each DEK it encrypts with AES-256-GCM, so a KEK version is good for about 2^32 encryptions. Add a new version before that.

AES-256-GCM-SIV (RFC 8452) resists nonce misuse: a repeated nonce reveals only whether the two values sealed with it are equal, and does not break integrity.

Deterministic encryption with AES-SIV takes no random nonce.

Data volume

AES-GCM also has a bound on the data under one key, whatever the nonces. The bounds per algorithm:

  • AES-GCM: RFC 8446, section 5.5, allows “up to 2^24.5 full-size records (about 24 million)” of 2^14 bytes, 2^38.5 bytes, “while keeping a safety margin of approximately 2^-57 for Authenticated Encryption (AE) security”. Luykx and Paterson, “Limits on Authenticated Encryption Use in TLS”, table 1, give the same 2^24.5 records for a confidentiality advantage of 2^-60. RFC 8452, section 9, allows 2^48 blocks, 2^52 bytes, under one AES-GCM key for an advantage of 2^-32;
  • AES-GCM-SIV: RFC 8452, section 9, allows 2^32 values of up to 8 GiB each under one key with random nonces for an advantage of 2^-32, so the bound on the number of values bounds it already;
  • ChaCha20-Poly1305: draft-irtf-cfrg-aead-limits, section 6.3, gives it no confidentiality limit beyond the security of ChaCha20 itself, and its integrity bound depends on the number of forgery attempts, which no writer can count.

The bound applies to AES-GCM keys this way:

  • a store-less envelope renews its DEK at max_bytes, 2^38 bytes by default under AES-GCM, below the 2^38.5 of RFC 8446, and at most 2^52, see Volume limit. AES-256-GCM-SIV and ChaCha20-Poly1305 have no default volume limit;
  • with encrypt_with_dek and AeadCipher, the application counts the bytes it seals under one AES-GCM key too, and moves to a new key before 2^38 bytes.

Key lifetime and zeroisation

DataEncryptionKey, LocalKek and the Vault token are zeroised on drop and shown as *** by Debug. The DEK cache zeroises a key when its entry leaves the cache and no with_dek closure holds it.

Some copies are out of the library’s reach:

  • the KMS SDKs and HTTP clients the providers use keep copies of each plaintext DEK in request and response buffers, which kms-aead cannot zeroise. The same holds for the Vault token in the HTTP stack;
  • ring does not zeroise its expanded key schedules, so they stay in freed memory after each call;
  • aws-lc-rs clears its key context through AWS-LC’s allocator, as long as the application leaves that allocator in place. The record keys AES-256-GCM-SIV derives for each call stay on the stack;
  • the RustCrypto backend zeroises its key objects and the per-call Poly1305 and POLYVAL keys;
  • an expired DEK stays in the cache’s memory until the next call on the cache or purge_expired;
  • decrypt returns the application’s own T: Plaintext. Only SecretValue as T is zeroised on drop; String and Vec<u8> take over the decrypted buffer and leave it in freed memory, and what the application does with the value afterwards is its own.

What rotation does not protect

Rotating the KEK in the KMS makes the KMS encrypt new DEKs under the new key version. It does not:

  • re-encrypt the DEKs already stored: they still decrypt with the old key version, which the KMS must keep enabled for as long as those values are read;
  • re-encrypt any value: a DEK that leaked keeps opening every value sealed under it, whatever the KEK version that encrypts it. To retire a leaked DEK, decrypt and encrypt the values again under new DEKs;
  • reach DEKs already in a DEK cache: they keep serving until their entries expire, or until invalidate or clear. The same holds for disabling a KMS key or revoking an IAM grant;
  • renew a store-less writer’s DEK: it is renewed by its policy, or once it leaves the cache.

With the local KMS, rotation is a new KEK version. The old version has to stay in the provider for as long as DEKs encrypted under it are read, and crypto-shredding means destroying every copy of it, backups included.

Keyring deployment

A keyring record decides which versions are read and which one seals new values, and nothing signs it: its integrity rests on the keyring store’s access control. The two principals of a deployment and their rights are in Applications and administration.

A writer of the keyring store can copy or relabel an encrypted DEK, between versions of one keyring or between keyrings under the same KEK: the KMS decrypts an encrypted DEK for any principal allowed to decrypt with the KEK, whatever version or keyring it is filed under. Such a writer can bring a compromised or destroyed version’s DEK back into use under a new key id, or point one tenant’s version at another tenant’s DEK. A writer without KMS rights cannot add a DEK of its own, since every decryption names the configured KEK and the KMS refuses a DEK encrypted under another key. The controls for this are the deployment’s, as in the threat model:

  • write access to the keyring store for the administration only, and read-only access for the applications;
  • one KEK per isolation boundary, such as a tenant or an environment, so a DEK copied across it fails to decrypt;
  • backups of the record, or versioning in the store, to compare with and restore from;
  • the KMS audit log of encrypt calls, which shows whether the administrative job encrypted a version’s DEK.

A running process also refuses every record that moves a version backwards, with an ERROR, see Record cache. That catches a rewritten state, such as a cleared compromised flag, and not a copied DEK filed under a new version.

Keyring limits

  • The administration is trusted. KMS encrypt plus store write re-activates any version, and so does an application that provisions keyrings lazily with the admin feature and those rights. The KMS audit log is the detection;
  • a new process has no baseline. A store writer can clear a compromised flag, re-activate a version or restore a destroyed one for the processes that start after the write. Running processes refuse such a record and log an ERROR; new ones take it. The record is not signed in this release;
  • an RSA key on Azure Key Vault encrypts for anyone. With an RSA key the encryption is a public-key operation, so whoever holds the public key encrypts a DEK of their own into the record. Use an AES key, from Managed HSM;
  • decrypt_envelope_for_migration knows no key version. It decrypts the encrypted DEK an envelope value carries, so an encrypted DEK kept from a version, compromised or destroyed since, still opens values through it. Keep it in the read path for the migration only;
  • a destroyed version’s DEK lives as long as the KEK version that encrypted it. A backup of the record holds encrypted DEKs the KMS still opens, see Crypto-shredding;
  • an exported BigQuery keyset holds the versions’ keys, encrypted with no associated data, since BigQuery decrypts it with none. Treat it as a copy of the record’s readable versions, and export again after every rotation and every mark_compromised;
  • a sweep re-seals forgeries as trusted values. Values read through a compromised version are decided per record before a sweep re-seals them, see The trust of re-sealed values;
  • deterministic fields leak equality and frequency, and an equality query across a rotation links a value’s history for whoever reads the query, see What it leaks;
  • beacons leak likely equality and frequency, as far as their bits tell values apart, see What a beacon leaks;
  • a promotion’s guard covers healthy processes only. promote refuses until record_ttl has passed since the rotation, and promote_now skips that. A process whose revalidations fail keeps an older record for longer: when it meets a value under a version it has not seen, it reloads its record, and fails the read when it cannot reach the store. So the wait beyond the record TTL is the operator’s, see Staged rotation.
